# 模块纪律 · 规范

| 字段 | 值 |
|---|---|
| **版本** | v0.1 |
| **规范等级** | **Normative** |
| **来源** | 提炼自 `bazidiy-atoms-workspace` 的工程实践（原子化架构、C1–C4、机器闸、渐进披露） |
| **上级文档** | [`../docs/framework.md`](../docs/framework.md) §17（模块视图） |

---

## 0. 为什么需要这份规范

框架 §1–§20 定义了**接口契约**（I1–I6、合规等级、规范条款），
但**没有定义模块本身的纪律**：一个模块该多大？边界在哪？怎么保证实现不退化？

结果是：接口可以是对的，而实现烂掉 —— 术语被拷贝进各个模块、依赖变成隐式、
文档与代码脱节、约定写在人的脑子里。

**本规范补上这一层。**

### 0.1 与接口规范的关系

| | 管什么 | 失效后果 |
|---|---|---|
| **接口规范**（I1–I6） | 模块之间**怎么对话** | 对接不上 |
| **本规范** | 一个模块**内部怎么组织** | 单体化、术语漂移、约定失效 |

**两者互补，缺一不可。**

## 1. 原子（Atom）

### 1.1 定义

> **原子 = 一个自包含的最小交付单元。它能用一句话说清意图，且文档、实现、测试、资源**同夹存放**。**

### 1.2 结构

```
atoms/<id>/
├── <id>.atom.md      文档 + 机器可读元数据（YAML frontmatter + 正文）
├── detail.json       结构化边车（与 atom.md 一一对应）
├── impl/             实现
├── tests/            测试
├── assets/           资源（可选）
└── tools/            本原子专属工具（可选）
```

**条款：**

| # | 条款 | 理由 |
|---|---|---|
| **A-1** | 每个原子 **MUST** 自包含：文档、实现、测试同夹 | 文档与代码分居两个目录，必然脱节 |
| **A-2** | 原子的**意图 MUST 能用一句话说清** | 说不清 = 该拆 |
| **A-3** | 原子 **MUST** 有唯一标识（`<域>.<名>`） | 依赖引用与检索的锚点 |
| **A-4** | 原子 **MUST NOT** 内嵌另一原子的实现（见 §2 C1） | 内嵌即失去单一真源 |

### 1.3 颗粒度判据

| 太粗 | 太细 | 合适 |
|---|---|---|
| 一句话里出现"并且" | 原子只有一行代码 | 一句话说清一个意图 |

> **判据是"意图"而不是"行数"。** 一个 500 行但只做一件事的原子没问题；
> 一个 20 行但做了两件事的原子该拆。

## 2. 四条代码约定（C1–C4）

### C1 · 零内嵌

> **领域术语的唯一来源 = 本体。代码 **MUST NOT** 内联术语表。**

**反例**：在算法文件里写死 `const TIAN_GAN = ['甲','乙',...]`。

**为什么**：同一个术语表散在三处，改一处漏两处 —— 这就是术语漂移的起点。
框架 `I1-G1` 要求"定义不可变"，而内嵌的表**根本不在版本控制之下**。

| # | 条款 |
|---|---|
| **C1-1** | 术语表 **MUST** 只存在于本体（Ossie YAML / 生成的绑定） |
| **C1-2** | 代码 **MUST** 通过导入使用术语，**MUST NOT** 复制字面量 |

### C2 · 只引用

> **跨原子依赖只用 import / 包引用，**MUST NOT** 拷贝实现。**

| # | 条款 |
|---|---|
| **C2-1** | 原子间依赖 **MUST** 用语言级导入 |
| **C2-2** | 依赖 **MUST** 在同原子的元数据里声明 |
| **C2-3** | **MUST NOT** 出现"为了省事抄一份" |

**拷贝的实现不会跟着上游修 bug** —— 这是隐性分叉。

### C3 · I/O 契约

> **每个原子 **MUST** 声明输入与输出的 schema。**

| # | 条款 |
|---|---|
| **C3-1** | 对外的输入/输出 **MUST** 有机器可校验的 schema |
| **C3-2** | schema **MUST** 与实现实际行为一致（由测试保证） |
| **C3-3** | 知识型原子 **MUST** 提供"术语查询 → 子图"式的结构化出口 |

**为什么**：没有 I/O 契约，Agent 就无法在不读实现的前提下调用它 ——
这正是框架 `A-2`「拒绝可自纠」的前提。

### C4 · 依赖透明

> **声明的依赖 **MUST** 等于真实的 import。**

| # | 条款 |
|---|---|
| **C4-1** | 元数据里的 `deps` **MUST** 等于代码里的真实依赖 |
| **C4-2** | 该等式 **MUST** 由机器闸强制（见 §4），**MUST NOT** 靠人工维护 |
| **C4-3** | **MUST NOT** 有隐式依赖（运行时才发现的、通过全局状态的） |

**为什么必须机器强制**：人工维护的依赖清单**必然**在第三次改动时过期。
C4 若只写在文档里，就等于没有。

## 3. 渐进披露的两层协议

> **本规范对 Agent 场景最重要的一条。**

### 3.1 两层

| 层 | 内容 | 成本 | 何时读 |
|---|---|---|---|
| **列表层** | `id` + `intent`（一句）+ `when_to_use` | 极低 | 检索时全量扫 |
| **详情层** | 完整正文（四节） | 高 | **命中后才整篇读** |

### 3.2 为什么这是结构性的，不是风格问题

Agent 的上下文预算是硬约束。若每个能力都要读完整文档才知道用不用得上，
**上下文会被候选清单吃光**。

> **渐进披露不是"文档写得好"的问题，是"能不能在预算内找到能力"的问题。**

### 3.3 条款

| # | 条款 |
|---|---|
| **P-1** | 每个可被检索的单元 **MUST** 提供**一句话意图**与**何时使用** |
| **P-2** | 一句话意图 **MUST** 足以判断"要不要读详情"，**MUST NOT** 是标题的同义反复 |
| **P-3** | 检索 **MUST** 只依赖列表层字段，**MUST NOT** 需要加载详情层 |
| **P-4** | 详情层 **MUST** 自足：读到它就不必再读别处 |

### 3.4 与 I6 的关系

I6 的 `ListActions` = 列表层；`DescribeAction` = 详情层。
**本规范为这两个操作提供了"为什么这样切"的依据**，
并新增一条 I6 未覆盖的要求：

> **`FindByCapability` 的 matcher 只能看列表层字段。**
> 若 matcher 需要读详情层，说明列表层写得不够。

## 4. 两类门禁

**框架 §19 只讲了运行期门禁（"该被拒绝的样本集"）。本规范补上构建期。**

| | **构建期门禁** | **运行期门禁** |
|---|---|---|
| 何时跑 | 提交前 / CI | 每次写入 |
| 拦什么 | 违反纪律的**代码与文档** | 违反约束的**数据与操作** |
| 典型 | 依赖不一致、编码错、契约漂移 | 非法关系、越权、版本冲突 |
| 框架对应 | **本规范新增** | §19.1、`I2-G1`、`I4` 各阶段 |

**两者都要。** 只做运行期，实现会慢慢烂掉；只做构建期，脏数据会进去。

### 4.1 构建期门禁的最小集合

| # | 门禁 | 查什么 | 条款依据 |
|---|---|---|---|
| **G-enc** | 编码闸 | UTF-8 无 BOM + **无 mojibake 残码** | §4.2 |
| **G-imp** | 引用闸 | 原子真源只允许相对/包 import | **C2** |
| **G-dep** | 依赖闸 | `deps` == 真实 import | **C4** |
| **G-con** | 契约闸 | 元数据必填字段 + schema 完整 | **C3** |
| **G-asm** | 组装闸 | 真源 → 派生视图可完整重建 | §5 |

**条款：**

| # | 条款 |
|---|---|
| **G-1** | 每个项目 **MUST** 至少实现上表五项 |
| **G-2** | 门禁 **MUST** 可被一条命令跑完，**MUST** 返回非零退出码表示失败 |
| **G-3** | 门禁失败 **MUST** 阻断提交或合并 |
| **G-4** | 门禁 **MUST NOT** 依赖外部服务（离线可跑） |

### 4.2 为什么要专门做"编码闸"

**这是实测出来的教训，不是理论。**

参考实现过程中，同一份 UTF-8 文件在不同终端下：
- `read` 工具读取 → 正常
- PowerShell 5.1 的 `Get-Content`（默认按 ANSI/GBK）→ **整篇乱码**

**当时差点误判为"文件损坏"并去"修复"一份完好的文件。**

> **编码问题是静默的**：文件本身合法，只是**在某个工具链下被读错**。
> 它不会让构建失败，只会让**人和 Agent 读到错误的内容**。
>
> 因此 **G-enc MUST 显式检查 mojibake 残码**（如 `闈㈠悜` 这类
> "UTF-8 字节被按 GBK 解读"的特征串），而不只是检查 BOM。

## 5. 真源与派生视图

### 5.1 原则

> **真源唯一，派生视图可随时重建。**

```
atoms/<id>/…          ← 真源（入库）
      ↓ 组装
.build/…              ← 派生视图（gitignore，可重建）
```

### 5.2 为什么这条保证了原子化

若派生视图入库，就会出现"改真源还是改视图"的犹豫，
两份内容**必然漂移**，原子化随之瓦解。

| # | 条款 |
|---|---|
| **S-1** | 真源位置 **MUST** 唯一 |
| **S-2** | 派生视图 **MUST NOT** 入库 |
| **S-3** | 派生视图 **MUST** 可由真源完整重建（**G-asm** 强制） |
| **S-4** | 修改 **MUST** 只动真源 |
| **S-5** | 发布/打包的输入 **MUST** 是派生视图，**MUST NOT** 直接是真源 |
| **S-6** | 真源 **MUST** 显式声明身份；生成物 **MUST** 声明「由谁、从什么生成」（§5.3） |
| **S-7** | 「来源 → 生成物」**MUST** 构成 DAG；**存在环即违规**（§5.3） |
| **S-8** | 被引用为来源的文件 **MUST** 也有身份标记（§5.3） |
| **S-9** | 生成物的标记 **MUST 由生成器写入**，**MUST NOT** 手改产物（§5.3） |
| **S-10** | 每个派生面 **MUST** 有 parity 闸（逐字节比对重新生成的结果）（§5.3） |
| **S-11** | 文件的角色 **MUST** 有声明，**MUST NOT** 靠约定俗成（§5.3） |

**S-5 的理由**：打包需要一个"装配好"的形态；若直接从真源打包，
装配逻辑就会散进打包脚本，失去单一性。

### 5.3 一条链上可以有多个派生面，但**真源只能有一个**（`S-6`~`S-11`）

> **本节来自一次真实事故。** 某参考实现里有两个文件**互相声称对方是自己的来源**：
>
> ```
> impl/beadCatalog.ts          // GENERATED by gen-bindings.mjs from kb/ossie
> kb/ossie/data/bead_schema.sql -- GENERATED by export-ossie-seed.mjs from kb binding
> ```
>
> 后果不是"两份清单对不上"（那至少能判谁错），而是**根本没有真源**：
> 改 TS 下次 export 覆盖 SQL，改 SQL 下次 gen-bindings 覆盖 TS，**两边静默互相覆盖**。
> 而它跑起来完全正常——生成链是幂等的，所以这个环可以潜伏很久。

| # | 条款 |
|---|---|
| **S-6** | 真源 **MUST** 显式声明身份（如 `TRUTH SOURCE` 标记）；生成物 **MUST** 声明「由谁、从什么生成」 |
| **S-7** | 「来源 → 生成物」关系 **MUST** 构成 **DAG**；**存在环即违规** |
| **S-8** | 被引用为来源的文件 **MUST** 也有身份标记——否则读的人无法判断它该不该手改 |
| **S-9** | 生成物的标记 **MUST 由生成器写入**，**MUST NOT** 靠手改产物（下次生成即失效） |
| **S-10** | 每个派生面 **MUST** 有 parity 闸，比对"重新生成的结果"与"仓里的文件"逐字节一致 |
| **S-11** | 若某文件的角色只能靠"读代码猜"（没有声明），**MUST** 补声明，**MUST NOT** 靠约定俗成 |

**关于 S-7 为什么是 MUST 而不是 SHOULD**：
环不会自己暴露。它幂等、它测试全绿、它甚至能跑好几年——
直到某天有人"按注释的指示"去改了错误的那一端。

**关于 S-9（本节的第二个事故）**：第一次改造时把标记**手写进产物**，
跑一遍生成链，标记全被冲掉，于是环检测闸报「扫到了标记但没有 GENERATED」。
**标记是生成器输出的一部分，不是产物的元数据。**

**关于 S-10 与"一源两面"**：同一个真源服务**两类消费者**是常见需求
（机器要可执行、人要可读）。两面的**起点相同**解决不了"中途被改"——
所以每个面都要有闸把它钉回真源。
参考实现的做法：人读面由生成器产出，闸把生成器重跑一遍到临时文件、与入库文件逐字节比对。

> ⚠️ **门禁自身的假绿**：环检测闸第一版运行时，全仓**没有一个文件**采用标记协议，
> 于是它"通过"了——**因为什么都没看见**。
> 这类假绿比不跑闸更危险：它给出一个"已检查"的错觉。
> **闸 MUST 有"我扫到了东西"的自检**（零命中 = FAIL，不是 PASS）。

## 6. 判据：声明式与命令式之间的第三态

### 6.1 问题

框架 §7.1 把"约束"二分为：

| | 形式化本体 | 应用代码 |
|---|---|---|
| 表达 | OWL 公理 / SHACL | 命令式 if/else |
| 推理 | 通用推理机 | 无 |
| 代价 | 复杂度爆炸、不可控 | 不可查、不可分析 |

**但实践中存在第三态，框架没给它位置。**

### 6.2 判据（Criteria）

> **判据 = 带本体 IRI 的声明式规则数据 + 一个轻量的、确定性的求值器。**

**特征：**

| 特征 | 说明 |
|---|---|
| **规则是数据** | 可被列出、比较、版本化 |
| **规则引用本体** | 用 IRI 指向概念，不重复术语（**C1**） |
| **求值是代码，但很短** | 只做匹配与组合，不做领域推理 |
| **不引入推理机** | 保持 CPU、确定性、零网络 |
| **可解释** | 命中哪条判据是明确记录下来的 |

### 6.3 为什么这很重要

**它同时拿到了两边的长处：**

| 拿到 | 从哪来 |
|---|---|
| 规则可查、可版本化、可审计 | 声明式 |
| 确定性、可控、无复杂度爆炸 | 命令式 |
| 术语不重复（引用本体 IRI） | **C1** |

**且它天然满足框架 `I3-G2`（可追溯）** ——
判据命中即是天然的 `via`：结论能指出"我依据哪条判据"。

### 6.4 条款

| # | 条款 |
|---|---|
| **R-1** | 领域约束 **SHOULD** 表达为判据（规则数据 + 求值器），**MUST NOT** 硬编码进算法 |
| **R-2** | 判据 **MUST** 用本体 IRI 引用概念，**MUST NOT** 内联术语（**C1**） |
| **R-3** | 判据命中 **MUST** 可被记录并作为结论的溯源（对接 `I3-G2`） |
| **R-4** | 求值器 **MUST** 是确定性的、可离线、无 LLM |

> **R-4 是硬边界：** 判据求值 **MUST NOT** 调 LLM。
> 这对应框架的分工：**"算账"交给确定性工具，"聊天"交给模型。**

## 7. 语言与命名约定

| # | 条款 |
|---|---|
| **L-1** | 面向人的正文 **MUST** 声明语言（如 `zh-CN`） |
| **L-2** | 标识符、枚举、字段名 **MUST** 用英文 |
| **L-3** | 检索用的 `tags` **SHOULD** 用英文（跨语言召回） |
| **L-4** | 同一概念在不同语言下 **MUST** 指向同一标识符 |

## 8. 规范性条款汇总

| 组 | 条款 |
|---|---|
| **原子** | A-1 自包含 · A-2 一句话意图 · A-3 唯一标识 · A-4 不内嵌他原子实现 |
| **C1** | 零内嵌：术语只在 本体 |
| **C2** | 只引用：跨原子用 import |
| **C3** | I/O 契约：schema 必须与实现一致 |
| **C4** | 依赖透明：deps == import，**机器强制** |
| **披露** | P-1 列表层字段 · P-3 检索只用列表层 · P-4 详情层自足 |
| **门禁** | G-1 五项最小集 · G-2 一条命令 · G-3 阻断合并 · G-4 离线 |
| **真源** | S-1 真源唯一 · S-2 视图不入库 · S-3 可重建 · S-5 打包用视图 |
| **判据** | R-1 领域约束用判据 · R-2 引用本体 IRI · R-3 命中可溯源 · **R-4 求值器不调 LLM** |
| **语言** | L-1 声明语言 · L-2 标识符英文 |

## 9. 一致性验收

| # | 验收项 | 方法 |
|---|---|---|
| 1 | 每个原子自包含 | 检查 `atoms/*/` 下同时存在 文档 + impl + tests |
| 2 | 零内嵌 | 搜索术语字面量，应只在本体/生成绑定中出现 |
| 3 | 依赖透明 | 跑 `G-dep`，全绿 |
| 4 | 引用纪律 | 跑 `G-imp`，全绿 |
| 5 | 编码 | 跑 `G-enc`，全绿（含 mojibake 检查） |
| 6 | 派生视图可重建 | 删掉派生视图，跑 `G-asm`，应完整重建且内容一致 |
| 7 | 渐进披露 | 检索只用列表层字段即可返回候选 |
| 8 | 判据可溯源 | 结论能指出命中哪条判据 |
