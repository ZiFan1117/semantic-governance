## 0. 范围

### 0.1 本规范解决什么

框架 §5.4 的五个要素回答了"语义**由什么构成**"（对象 · 关系 · 规则 · 策略 · 动作），
但**没有回答"一类东西能被怎么对待"** —— 这个问题的答案不是内容分类，而是**类型的多态抽象**。

本规范定义**接口**这一构造：它的定义形态、实现规则、链接约束，以及它的变更纪律。

### 0.2 在范围内

| # | 内容 |
|---|---|
| 1 | **接口的组成**（仅共享属性 + 接口链接类型 + 元数据） |
| 2 | **接口的三条硬边界**（无数据源 · 无主键 · 不可实例化） |
| 3 | **接口的扩展**（接口扩展接口） |
| 4 | **接口的实现**（对象类型如何满足接口） |
| 5 | **接口链接类型约束**及其四个参数 |
| 6 | **接口变更的纪律**（破坏性变更的处理） |
| 7 | **接口的发现**（移交 I6） |

### 0.3 明确不在范围内

| 不在范围 | 为什么 |
|---|---|
| **权限模型的实现** | 接口权限经**角色**体系（框架 §2、§14），本规范只要求"接口 MUST 可被授权" |
| **接口的动作约束的完整语义** | 官方该能力仍在演进（见 §8），本规范只定义**边界**（§6.3） |
| **多态在查询/动作上的完整语义** | 属 I3 / I4 的扩展，不在本规范 |
| **接口的实例** | **不存在**——接口不可实例化（`IF-3`） |

## 1. 术语

| 术语 | 定义 |
|---|---|
| **接口**（Interface） | 描述**对象类型的形状及其功能**的类型。**提供对象类型的多态性** |
| **共享属性**（Shared Property） | 可在多个对象类型上使用的属性。**接口的架构只能由共享属性构成** |
| **接口链接类型**（Interface Link Type） | 定义**实现接口的所有对象类型之间**的对象到对象关系 |
| **链接类型约束**（Link Type Constraint） | 接口链接类型的参数声明：目标类型 · 目标 · 基数 · 是否必需 |
| **实现**（Implementation） | 对象类型声明"我符合某个接口"，并提供属性与链接的映射 |
| **功能接口**（Capability Interface） | 官方称谓：代表**一种独特的功能**，"促进该功能在所有实现对象类型上的重用"，通常只有**一小组**属性/链接 |
| **抽象对象接口**（Abstract Object Interface） | 官方称谓：两个或多个共享共同属性和链接的对象类型的**超类型** |

> **⚠️ 关于最后两个术语**：官方明说 **"在 Ontology 中，这两者都不是显式的子类型，但它们是讨论和理解接口如何被频繁使用的有用术语"**。
> **因此本规范不为它们设字段** —— 它们是**描述性**称谓，不是可声明的类型。

## 2. 接口的定义

### 2.1 接口由三样东西组成

| # | 组成 | 说明 |
|---|---|---|
| 1 | **共享属性** | **唯一**的架构来源 |
| 2 | **接口链接类型**（含约束） | 非必填 |
| 3 | **元数据** | 见 §2.3 |

### 2.2 三条硬边界（`IF-1`~`IF-3`）★

官方原文：

> **"对象类型是具体的；它们具有由共享或本地属性定义的架构，由包含属性值的数据集支持，并可以实例化为对象。**
> **相比之下，接口是抽象的；它们仅具有由共享属性定义的架构，不由数据集支持，且无法实例化。"**

| # | 条款 |
|---|---|
| **IF-1** | 接口的架构 **MUST** 只由**共享属性**构成；**MUST NOT** 声明本地属性 |
| **IF-2** | 接口 **MUST NOT** 声明数据源；接口 **MUST NOT** 由数据集支持 |
| **IF-3** | 接口 **MUST NOT** 声明主键；接口 **MUST NOT** 可实例化 |

> **为什么这三条是定义性的而非建议性的**：接口若可实例化，它就成了对象类型；
> 若可绑数据源，它就有了自己的事实侧。**任一被破坏，多态都不再成立** ——
> 因为"实现者"与"接口"将同时拥有事实，无法判定谁是真源。

### 2.3 接口的元数据（官方原表）

| 字段 | 官方说明 |
|---|---|
| **RID** | "每个资源自动生成的唯一标识符。接口的 RID 将在平台上的出错信息中被引用" |
| **图标** | "接口的图标周围有**虚线**，以在视觉上将其与对象类型图标区分开" |
| **显示名称** | |
| **描述** | |
| **API 名称** | "在代码中以编程方式引用接口时使用的名称" |
| **状态** | 取值为 `active` / `experimental` / `deprecated` |
| **可搜索** | 布尔值。"可搜索接口允许用户一次加载或搜索该接口的所有对象" |

| # | 条款 |
|---|---|
| **IF-4** | 接口 **MUST** 有 API 名称；**MUST NOT** 在未声明 API 名称的情况下被实现 |
| **IF-5** | 接口 **MUST** 有状态，取值 **MUST** 限于 `active` / `experimental` / `deprecated` |

> **IF-4 的理由（官方）**：**"由于接口暴露 API 名称，对接口定义的任何更改都有可能破坏下游应用"** ——
> API 名称是契约面，不是给人看的标签。

**官方给的上限（实现约束，非规范要求，供参考）**：

| 可搜索 | 最多可被多少对象类型实现 |
|---|---|
| 是 | **75** |
| 否 | **1,000** |

### 2.4 接口的扩展（`IF-6`~`IF-8`）

官方原文：

> **"扩展接口使您可以将多个接口组合在一起，创建一个新的、更具体的接口。这对于构建实现多个功能接口的抽象 Object 接口特别有用。一个接口会继承其扩展接口的共享属性和链接。一个接口可以扩展任意数量的其他接口。"**

| # | 条款 |
|---|---|
| **IF-6** | 接口 **MAY** 扩展任意数量的其他接口 |
| **IF-7** | 扩展 **MUST** 继承被扩展接口的**共享属性**与**链接类型约束**（继承是强制的，不可选择性忽略） |
| **IF-8** | 移除扩展时，实现 **MUST** 同时移除所有继承来的共享属性与链接类型约束，并解除关联；**MUST NOT** 留下孤儿声明 |

### 2.5 定义格式

> **键名为本文所选；字段全部来自官网。** 官方未公开机器可读 schema。

```yaml
interfaces:
  - rid: <RID>                          # 官方：RID
    display_name: <显示名称>            # 官方：显示名称
    api_name: <API 名称>                # 官方：API 名称
    description: <描述>                 # 官方：描述
    icon: <图标>                        # 官方：图标（虚线显示）
    status: active | experimental | deprecated   # 官方：状态
    searchable: <bool>                  # 官方：可搜索

    # ⚠️ IF-1：只能引用共享属性
    shared_properties: [<共享属性 api_name>, ...]

    extends: [<接口 api_name>, ...]      # 官方：扩展接口

    link_type_constraints:               # 官方：接口链接类型（非必填）
      - name: <约束名>
        api_name: <API 名称>
        description: <说明>
        target_kind: interface | object_type    # 官方：链接目标类型
        target: <接口或对象类型 api_name>         # 官方：目标
        cardinality: ONE | MANY                 # 官方：基数
        required: <bool>                        # 官方：是否必需

    # IF-2 / IF-3：无数据源字段，无主键字段
```

## 3. 接口的实现

### 3.1 官方要求

> **"一旦定义，符合接口定义的任何对象类型都可以实现接口。这意味着对象类型必须包含接口的共享属性（或映射并满足接口共享属性的本地属性），并且拥有满足接口上定义的所有所需链接类型约束的链接。"**

**官方给的实现步骤**：

```
① 选择接口与对象类型
② 映射本地属性 —— 两边都有的共享属性「自动映射」，缺的「手动映射」
③ 映射链接类型约束 —— 每个「必需」约束都要挑一个链接类型来满足
④ 保存
```

### 3.2 条款（`II-1`~`II-5`）★

| # | 条款 |
|---|---|
| **II-1** | 对象类型 **MAY** 实现任意数量的接口 |
| **II-2** | 实现时，对象类型 **MUST** 满足接口的**全部**共享属性 —— 或自身包含该共享属性，**或**声明本地属性→共享属性的**映射** |
| **II-3** | 接口上**必需**的链接类型约束，实现方 **MUST** 提供一个满足其参数的链接类型；**非必需**约束 **MAY** 不满足 |
| **II-4** | 实现关系的建立与撤销 **MUST** 是显式声明，**MUST NOT** 由"名字相同"推断 |
| **II-5** | 移除实现时，**MUST** 一并移除该实现引入的属性映射与链接映射；**MUST NOT** 留下孤儿映射 |

> **II-2 的关键**：接口约束的是**"能提供这个语义"**，不是"必须用这个共享属性"。
> 官方原文的"或映射并满足接口共享属性的本地属性"就是这个意思。**这给了实现方自由，同时不放弃约束力。**

### 3.3 实现带来的两项能力（官方原文）

> **"① 针对接口的对象集服务搜索将返回实现对象类型的匹配对象。**
> **② 实现对象类型的对象可以通过其本地 API 名称（当类型为具体对象类型时）和接口 API 名称（当类型为接口类型时）与属性和链接进行交互。"**

| # | 条款 |
|---|---|
| **II-6** | 按接口发起的查询 **MUST** 返回**所有**实现该接口的对象类型的匹配实例 |
| **II-7** | 实现方对象 **MUST** 可同时经其**本地 API 名称**与所实现接口的 **API 名称**访问 |

### 3.4 官方给出的收益（可引用，作为采用理由）

> **"实现接口允许应用程序消费者通过接口定义与任何和所有实现对象进行交互。这使得应用程序代码可以使用接口作为 API 层，而不需要应用程序单独支持每个实现对象类型。此外，通过使用接口作为应用程序 API 层，可以通过让新对象类型实现应用程序接口来将其添加到应用程序中，而不需要更改代码以显式支持新对象类型。"**

**最后一句是本契约的核心价值**：

> **新增实现方不需修改消费方代码** —— 这是"前向兼容"的准确表述。

### 3.5 实现格式

```yaml
# 在对象类型侧
implements:
  - interface: <接口 api_name>
    property_mappings:                    # 官方：映射本地属性
      - interface_property: <接口共享属性 api_name>
        local_property: <本类型属性 api_name>
    link_mappings:                        # 官方：映射链接类型约束
      - constraint: <约束名>
        link_type: <本类型链接类型 api_name>
```

## 4. 接口链接类型（`IL-1`~`IL-6`）★

### 4.1 官方定义

> **"接口链接类型定义了实现接口的所有对象类型之间的对象到对象的关系。**
> **当一个对象实现带有接口链接类型的接口时，接口上的所有接口链接类型都由对象类型上的具体链接类型支持。任何本体论修改都将验证具体链接类型是否符合关联链接类型约束所指定的参数。"**

### 4.2 约束的四个参数（官方原表）

| 参数 | 取值 |
|---|---|
| **链接目标类型** | 接口 或 对象类型 |
| **目标** | 一个具体的接口或对象类型 |
| **基数** | `ONE` / `MANY` |
| **是否必需** | 是 / 否 |

### 4.3 两种链接目标的判据（官方原文，可直接引用）★

| 目标类型 | 什么时候用 |
|---|---|
| **接口链接目标** | **"当你想要建模两个抽象对象类型之间的关系时"** |
| **对象类型链接目标** | **"当接口和目标之间的关系是具体的，并且应由链接类型约束来强制执行其特异性时"** |

**官方给的两个例子**：

| 例子 | 说明 |
|---|---|
| `Facility` 接口 → **`Alert` 接口** | "因为**有好几种设施和几种警报**，如果你只能为链接的每一端使用单一对象类型，那么就不可能建模两者之间的连接" |
| `Facility` 接口 → **`Airlines` 对象类型** | "这个接口链接将建模**无论设施类型是什么**，你都期望它有一个链接到其服务的具体航空公司" |

### 4.4 基数（官方原文）

> **"`ONE` 基数表示一个具体对象（一个对象类型的行）应该链接到正好一个其他具体对象。`MANY` 基数表示一个具体对象可以有一个或多个链接到其他具体对象。"**
>
> **"接口链接类型是关系的左侧。"**

### 4.5 条款

| # | 条款 |
|---|---|
| **IL-1** | 链接类型约束 **MUST** 声明四个参数：链接目标类型 · 目标 · 基数 · 是否必需 |
| **IL-2** | 约束的 `target_kind` 为 `interface` 时，`target` **MUST** 是接口；为 `object_type` 时 **MUST** 是对象类型 |
| **IL-3** | 实现方提供的具体链接类型 **MUST** 满足被映射约束的**全部四个参数**；不满足 **MUST** 被拒绝 |
| **IL-4** | 校验 **MUST** 发生在**本体修改时**（写入路径），**MUST NOT** 只在读取时校验 |
| **IL-5** | 一端或两端可能多样时，**SHOULD** 使用接口链接目标；一端确定时，**SHOULD** 使用对象类型链接目标 |
| **IL-6** | 约束 **MUST** 可标记为必需或非必需；**必需**的约束未被满足时，实现 **MUST NOT** 被接受 |

> **IL-3 与 IL-4 是配套的**：官方原文说"**任何本体论修改都将验证**"——
> 验证点在**定义变更**上，不在查询上。

## 5. 接口的变更纪律（`IF-9`~`IF-11`）★★

### 5.1 官方警示（逐字）

> **"由于接口暴露 API 名称，对接口定义的任何更改都有可能破坏下游应用，并且必然会破坏现有的 Object 实现。当向接口添加新的共享属性或链接类型约束时，所有使用该接口的 Object 类型的实现必须在同一次更新中完成到您的 Ontology。我们还建议同时更新您的接口定义和消费者。"**

**官方给的缓解办法**：

> **"如果您的下游应用程序不能与接口更改同时更新，您可以选择创建一个新版本的接口（作为扩展或独立接口），并尽快迁移到新的接口定义。"**

### 5.2 条款

| # | 条款 |
|---|---|
| **IF-9** | 对接口定义的变更（新增共享属性 / 新增链接类型约束）**MUST** 被视为**破坏性变更** |
| **IF-10** | 破坏性变更时，**MUST** 二选一：① 在同一次更新中完成全部实现的迁移；② **新建接口版本**（作为扩展或独立接口）并给出迁移期 |
| **IF-11** | 接口定义 **MUST NOT** 被就地修改而不处理既有实现；**MUST NOT** 用"暂时不一致"过渡 |

> **IF-11 与框架 §1.4（版本与兼容性）、§1.5（分叉与退出）一致**：
> **接口是契约，契约的变更要么同步迁移，要么开新版本** —— 迁移期就是退出权的落地形式。

### 5.3 与既有条款的关系

| 与谁 | 关系 |
|---|---|
| 框架 §1.2（变更流程） | 接口变更 **MUST** 走提案流程 |
| 框架 §1.4（版本与兼容性） | 接口版本与框架的版本纪律一致 |
| 框架 §1.5（分叉与退出） | 迁移期是退出权的落地形式 |
| **I1 语义契约** | 接口与其共享属性 **MUST** 在 I1 可见；接口 **MUST NOT** 引用未声明的共享属性 |

## 6. 接口与其它构件的关系

### 6.1 关系表（全部有官方依据）

| 关系 | 方向 | 官方依据 |
|---|---|---|
| 对象类型 **实现** 接口 | 对象类型 → 接口 | `implement-interface` |
| 接口 **扩展** 接口 | 接口 → 接口 | `extend-interface` |
| 接口 **声明**链接类型约束 → 对象类型 **提供**具体链接满足 | 接口 → 对象类型 | `interface-link-types-overview` |
| 接口 **由**共享属性**构成** | 接口 → 共享属性 | `create-interface` |
| 接口 **经**角色**授权** | 角色 → 接口 | `interface-overview` |
| 接口 **可被**动作**作用于** | 动作 → 接口 | 见 §6.3 |

### 6.2 接口与对象类型的分工（一表说清）

| | 对象类型 | 接口 |
|---|---|---|
| 具体 / 抽象 | **具体** | **抽象** |
| 架构来源 | 共享属性 **或**本地属性 | **仅共享属性**（`IF-1`） |
| 数据源 | **有** | **无**（`IF-2`） |
| 可实例化 | **可以** | **不可以**（`IF-3`） |
| 回答的问题 | 世界**是**什么 | 世界**能**被怎么对待 |

### 6.3 接口的动作约束：**只定义边界**（`IL-7`~`IL-8`）

**官方英文版 `interfaces/interface-action-type-constraints` 的关键界线（逐字）**：

> **"Interface action type constraints do not define action execution logic, submission criteria, side effects, or form layout."**
> （接口的动作类型约束**不**定义执行逻辑、提交条件、副作用和表单布局 —— 那些配在具体的操作类型上。）

| # | 条款 |
|---|---|
| **IL-7** | 接口 **MAY** 声明"应当存在某个动作能力"，但该声明 **MUST NOT** 定义执行逻辑、提交条件、副作用或表单布局 |
| **IL-8** | 上述声明 **MUST** 由实现方映射到**该对象类型上的具体动作类型**；**MUST NOT** 被直接调用 |

> **⚠️ 采用注意**：该能力在官方**仍处于 beta**，且**中文版未收录该页**。
> 本规范只锁定边界（"不定义什么"），**不锁定具体字段** —— 因为官方尚未定稿。

## 7. 与 I6 发现的接口（移交）

**接口的枚举与查询属 I6 发现契约**，不在本规范。I6 **MUST** 提供：

| 操作 | 用途 |
|---|---|
| `ListInterfaces` | 枚举接口（`I6-G1` 可枚举） |
| `GetInterface` | 取单个接口的完整定义（含共享属性与链接约束） |
| `ListImplementers` | 取某接口的全部实现对象类型 |

**为什么必须在 I6**：**"这类东西能被怎么对待"是 Agent 与业务软件都要问的问题**；
没有这三个操作，接口就只是建模者脑中的概念，不可被发现。

## 9. 规范性条款汇总

| 组 | 条款 |
|---|---|
| **接口定义** | **IF-1 只由共享属性构成** · **IF-2 无数据源** · **IF-3 无主键、不可实例化** · IF-4 必须有 API 名称 · IF-5 状态取值受限 · IF-6 可扩展多个接口 · IF-7 扩展继承强制 · IF-8 移除扩展须清理 · **IF-9 变更为破坏性** · **IF-10 同步迁移或开新版本** · IF-11 禁止就地改而不处理实现 |
| **接口实现** | II-1 可实现多个 · **II-2 满足全部共享属性（含映射）** · **II-3 必需约束必须满足** · II-4 显式声明 · II-5 移除须清理 · II-6 按接口查询返回全部实现方 · II-7 双名称可访问 |
| **链接约束** | **IL-1 四参数齐备** · IL-2 目标类型与目标一致 · **IL-3 实现须满足全部参数** · **IL-4 校验在写入路径** · IL-5 两种目标的选用判据 · IL-6 必需/非必需 · IL-7 动作约束只定义边界 · IL-8 由实现方映射到具体动作 |
| **禁止** | 接口声明本地属性 **MUST NOT** · 接口绑数据源 **MUST NOT** · 接口可实例化 **MUST NOT** · 就地改接口而不处理实现 **MUST NOT** |

## 10. 一致性等级

| 等级 | 要求 |
|---|---|
| **I7-min/Core** | 全部 MUST：`IF-1`~`IF-3` · `IF-4` · `IF-6`~`IF-8` · `II-1`~`II-5` · `IL-1`~`IL-4` · `IL-6` |
| **I7-min/Plus** | Core + 状态与可搜索元数据（`IF-5`）+ 双名称访问（`II-7`）+ 两种目标的选用（`IL-5`） |
| **I7-min/Full** | Plus + 动作约束（`IL-7`~`IL-8`）+ I6 的三个发现操作（§7） |

**验收方法**：

```
① 试声明一个带本地属性的接口        → MUST 被拒绝            （IF-1）
② 试给接口绑数据源                  → MUST 被拒绝            （IF-2）
③ 试给接口声明主键 / 造一个接口实例  → MUST 被拒绝            （IF-3）
④ 实现方缺少一个共享属性且未声明映射 → MUST 被拒绝            （II-2）
⑤ 实现方未满足一个「必需」链接约束   → MUST 被拒绝            （II-3 / IL-6）
⑥ 实现方提供的链接基数与约束不符     → MUST 在写入时被拒       （IL-3 / IL-4）
⑦ 给接口加一个共享属性而不动实现方   → MUST 被拦（要求同步或开新版本）（IF-9/IF-10）
⑧ 按接口查询                          → MUST 返回全部实现方的实例（II-6）
⑨ 按接口 API 名称访问实现方属性       → MUST 可行              （II-7）
```

> **第 ⑦ 条是本规范最难验收也最重要的一条** —— 它把"接口是契约"从口号变成可检查的行为。
