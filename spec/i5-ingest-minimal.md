# I5 接入契约 · 最小规范
<!-- clauses: CT IG QT -->

| 字段 | 值 |
|---|---|
| **版本** | v0.1（草案） |
| **规范等级** | **Normative**（含 MUST / MUST NOT / SHOULD） |
| **上级文档** | [`../docs/framework.md`](../docs/framework.md) §19 |
| **五要素落位** | **不新增要素**——接入侧把**外部表示**翻译成合法事实（对象与关系），并把**数据来源→对象**的对应关系声明为**映射**（`ontology_mappings`）。映射**不是要素**，归本契约 |
| **本规范自有条款前缀** | `CT-`（契约声明与校验）· `IG-`（摄取）· `QT-`（拒收与隔离） |
| **前置** | 框架 §11.1 `LD-1`：接入侧是**条件性能力**——只在存在外部数据源时出现。**不接外部数据源的实现不必实现本规范** |

---

## 0. 范围

### 0.1 本规范解决什么

框架 §19 给出了 I5 的四条保证（`I5-G1`~`I5-G4`），但没有给出**可实现的接口与验收**：
契约声明成什么形状、摄取时按什么顺序校验、不合规的数据去哪、"身份先于属性"怎么落地。
本规范把这些定到可测试的程度。

### 0.2 在范围内

| # | 内容 |
|---|---|
| 1 | **契约声明**：一个数据源接入前必须声明什么 |
| 2 | **契约校验**：上游是否满足契约，怎么判 |
| 3 | **摄取**：增量 / 全量，以及**校验发生在哪一步** |
| 4 | **拒收与隔离**：不合规的数据去哪，怎么被修复后重新进入 |
| 5 | **身份解析的顺序要求**："先定身份，再谈属性"为何是硬要求 |

### 0.3 明确不在范围内

| 不在范围 | 为什么 |
|---|---|
| **连接器实现**（CDC、API 拉取、文件解析） | 有现成产品（Debezium / Airbyte 等），本规范只管**契约与验收** |
| **自动清洗** | ❌ **明确禁止**（`I5-G2`）：清洗是错误放大器 |
| **身份解析的算法** | 规则匹配 / 概率匹配 / 人工复核都是实现选择；本规范只要求**顺序与可解释** |
| **物理存储选型** | 属实现自由 |

## 1. 术语

| 术语 | 定义 |
|---|---|
| **数据源** | 提供外部数据的系统（数据库 / API / 消息流 / 文件） |
| **契约**（Contract） | 对某个数据源的**声明式约定**：它必须提供哪些字段、各自什么类型与约束、身份怎么定。**用 ODCS 表达** |
| **接入侧缺失** | 本实现没有任何外部数据源。此时本规范整体不适用（`LD-1`），但实现 **MUST** 显式声明这一点（`LD-3`） |
| **拒收区**（Quarantine） | 存放**不合规记录**的地方。记录带着**为什么被拒**一起进区，等人来修 |
| **归一** | 把某个数据源自己的表示，翻译成契约声明的形状 |
| **身份**（Identity） | 一个实例**唯一**的引用方式（`identify_by` 声明的那些关系） |

---

## 2. 契约

| 操作 | 说明 |
|---|---|
| `DeclareContract(source, contract)` | 为数据源声明契约（ODCS 文档） |
| `ValidateContract(source)` | 校验上游**是否满足**契约 |
| `Ingest(source, mode)` | 摄取（`mode`: `incremental` / `full`） |
| `Quarantine(records)` | 把不合规记录移入拒收区（带原因） |

### 2.1 契约必须先于数据（`I5-G1`）

```
声明契约 → 校验契约 → 摄取
   ↑ 少了任何一步，摄取 MUST 被拒绝
```

**没有契约的数据源不得接入**——因为"没有契约"意味着**没有任何东西能判定它合不合规**，
于是数据会直接污染事实侧。

### 2.2 契约声明什么（最小集）

| 字段 | 必填 | 说明 |
|---|---|---|
| `source` | ✅ | 数据源标识 |
| `fields[]` | ✅ | 每个字段的：名字 · 类型 · 是否可空 · 约束 |
| `mapping` | ✅ | **字段 → 对象属性 / 关系**的映射（`ontology_mappings`） |
| `identity` | ✅ | 本源的实例身份怎么定（引用哪个 `identify_by` 关系） |
| `freshness` | ⚠️ | 更新频率 / 延迟预期（影响 L4 的 SLA 验收） |
| `owner` | ⚠️ | 谁负责修不合规数据（拒收区需要知道找谁） |

## 3. 保证

| # | 保证 | 说明 |
|---|---|---|
| **I5-G1** | **契约先于数据** | 没有契约的数据源不得接入（§2.1） |
| **I5-G2** | **不合规即拒收** ⭐ | **绝不自动清洗**——隔离等人来修 |
| **I5-G3** | **拒收可解释** | 说清违反了契约的哪一条 |
| **I5-G4** | **身份先于属性** | 实例身份必须能稳定解析 |

### 3.1 为什么"绝不自动清洗"（`I5-G2` 的理由）

> **自动清洗是错误放大器。** 它把业务问题藏起来，而且越藏越深：
> 一条金额为负的订单，被自动取绝对值之后，**看起来一切正常**——
> 而"为什么会为负"这个问题，从此再没有人问。

**允许的两种处理**：**拒收**（进隔离区）或 **按契约拒绝整个批次**。
**不允许的**：静默修正、丢弃字段、填默认值。

### 3.2 拒收区的记录形状（`I5-G3` 的可验收要求）

```
{
  "source": "erp.orders",
  "record_ref": "<原记录的可定位引用>",
  "received_at": "<时刻>",
  "violations": [
    { "field": "amount", "value": -100,
      "rule": "erp.orders.amount >= 0",     ← 依据：违反契约的哪一条
      "message": "金额不得为负" }
  ],
  "owner": "谁负责修"
}
```

**三条要求**：

| # | 条款 |
|---|---|
| **QT-1** | 拒收记录 **MUST** 含 `violations[].rule`（回引契约里的具体条款），**MUST NOT** 只给一句自然语言 |
| **QT-2** | 拒收记录 **MUST** 保留**原值**（`value`），**MUST NOT** 存清洗后的值——否则无从判断问题 |
| **QT-3** | 拒收 **MUST NOT** 阻塞**其它合规记录**的摄取（除非显式选择"整批拒绝"模式） |

### 3.3 身份先于属性（`I5-G4`）

**摄取 MUST 按这个顺序**：

```
① 解析身份（identify_by 指定的关系）
② 身份解析失败 → 拒收（不进入下一步）
③ 身份确定后，才装载属性与其它关系
```

| # | 条款 |
|---|---|
| **IG-1** | 摄取 **MUST** 先解析身份再装载属性；**MUST NOT** 先写属性、后补身份 |
| **IG-2** | 身份解析失败 **MUST** 拒收，**MUST NOT** 新建一个"临时身份"顶替 |
| **IG-3** | 摄取 **MUST** 在**写入路径上**过规则校验（框架 `I2-G1`），**MUST NOT** 只在读取时校验 |

> **⚠️ 为什么顺序是硬要求**：如果先写属性、后补身份，就会出现**同一实体被建成两条实例**——
> 而属性已经挂上去了，事后合并要处理冲突。**这是事实侧脏数据的头号来源。**

### 3.4 幂等

| # | 条款 |
|---|---|
| **IG-4** | 同一批数据重复摄取 **MUST** 是幂等的（结果不变），**MUST NOT** 产生重复实例或重复事实 |
| **IG-5** | 实现 **MUST** 能回答"这批数据是什么时候、按哪版契约摄取的" |

## 4. 与其它契约的关系

| 与谁 | 关系 |
|---|---|
| **I1 语义契约** | 契约里引用的对象/关系名 **MUST** 在 I1 里已声明；**MUST NOT** 内联未声明的名字 |
| **I2 事实契约** | 摄取**经 I2 写入**（框架 §16 `I2-G3` 的**接入路径**），与动作路径并列；**两条路径都必须过规则** |
| **I4 动作契约** | 两者是事实的**两个入口**，互不替代：I5 是外部的到来触发，I4 是使用者发起（`LD-2`） |

> **⚠️ 常见误解**：以为"接进来的数据可以不经过动作层，所以不用过规则"。
> **恰恰相反**——`I2-G1` 对所有写入生效，**不分路径**。

## 5. 规范性条款汇总

| 组 | 条款 |
|---|---|
| **契约** | CT-1 契约先于数据（无契约不得摄取）· CT-2 契约 MUST 含 mapping 与 identity · CT-3 引用的名字 MUST 在 I1 已声明 |
| **摄取** | **IG-1 先身份后属性** · IG-2 身份失败即拒收 · **IG-3 写入路径上过规则** · IG-4 摄取幂等 · IG-5 可回答"哪版契约、何时" |
| **拒收** | **QT-1 必须回引契约条款** · QT-2 保留原值 · QT-3 不阻塞合规记录 |
| **禁止** | 自动清洗 **MUST NOT**（`I5-G2`）· 临时身份顶替 **MUST NOT** |

### 5.1 各条款的详细定义

| # | 条款 |
|---|---|
| **CT-1** | 无契约的数据源 **MUST NOT** 被摄取 |
| **CT-2** | 契约 **MUST** 声明 `mapping`（字段→对象/关系）与 `identity`（身份怎么定） |
| **CT-3** | 契约引用的对象/关系名 **MUST** 在 I1 语义契约里已声明 |
| **IG-1** | 摄取 **MUST** 先解析身份、后装载属性 |
| **IG-2** | 身份解析失败 **MUST** 拒收；**MUST NOT** 以临时身份顶替 |
| **IG-3** | 摄取 **MUST** 在写入路径上过规则校验（框架 `I2-G1`） |
| **IG-4** | 同一批数据重复摄取 **MUST** 幂等 |
| **IG-5** | 实现 **MUST** 记录每批数据的摄取时刻与所用契约版本 |
| **QT-1** | 拒收记录 **MUST** 回引被违反的契约条款 |
| **QT-2** | 拒收记录 **MUST** 保留原值 |
| **QT-3** | 单条拒收 **MUST NOT** 阻塞同批其它合规记录（除非显式选择整批拒绝） |

## 6. 一致性等级

| 等级 | 要求 |
|---|---|
| **I5-min/Core** | 全部 MUST 条款（`CT-1`~`CT-3`、`IG-1`~`IG-5`、`QT-1`~`QT-3`） |
| **I5-min/Plus** | Core + `freshness`/`owner` 元数据 + 拒收区的修复工作流 |

**验收方法**：

```
① 无契约摄取 → MUST 被拒绝                       （CT-1）
② 造一条违反契约的记录 → 进拒收区，且带条款回引   （I5-G2 / QT-1）
③ 检查拒收记录里的值是原值，不是清洗后的值         （QT-2）
④ 造一条身份解析失败的数据 → 拒收，且没新建临时身份（IG-2）
⑤ 同一批数据摄取两次 → 事实数不变                 （IG-4）
⑥ 喂一批"本该被拒"的样本集，全部被拒且原因正确     （框架 §24.1 的方法）
```

> **第 ⑥ 条是框架推荐的通用验收法**（§24.1「建一个该被拒绝的样本集」），
> 对 I5 尤其适用——**接入侧是脏数据的入口，它拒得对不对，直接决定事实侧干不干净**。
