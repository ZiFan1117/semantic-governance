# 语义治理框架（Semantic Governance Framework）

> **让组织里的每一个系统、每一个人、每一个智能体，都在同一套语义背景上说话。**

**状态**：草案 v0.2 · 征求意见中（RFC）
**许可**：Apache-2.0

---

## 这是什么

一套**开放、通用**的框架，规定：

- 业务语义如何被**声明**（概念、关系、约束、派生、动作、映射）
- 语义如何被**治理**（谁有权定义、怎么改、有分歧怎么办、怎么退出）
- 系统之间靠**什么接口**对话（六个接口，各自的契约与保证）
- 一套实现**做到哪一步算合规**（五级阶梯）

它要解决的问题很具体：

> 同一个"客户"在四个系统里四个定义，
> 同一个"营收"在四个看板里四个数字，
> AI 拿到互相冲突的业务逻辑只能胡说，
> 想改一个规则要改几十个地方，还改不全。

**Palantir 的 Ontology 解决了这个问题，但它是专有的。**
**本框架给出一个通用、公开、可开源的等价物。**

---

## 核心理念：语义治理，不是语义建模

| 词 | 隐含的重心 | 问题 |
|---|---|---|
| 本体论 | 建模 | 听起来像学术活动，做完就完了 |
| 知识图谱 | 数据 | 听起来像存储选型 |
| **语义治理** | **权责 + 契约 + 技术** | ✅ 点出了"这是一件持续治理的事" |

**"治理"三个字要求框架必须回答：谁有权定义、怎么改、有分歧怎么办、怎么退出。**

一个不回答这些问题的"语义"框架，只是又一份 schema 规范。

---

## 核心命题

> **把业务语义从应用代码里抽出来，做成一份可声明、可校验、可执行、可交换的权威契约；
> 规定六个接口，让所有读写都必须经过它；
> 并用一套治理机制保证这份契约能持续演进而不失控。**

---

## 形态：中央式权威，以及它的代价

本框架采用**中央式**——一套权威语义，所有系统向它对齐。

**它给你什么**：强一致、无歧义、可治理、可推理。

**它要你放弃什么**（这一条必须说清）：

- ❌ "任何人都能改核心" —— 不可能
- ❌ 域之间的完全自治 —— 各域必须向核心对齐
- ⚠️ 中央成为瓶颈、成为风险点

**所以本框架的"开放"具体指什么：**

| ✅ 开放的 | ❌ 不开放的 |
|---|---|
| 规范本身（任何人可自由实现） | **核心定义的直接修改权** |
| **提案权**（任何人可提变更提案） | |
| 扩展命名空间（域内自定义，无需批准） | |
| **分叉权**（可 fork 核心，另立门户） | |
| **退出权**（可导出全部定义与事实并离开） | |

> **开放的是「加入、提案、分叉、退出」，不是「就地修改」。**
>
> 这不是妥协——IETF、W3C、Kubernetes 都是这个形态：
> **提案开放，权威集中**。这是唯一被验证过能同时做到"开放"和"稳定"的形态。

## 六个接口（框架的核心）

标准化不是靠分层，是靠**接口契约**。

| # | 接口 | 契约核心 | 现有标准 |
|---|---|---|---|
| **I1** | **语义接口** | 读定义，定义不可变 | ✅ **Apache Ossie** |
| **I2** | **事实接口** | **写入必须过约束** | ⚠️ GQL（需补一条） |
| **I3** | **查询接口** | **结果必须可追溯** | ⚠️ MCP（需补一条） |
| **I4** | **动作接口** | 受控修改的完整契约 | ❌ **需原创** |
| **I5** | **接入接口** | 契约先于数据 | ✅ **ODCS** |
| **I6** | **发现能力** | 不知道有什么时能列出来 | ❌ **需原创** |

> **要发明的只有两个（I4、I6），要补的只有两条约束（I2-G1、I3-G2），
> 其余全部是选型与组合。**
>
> 这不是缺点。标准之所以能成，往往不是因为它发明了什么，
> 而是因为它**把已有的东西拼成了一个可用的整体**。（schema.org 就是这么成的。）

## 与现有标准的关系：不重复造轮子

| 已有标准 | 覆盖什么 | 本框架 |
|---|---|---|
| **Apache Ossie** | 语义定义的格式 | ✅ 直接采用 |
| **ODCS** | 数据契约 | ✅ 直接采用 |
| **GQL**（ISO/IEC 39075:2024） | 图查询语言 | ✅ 直接采用 |
| **MCP** | Agent 接入 | ✅ 直接采用 |
| **OpenFGA / Zanzibar** | 授权模型 | ✅ 直接采用 |
| **OpenLineage** | 数据血缘 | ✅ 直接采用 |
| **CloudEvents** | 事件格式 | ✅ 直接采用 |
| **W3C PROV-O** | 溯源 | ✅ 参考 |
| **OWL / SHACL** | 形式化本体与校验 | ⚠️ 按需补充，不作主格式 |
| **Palantir Ontology** | 全套（专有） | ⚠️ **抄概念，不抄实现** |

## 三种剖面（Profile）

不同用途的需求差别极大，所以框架定义三种剖面，而不是一套统一要求：

| | **A · 轻量** | **B · 组织** | **C · 严格** |
|---|---|---|---|
| 适用 | Agent 记忆库 | 部门数据治理 | 跨系统权威语义 |
| 变更流程 | 无需提案 | 内部评审 | 正式提案 + 公示 + 弃用期 |
| 目标等级 | L0~L1 | L0~L3 | L0~L4 |

---

## 五级合规阶梯

```
Level 4  可运营   + 全部切面（合规删除、成本、SLA、治理流程）
   ↑
Level 3  可治理   + 授权 + 审计 + 版本
   ↑
Level 2  可写     + 动作接口              ← ⭐ 分水岭
   ↑
Level 1  可读     + 事实 + 查询 + 发现接口
   ↑
Level 0  可声明   + 语义接口                ← Ossie 已给
```

> **Level 1 → 2 是分水岭：以下只能"看"，以上才能"安全地改"。**
> **绝大多数开源方案停在 Level 1。**

## 已知的开放问题

框架**不是完整答案**。最重要的两条自我质疑（详见 framework.md §24）：

> **1. 治理真正难的是让人达成共识。**
> 一个高效的提案系统也救不了一群谈不拢的人。
>
> **2. 采用本框架 = 选择"强 TBox"路线。**
> 如果你的场景里语义稳定、消费者很少，那用一张表 + 一段代码就够了，**不要用这个框架**。

其余 7 条开放问题包括：派生不落库与前置条件的冲突、动作抽象模型无先例、身份解析的准确率上限、合规删除的完整性验证、定义变更的影响分析等。
