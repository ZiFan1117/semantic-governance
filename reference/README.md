# I4-min 参考实现

> 实现 [`../spec/i4-action-minimal.md`](../spec/i4-action-minimal.md) 的参考实现。
> 目标：验证规范**是否真的可实现、自洽**。

---

## 为什么要有它

框架把「至少一个实现达到 Level 2」列为 **v1.0 的发布条件**。
更重要的是：**规范写了 40 条 MUST，但一行代码都没验证过它们是否自洽。**

**这个参考实现的产出不是代码，是它暴露的规范缺口**（见文末）。

---

## 运行

**依赖**：Python ≥ 3.10 + `pyyaml`（唯一第三方依赖）

```bash
pip install pyyaml

# 端到端演示（覆盖 §8 全部 9 条验收样本）
python reference/demo.py

# 一致性测试套件（45 个测试）
python reference/tests/test_i4_min.py
```

## 分层对应

| 框架的层 | 本实现 | 用了什么标准/技术 |
|---|---|---|
| **L3 语义定义**（I1） | `ossie_model.py` + `ontology.ossie.yaml` | ✅ **Apache Ossie YAML** |
| **L2 事实**（I2） | `store.py`（SQLite） | 最小实现（框架 §23 建议 Postgres） |
| **L4 查询**（I3） | `query.py` | ⭐ **首次实现 Ossie 的 `derived_by`** |
| **L5 动作**（I4） | `engine.py` | ⭐ **本框架的原创部分** |
| **I6 发现** | `discovery.py` | ⭐ **本框架的原创部分** |
| 授权 | `SimpleAuthz`（Zanzibar 风格元组） | 生产应换 OpenFGA |
| 审计 | `store.audit` 表 | 字段按规范 §5 |
| 表达式 | `expr.py`（CEL 子集） | 规范 E-2 的最低能力 + `is null` |

**"符合的部分用 Ossie"** —— 概念、关系、值类型、约束（`requires`）、标识（`identify_by`）
全部走 Ossie 格式，且 `ActionLoader` 会校验动作定义对 Ossie 概念的引用（规范 `D-1`）。

**动作定义不在 Ossie 里** —— Ossie 不管动作，所以是独立的 YAML 文件，
通过 `target.concept` / `parameters[].type` **引用** Ossie 定义。

## ⚠️ 规范缺口发现

> **这才是本参考实现的主要产出。**
> 以下四条是**写代码时才暴露出来的**，纸面推演发现不了。

### 发现 1：`multiplicity` 的强制点必须前移到写入路径

| | |
|---|---|
| **类型** | 🔴 实现缺陷 + 规范强调不足 |
| **相关条款** | 框架 **I2-G1**『写入必须过约束』 |

**现象**：最初的实现把 `multiplicity`（Ossie 的 `ManyToOne` / `OneToOne`）
**只在读取时检查**。结果是：

```
写入两条 status  →  成功（脏数据进库）
读取 status      →  抛错「有 2 个值，但它被声明为单值」
```

**这正好违反了 I2-G1 的立意** —— 约束必须在**写入路径**上拦，而不是等读取时炸。

**已修**：`Store.set_fact(..., single_valued=...)` 在写入时按 Ossie 的 multiplicity
决定"替换"还是"追加"；`ActionEngine` 从本体读取该标志。

**教训**：**"声明了约束"和"约束生效"之间隔着一整条写入路径。**
框架把 I2-G1 写成一条 MUST 是对的，但**没有说清强制点在哪一层** —— 建议在规范里明确：
**强制点 MUST 在 I2 的写入操作内，MUST NOT 只在读取时校验。**

---

### 发现 2：`R-5` 对「未发生读取的早期拒绝」要求过严

| | |
|---|---|
| **类型** | 🟠 规范缺口 |
| **相关条款** | 规范 **R-5**『记录 MUST 含 `based_on.snapshot`』 |

**现象**：参数校验失败、目标不存在、无权限 —— 这三种拒绝发生在**任何读取之前**。
此时**根本不存在快照**，`based_on.snapshot` 无值可填。

本实现对这些记录填 `snapshot = None`。

**规范的 R-5 是无条件的，与实现冲突。**

**建议修正 R-5：**

> **R-5（修订）**：**若本次提交发生了任何对事实层的读取**，
> 记录 **MUST** 含 `based_on.snapshot`。
> 未发生读取的早期拒绝，`based_on` **MUST** 存在但 `snapshot` **MAY** 为 null。

### 发现 3：可选参数缺失时，表达式的求值语义未定义

| | |
|---|---|
| **类型** | 🟠 规范缺口 |
| **相关条款** | 规范 §2.2（`required`）、§2.3（表达式上下文） |

**现象**：若参数 `required: false` 且调用方未提供，那么在前置条件表达式里
引用该参数会发生什么？规范**没有定义**：

| 候选语义 | 问题 |
|---|---|
| 变量为 `null`，比较返回 false | 会导致"因未传可选参数而被拒"，语义可疑 |
| 变量为 `null`，比较返回"未知" | 那"未知"的前置条件算不算通过？ |
| 直接报错 | 可选参数就失去意义了 |

**本实现的临时选择**：变量为 `null`；与 `null` 的顺序比较返回 `None`（未知）；
`None is not True` → 前置条件不通过。

**规避**：示例里把 `refund_amount` 设为**必填**，绕开了这个问题。

**建议**：规范 **MUST** 定义缺失可选参数的求值语义。
本实现倾向于"**存在性守卫**"方案：表达式需显式处理 null，否则该前置条件判为不通过并在
`violations[].actual` 里标出缺失的参数名。

### 发现 4：`suggestions` 的"可选"与 `A-2`（可自纠）存在张力

| | |
|---|---|
| **类型** | 🟡 设计张力 |
| **相关条款** | 规范 §4.2（`suggestions` 可选）vs 框架 **§20.8 A-2** |

**现象**：框架的 Agent-first 条款 `A-2` 要求"所有拒绝 MUST 可被自动纠正"。
但规范里 `suggestions` 是**可选**字段。

**本实现的 `suggestions` 恒为空数组**（`ActionEngine._suggestions` 是显式的空实现，
不是遗漏）。

**问题**：一个只读拒绝信息的 Agent，在没有 `suggestions` 时能否自纠？
实践上，`stage` + `violations[].id` + `actual` 已经足够让它**修正参数**，
但不足以让它**改选另一个动作**（那需要知道本体里有哪些替代动作 —— 属 I6 发现）。

**建议**：把"替代动作建议"归入 **I6 发现**的职责，而不是 I4 的可选字段。
即：`suggestions` 保持可选，但 **I6 MUST 提供"按需求找能力"**，
让 Agent 自己完成改选。

### 发现 5：YAML 1.1 把 `on` 解析成布尔值 —— 字段名陷阱

| | |
|---|---|
| **类型** | 🔴 **格式陷阱（实际踩到）** |
| **相关条款** | I4 v0.2 **`M-8`** |

**现象**：多实例事务最初用 `on:` 指定效果的作用目标：

```yaml
effects:
  - on: customer        # ← 灾难
    set: { path: "risk_flag", value: "'high'" }
```

**PyYAML（遵循 YAML 1.1）把 `on` 解析为布尔值 `true`。**
于是这个 effect 的键名**根本不是字符串 `"on"`**，而是 `True`：

```python
e.get("on")   # → None        # 字段静默丢失
```

**后果：不报错，只是不生效。** 效果被作用到了错误的目标，或者根本没指定。
这类"静默失效"比报错危险得多。

**修法**：字段名改为 **`applies_to`**；同时加载器**显式拒绝** `on` 并给出解释（不让人再踩）。

> **教训：YAML 格式的规范 MUST 禁用 `on` / `off` / `yes` / `no` 作为字段名。**
> JSON 没这个问题（只有 `true`/`false`），但 Ossie 系列规范都用 YAML。

### 发现 6：ABox 缺少类型断言，派生规则无法定位主语

| | |
|---|---|
| **类型** | 🟠 规范缺口 |
| **相关** | Ossie 的 `ontology mappings` vs 运行时 |

**现象**：实现 `derived_by` 求值时，需要知道"哪些实例属于概念 C"以限定主语范围。

但 Ossie 只用 `ontology mappings` 描述**静态的"物理字段 → 概念"映射**，
**没有定义运行时的类型断言**（"这个实例属于哪个概念"）。

本实现引入保留关系 `__concept`。**但这应该是规范的一部分，而不是每个实现自己发明。**

**建议**：在 I1/I2 规范里明确运行时类型断言的表示与写入时机。

---

### 发现 7：Ossie 自带表达式语言，本实现不该另立 CEL

| | |
|---|---|
| **类型** | 🟠 **规范偏离（已修正为 `E-3` 过渡态）** |
| **相关条款** | I4 §2.3 `E-1` ~ `E-3` |

**发现**：`ossie-apache/core-spec/expression_language.md`（36 KB）定义了 Ossie 的表达式语言
（状态 *Proposed Final*，工作组含 Snowflake / Databricks / dbt Labs / Starburst / Cube / Denodo）。

**它是 SQL 的一个子集**，不是通用表达式语言，而且**对齐本体的命名空间解析**。

**问题**：I4 最初推荐 CEL。但表达式出现在 Ossie 的 `requires` / `derived_by`
与本规范的 `preconditions` / `constraints` / `effects` 中 ——
**在同一个语义层里放两套表达式语言，是人为制造的割裂。**

**处理**：

- I4 §2.3 已修正为 **MUST 使用 Ossie 表达式语言**
- 本实现（`expr.py`）仍是 CEL 子集，**标注为 `E-3` 允许的过渡态**
- 待 Ossie 表达式语言定稿后，参考实现应迁移

> **教训：在"符合的部分用 Ossie"这个原则下，先查 Ossie 有没有，再决定自己做什么。**
> 这次的教训是**没查就推荐了外部语言**。

## 已知的实现取舍

| 取舍 | 说明 |
|---|---|
| **SQLite 而非 Postgres** | 参考实现要能零运维跑起来；框架 §23 建议 Postgres |
| **合并 facts 表** | 框架建议实体表 + 边表；本实现用一张 append-only 表 + 有效区间，换取快照读 |
| **乐观并发** | 规范 C 组只要求乐观 |
| **表达式子集** | 不是完整 CEL，只覆盖 E-2 的 MUST；不支持函数调用（会明确报错） |
| **不支持的 Ossie 字段会被记录** | `OssieModel.unsupported`，打印在 `describe()` 里 |

## 一致性声明

**对 I4-min 规范**：本实现声称符合 **I4-min/Core**（全部 MUST 条款）。

**未声称符合 I4-min/Plus** —— 它要求全部 SHOULD，
而其中「用 CloudEvents 发布审计事件」与「产生替代动作建议」未实现。

**对框架的合规等级**：本实现**没有**完整达到任何一级。

| 等级 | 要求 | 本实现 |
|---|---|---|
| **L0 可声明** | 用 Ossie 描述概念/关系/约束/派生 | ⚠️ 概念、关系、约束 ✅；**`derived_by` 未支持** |
| **L1 可读** | I1 + I2 + **I3** + **I6** | ❌ **I3（查询接口）与 I6（发现）完全没实现** |
| **L2 可写** | I4 + 写入过约束 + 拒绝可解释 | ✅ **核心已具备** |

### ⚠️ 一个框架层面的观察：等级阶梯暗示的顺序不成立

框架 §18 把合规等级画成阶梯：

```
L0 可声明 → L1 可读 → 【分水岭】→ L2 可写 → ...
```

**暗示你必须先过 L1 才能到 L2。**

**但这个参考实现是在完全没有实现 I3（查询接口）的情况下，把 L2 的核心（I4）做出来的。**
因为在最小 I4 的范围里，动作只需要读取目标实例的属性 —— 那是 I2 的能力，不需要 I3。

**结论**：阶梯描述的是**能力等级**，不是**实现顺序**。
建议框架补一句说明，避免读者以为必须先做完 L1 才能碰 L2。

（这也有可能说明 L1 的接口划分需要重新审视 —— I3 与 I2 的边界在最小场景下是模糊的。）
