# 质疑：治理真正难的是让人达成共识

| 字段 | 值 |
|---|---|
| **类型** | 💬 讨论 · **对本框架自身的质疑** |
| **严重度** | 高（若成立，框架的治理部分价值有限） |
| **关联章节** | `docs/framework.md` §1、§24.2 第 8 条 |

---

## 质疑内容

框架第一部分用整章定义了"治理的六件事"：

```
命名空间与权威 · 变更流程 · 争议解决 · 版本兼容 · 分叉退出 · 权责矩阵
```

**但这些都是机制。而治理真正难的不是机制，是人。**

> **一个高效的提案系统，救不了一群谈不拢的人。**

## 具体表现

### 1. 机制能加速共识，但不能产生共识

| 框架提供的 | 能解决 | 不能解决 |
|---|---|---|
| 提案模板 | 提案写得更规范 | **两个部门对"客户"定义不肯让步** |
| 公示期 | 让受影响方知情 | **知情了也不同意** |
| 争议解决流程 | 有地方吵 | **吵完了还是各说各话** |
| 分叉权 | 可以不吵，各做各的 | **但那就没有"共同语义"了** |

**最后一行是关键**：框架给出的终极解法是"分叉"。
但**如果分歧的双方都选择分叉，那"共同语义背景"这个目标就落空了**。

### 2. 权力不对称

框架假设参与方是平等的。但现实中：

- 强势部门说"必须按我们的定义"，弱势部门只能接受
- 或者反过来，谁都不肯改，于是核心层永远空着

**"共识"在权力不对称下不是谈出来的，是压出来的。**
框架对此没有说法。

### 3. 激励问题（语义网的核心教训）

> 共享"语义"这件事：**成本归你自己，收益归所有人。**

所以理性的选择是：

- 用别人的定义（省事）
- 不维护自己的定义（省成本）
- 不提提案（不惹麻烦）

**结果：核心层长期无人维护，逐渐腐化。**

这正是语义网失败的原因，框架在 `docs/rationale.md` 里分析过，**但没有把对策写进框架**。

## 可能的应对（都需要验证）

| # | 方向 | 疑问 |
|---|---|---|
| 1 | **让维护核心有收益** —— 比如治理机构掌握资源分配权 | 这不就是权力不对称？ |
| 2 | **降低参与成本** —— 扩展层无需批准（框架已有） | 可能让核心层更没人管 |
| 3 | **自上而下强推** —— 高层下命令 | 有效但脆弱，换领导就废 |
| 4 | **小范围起步** —— 先在一个业务闭环里成功，再扩 | 框架的 Profile 已经隐含这个，但没明说 |
| 5 | **承认它解决不了** —— 框架只提供机制，组织问题交给组织 | **最诚实，但也是最弱的** |

## 需要什么帮助

- 🎯 **有本体/KG 项目落地经验的人**：项目最后失败，是因为技术还是因为组织？
- 💬 **有没有"核心层长期有人维护"的成功案例？它靠什么维持？**
- 💬 **框架是否应该明确写出"本框架不解决组织问题"**，把预期管理清楚？
- 💬 **如果最终解法是"小范围起步"，那框架是否该改成"从 Profile A 起步，逐级升"的渐进模型？**

## 为什么这条值得单开

**因为如果这个质疑成立，框架第一部分（治理）就从"核心设计"降级为"机制清单"。**

它仍然有用 —— 但没有框架暗示的那么重要。
**与其让使用者以为有了提案系统就能治理好，不如明说：机制只是一半。**
