# 定义变更的影响分析怎么做

| 字段 | 值 |
|---|---|
| **类型** | 🎯 核心工作 |
| **严重度** | 高（治理能否成立的前提） |
| **关联条款** | `G-6`（变更 MUST 可计算影响面）、`I1-3`（MUST 支持差异对比） |

---

## 背景

框架的治理部分有一条硬要求：

> **`G-6`：变更 MUST 可计算影响面。**

以及一条接口要求：

> **`I1-3`：MUST 支持任意两版本的差异对比。**

**但没有说"怎么算"。** 这是治理能否真正成立的前提 —— 如果算不出影响面：

- 公示期变成形式（没人知道该关注什么）
- 弃用期无法评估（不知道该通知谁）
- 提案评审是盲的

## 影响面要回答的问题

给定一个变更（比如"给 `Order` 概念加一个必填属性"），要能算出：

| # | 问题 | 难度 |
|---|---|---|
| 1 | 哪些**概念/关系**受影响？ | 🟢 容易（静态引用分析） |
| 2 | 哪些**派生规则**会失效或改变结果？ | 🟡 中等（要跟随引用链） |
| 3 | 哪些**动作**的前置条件会失效？ | 🟡 中等 |
| 4 | 哪些**消费者**（系统/报表/Agent）会受影响？ | 🔴 **难** —— 需要知道谁在用 |
| 5 | 有多少**实例**违反新约束？ | 🔴 **难** —— 要在全量事实上试算 |
| 6 | 影响是**立即**还是**随数据增长显现**？ | 🔴 **很难** |

第 4、5、6 条是真正的难点。

## 具体缺口

### 缺口 1：消费者注册

**框架没有要求消费者注册。**

不知道谁在用某个概念，就算不出"哪些消费者受影响"。
但要求注册又增加采用门槛 —— **这是个取舍**。

候选：

- 强制注册（治理强，门槛高）
- 通过 I6 发现机制的**访问日志**反推（无门槛，但冷启动期算不出）
- 两者结合

### 缺口 2：试算成本

"有多少实例违反新约束"需要在全量事实上跑新约束。

- 对小数据量：可行
- 对大数据量：可能几小时

**那么提案评审时是拿着一个估算值决策，还是等试算跑完？**

### 缺口 3：延迟影响

```
今天加一个必填属性
  ↓
现有实例都不满足 → 但通过 grandfather 条款放行
  ↓
三个月后新建的实例才真正被约束
```

**这种"延迟影响"怎么在提案阶段表达？**

## 需要什么帮助

- 🎯 **做过 schema 演进治理的人**：你们怎么算影响面？
- 💬 **消费者注册该不该强制？** 这是采用门槛 vs 治理能力的直接取舍
- 💬 **Protobuf / Avro 的兼容性检查**能借鉴多少？（它们只处理结构，不处理语义与数据）
- 💬 **是否应该把"影响分析"做成一个独立的参考实现**，而不只是规范要求？

## 建议

先做**最小可用版本**：

```
1. 静态引用分析（问题 1~3）—— 容易，先做
2. 基于 I6 访问日志反推消费者（问题 4）—— 中等
3. 试算只对抽样数据做（问题 5 的近似）—— 够用
```

**不要一开始就追求精确算全量。**
