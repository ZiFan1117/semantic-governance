# 质疑：强 TBox 是否普遍适用

| 字段 | 值 |
|---|---|
| **类型** | 💬 讨论 · **对本框架自身的质疑** |
| **严重度** | 高（若成立，框架适用范围远小于暗示） |
| **关联章节** | `docs/framework.md` §2.2、§24.2 第 9 条 |

---

## 质疑内容

框架在选择 TBox/ABox 作为理论底座时，自己标注过一句：

> **采用 TBox/ABox 框架，等于站在形式本体这一边看问题。**
> **它会天然倾向于"应该有独立的 TBox""应该有推理机"。**
> **这个框架能用，但要记住它不是中立的。**

这个标注是诚实的。**但它的后果可能比标注所暗示的更严重。**

## 后果一：框架预设了"语义应当独立成层"

六层架构的 **L3 是语义层**。如果目标系统：

- 语义本来就稳定（几年不变）
- 只有一两个消费者
- 约束写在应用代码里就够了

**那 L3 会塌掉，六层变五层，"本框架"就退化成"一个普通的数据应用架构"。**

框架在 §24.2 承认了这点，但没有回答：**这种场景占多大比例？**

如果它占多数，那框架就不是"通用标准"，而是"特定场景的标准"。

## 后果二：TBox/ABox 是描述逻辑的视角，但工程界大量系统没有 TBox

一个反例清单：

| 系统 | 有独立 TBox 吗 |
|---|---|
| 大多数 Web 应用 | ❌ 约束在 ORM 和业务代码里 |
| 大多数数据仓库 | ❌ 约束在 ETL 和 dbt tests 里 |
| 大多数微服务 | ❌ 每个服务自己的领域模型 |
| Palantir | ⚠️ 有，但以"元数据 + Action 代码"形式，不是公理 |
| **Ossie** | ✅ 有（但才 0.2.0.dev0） |

**框架的整个论证建立在"应该有独立 TBox"之上。但这个前提本身是需要论证的，不是自明的。**

## 后果三：可能低估了"隐式语义"的价值

不是所有语义都需要被显式声明：

- 一个只有 3 个字段的表，它的语义不言自明
- 一个内部小工具，"订单"就是那个订单，不需要本体

**把这些都强制显式化，是负担而不是收益。**

框架在 Profile A 里已经承认这点（轻量剖面）。**但 Profile A 还需要 I1+I2+I3 三个接口 —— 对一个记忆库来说，这是不是仍然过重？**

## 未决问题

1. **"强 TBox 路线"的适用边界在哪？** 能否给出一条判据（比如消费者数 × 语义变更频率）？

2. **框架是否应该提供一条"渐进升级路径"？**
   ```
   阶段 0：没有显式语义（就是代码）
      ↓ 什么时候该升？
   阶段 1：有 schema 但没有独立层
      ↓
   阶段 2：有独立语义层（本框架的 L3）
   ```
   **升级的触发条件是什么？**

3. **如果多数场景不该用本框架，那本框架的定位该怎么说？**
   - 是"通用标准"？（可能夸大）
   - 还是"面向多消费者场景的标准"？（更诚实）

## 需要什么帮助

- 💬 **反例征集**：有没有"语义复杂、消费者多，但不用独立语义层也活得好"的系统？
- 💬 **判据**：你认为什么条件下才值得抽出独立语义层？
- 💬 **是否应该在 README 顶部就写明适用边界**，而不是藏在 §24？
- 💬 **Profile A 是否还太重？能否定义一个"Profile 0"**（只有 I1，语义即文档）？

## 为什么这条值得单开

**因为它质疑的是框架的存在理由，而不只是某个设计。**

如果"强 TBox"只适用于少数场景，那这个框架应该诚实地把自己定位为**面向多消费者、多系统场景的语义治理标准**，
而不是暗示"所有组织都需要一套语义背景"。
