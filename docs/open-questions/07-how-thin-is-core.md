# 核心层该多"瘦"？没有客观标准

| 字段 | 值 |
|---|---|
| **类型** | 💬 讨论 |
| **关联章节** | `docs/framework.md` §1.1、§28.2 第 7 条 |

---

## 背景

框架的命名空间设计要求：

> **核心层 MUST 极简** —— 只放跨域必需的概念（客户、组织、时间、金额……）。
> **核心层越胖，治理成本越高，越容易变成瓶颈。**

理由很硬：核心层的每次变更都要走正式提案流程。
核心层越大，走流程的量越大，中央就越容易成为瓶颈 —— 而**瓶颈是中央式治理失败的头号路径**。

**但"极简"没有客观标准。**

## 两难

| 核心层太瘦 | 核心层太胖 |
|---|---|
| 各域重复定义，"客户"在三个域里三个样 | 变更排队，各域绕过中央自己搞 |
| **等于没统一** | **等于没有治理** |
| 跨域对接时才发现对不上 | 中央团队成为全组织瓶颈 |

**注意两边都会导致同一个结果：各域自己搞一套。**

## 一个具体的判断难题

假设三个域都要用"客户"：

| 域 | 对"客户"的理解 |
|---|---|
| 销售域 | 签了合同的法人 |
| 客服域 | 提过工单的联系人（可能是个人） |
| 财务域 | 有应收账款的付款主体 |

**问题：这是"一个核心概念"还是"三个不同概念"？**

- 若判为一个 → 核心层出现一个含义模糊的"客户"，各域在其上打补丁
- 若判为三个 → 核心层没有"客户"，跨域统计时又要对齐

**框架的 §1.3 说"共识是谈出来的，不是统一出来的"，以及"语义冲突必须拆成两个概念"。**
**但这条在三域场景下会退化成"什么都拆"，最终核心层空空如也。**

## 未决问题

1. **有没有可操作的判据**，判断某个概念该不该进核心层？
   - 候选：被 N 个以上域引用？（N 是多少？）
   - 候选：出现在跨域查询里？（怎么预先知道？）
   - 候选：它是否是"跨域事务的参与方"？

2. **核心层应该允许"分层"吗**？
   比如 core-l1（绝对核心：时间、金额、组织）和 core-l2（多数场景核心：客户、订单）？
   分层会不会让治理更复杂？

3. **谁来决定**？§1.6 权责矩阵说"治理机构"，但治理机构凭什么判断"这个够核心"？

## 需要什么帮助

- 💬 **有跨域治理实践的人**：你们怎么划这条线的？
- 💬 **反例征集**：有没有"核心层很胖但治理依然有效"的案例？如果有，框架的假设就是错的
- 💬 **是否应该在框架里只给"判断维度"，不给"阈值"**（承认没有普适标准）？
