# 身份解析的准确率上限与人工介入点

| 字段 | 值 |
|---|---|
| **类型** | ⚠️ 工程约束 |
| **严重度** | 高（是脏数据的头号来源） |
| **关联条款** | `I5-4`（实例身份 MUST 可稳定解析） |
| **关联章节** | `docs/framework.md` §19 |

---

## 背景

框架把"身份先于属性"列为接入接口的硬要求（`I5-4`）：

> 实例的身份（主键/标识）必须能稳定解析。

**但这是整个系统里最难做到的一条。**

真实场景：

```
ERP 里叫「客户 ID」       CRM 里叫「客户编号」
售后系统叫「用户编码」     某部门 Excel 里是手填的公司名
```

同一个客户，四个系统四个身份，而且**没有一个是权威的**。

## 为什么这是头号来源

身份解析错了，会产生**最恶劣的一类脏数据**：

| 错误类型 | 后果 |
|---|---|
| **合并过度**（把两个客户当同一个） | 数据串了，A 的订单出现在 B 名下 —— **且很难发现** |
| **合并不足**（同一个客户算两个） | 统计口径错，报表数字不对 —— **且很难发现** |

**注意两者都"很难发现"** —— 这是它比普通脏数据更危险的原因。
一个空值你能看见，一个错误的合并你看不见。

## 已知的界线

框架没有给出方案，只在 §28.2 里承认：

> 规则解决约 80%，剩下 20% 必须人工。

**这个 80/20 是需要验证的经验值，不是被证实的数据。**

## 未决问题

### 1. 人工介入点设在哪？

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只处理"自动判定为确定相同/不同"的，其余全部人工 | 准确率高 | 人工量爆炸 |
| 自动处理高分和低分，中间带人工 | 量可控 | **中间带的边界怎么定** |
| 全自动 + 事后抽检 | 省人力 | 错误可能长期潜伏 |

### 2. 身份解析的结果要不要落库？

如果落库（存"这两条是同一个实体"的判定），就变成了事实，撤回时又要处理。
如果不落库，每次都要重算。

**这与 Issue #1、#2 是同一类冲突。**

### 3. 人工判定怎么审计？

谁判定"这两个是同一个客户"？依据是什么？判定错了谁负责？

**这是治理问题，不只是技术问题** —— 对应框架 §1.6 权责矩阵，但那里没覆盖身份解析。

### 4. 与 TBox 的关系

`identify_by`（Ossie 有）声明了"用什么关系标识一个概念"。
但**跨系统身份对齐**不等于 **概念内的标识** —— 这是两件事，框架目前混在一起。

## 需要什么帮助

- 🎯 **有 MDM（主数据管理）经验的人**：你们实际怎么划人工介入点？
- 💬 **80/20 这个经验值成立吗？** 有没有反例（某些领域能做到 95%+）？
- 💬 **是否应该把身份解析提升为框架的一等模块**，而不是塞在 I5 里？
