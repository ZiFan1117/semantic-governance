# I4 动作抽象模型：需要可实现的详细规范

| 字段 | 值 |
|---|---|
| **类型** | 🎯 核心工作 |
| **严重度** | 最高（框架唯一的原创核心） |
| **关联章节** | `docs/framework.md` §18 |

---

## 背景

**I4 是本框架唯一需要原创设计的接口。** 其余五个接口都有现成标准可依：
I1 用 Ossie、I2 用 GQL、I3 用 MCP、I5 用 ODCS、I6 待定但概念简单。

**I4 没有先例** —— Palantir 的 Action 是专有的，从未公开其契约模型。

## 现状

框架 §18 已经给出**候选设计**，但它是"候选"，不是"可实现、可测试的规范"：

| 需要定义的四件事 | 现状 |
|---|---|
| ① 动作的**描述格式** | 已列出要素，但无 schema |
| ② 提交的**语义** | 已列出待定义项，但无判定规则 |
| ③ **审计记录**格式 | 已列要素，无字段定义 |
| ④ **拒绝**格式 | 有示例，无规范 |

## 具体缺口（这是本 Issue 要做的事）

### 缺口 1：描述格式需要一份 schema

现在是自然语言列举："参数、前置条件、副作用、写回目标、幂等性"。
**需要**：机器可校验的结构定义（JSON Schema / YAML 结构），以及与 Ossie 的关联方式。

关键未决问题：

- 动作**如何声明它读写哪些概念/关系**？语法是什么？
- 前置条件用**什么表达式语言**？（Ossie 的 `requires` 是表达式，能否复用？）
- 副作用如何**声明式描述**？（对比：命令式写代码）

### 缺口 2：提交语义的判定规则

| 要素 | 待定 |
|---|---|
| 事务边界 | 涉及多实例时，原子性范围由谁决定？动作声明还是实现决定？ |
| 失败语义 | 拒绝 / 部分成功 / 补偿 —— 由动作声明，还是调用方指定？ |
| 并发 | 乐观锁 / 悲观锁 / 由调用方传版本号？ |

### 缺口 3：审计记录需要字段定义

现在写的是"谁·何时·动作·参数·基于什么·结果·副作用·可回滚"。
**需要**：具体字段名、类型、必填性，以及与 CloudEvents 的映射。

**其中"基于什么"最难**：它要求记录读取了哪些事实。
但这与 §13.1 的快照读路径耦合 —— 记录读取集本身有成本。

### 缺口 4：拒绝格式需要规范

拒绝信息的**充分条件**是什么？—— "足以让调用方自动纠正"。

这需要一条可测试的判据，例如：

> 给定拒绝信息 D，一个只读 D 的调用方能否推出正确的重试参数？

## 需要什么帮助

- 🎯 **这份规范是本仓库下一个主要产出物**。欢迎直接提 PR（用 `proposals/0000-template.md`）
- 💬 **前置条件的表达式语言**：复用 Ossie 的表达式，还是另立？
- 💬 **是否应该出一个最小 I4 规范**（只覆盖单实例、同步、无副作用），先把 Level 2 打通？

## 建议的实现顺序

```
1. 先出「最小 I4」：单实例 · 同步 · 无副作用 · 有审计
2. 再补：多实例事务边界
3. 再补：异步与补偿
4. 最后补：声明式副作用
```

**不要一次设计全套** —— 那会做不完。
