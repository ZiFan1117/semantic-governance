# 派生不落库 vs 动作前置条件的冲突

| 字段 | 值 |
|---|---|
| **类型** | 🐛 设计冲突 |
| **严重度** | 高（影响 I2-4 与 I4 的可行性） |
| **关联条款** | `I2-4`（派生事实 MUST NOT 持久化）、`I4-7`（动作读 MUST 用一致性读路径） |
| **关联章节** | `docs/framework.md` §18.2（派生不落库 vs 前置条件）、§16（I2 事实契约）、§18（I4 动作契约） |

---

## 背景

框架有两条硬要求，它们在**同一时刻**互相拉扯：

**要求 A（I2-4）**：派生事实 **MUST NOT** 被持久化。
—— 推出的结论是视图，不是事实。

**要求 B（I4-7 + §18.1 R2）**：动作的一致性读路径 **MUST** 能读到派生事实。
—— 否则写不出"客户订单总额超限"这类前置条件。

## 冲突点

当一次动作提交需要派生值作为前置条件时：

```
① 派生不落库 → 没有现成的派生值可读
② 要在事务里得到它 → 必须现算闭包（不动点迭代）
③ 但闭包计算可能：
   · 超出事务时限
   · 在计算中途遇到定义变更
   · 在高频动作场景下成本不可接受
```

**核心矛盾：不落库换来了"永远与定义同步"，但代价是"每次都要现算"。**
**而动作提交是热路径，现算的开销最不能接受。**

## 候选方案（均无定论）

| # | 方案 | 优点 | 缺点 |
|---|---|---|---|
| 1 | **限定派生深度** | 实现简单 | 表达力受限；深度阈值怎么定 |
| 2 | **物化 + 绑定定义版本** | 快 | 引入了"派生也会落库"，与 I2-4 冲突；需要失效机制 |
| 3 | **前置条件改写** | 无需派生 | 不总是可行（有些条件本质是递归的） |
| 4 | **两阶段：快照上算派生 → 进事务校验** | 事务短 | 有窗口期（算完到校验之间状态可能变） |
| 5 | **混合：热派生物化，冷派生现算** | 平衡 | 复杂度高，需要热度统计 |

## 需要什么帮助

- 🎯 **有实践经验的实现者**：你们在生产里怎么处理这个？
- 🎯 **反例**：有没有场景是这五种方案全都不可行的？
- 💬 **是否应该放宽 I2-4**：允许"声明为可物化的派生"作为显式的例外？

## 为什么这条最硬

它是框架里**唯一一条"理论要求与工程可行性正面冲突"**的地方。
其他开放问题大多是"还没想清楚怎么做"，而这条是"两个 MUST 打架"。
