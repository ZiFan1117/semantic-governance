# 撤回与派生的失效传播

| 字段 | 值 |
|---|---|
| **类型** | 🐛 设计冲突 |
| **严重度** | 高 |
| **关联章节** | `docs/framework.md` §24.2 第 2 条 |

---

## 背景

这是 **TBox/ABox 第三条关系**（撤回）的工程实现，也是经典难题：

> 撤掉一条事实，依赖它的派生结论必须失效。

## 三个具体难点

### 难点 1：同一结论可能有多条推导路径

```
api→auth,  auth→pg   ⟹  api→pg     （路径 1）
api→cache, cache→pg  ⟹  api→pg     （路径 2）
```

撤回 `auth→pg` 后，`api→pg` 该不该消失？

**不该** —— 路径 2 还在。

**所以不能"谁引用我就删谁"**，必须知道每条结论**有几条独立支撑**（justification set）。

### 难点 2：环

```
A → B → C → A
```

推导时没问题（传递闭包自然收敛），但撤回时按"谁引用我删谁"走会**无限绕圈**。

### 难点 3："撤回"有三种，语义完全不同

| 意思 | 正确处理 |
|---|---|
| 当初**录错了** | 永远不该存在 → 依赖它的全部失效 |
| **暂时**不成立 | 有时限的事实 → 要能自动恢复 |
| 出现了**例外** | 默认推理 → 只失效部分结论 |

而多数系统**只实现了第一种**。

## 与"派生不落库"的直接冲突

| | 改定义（TBox） | 撤回事实（ABox） |
|---|---|---|
| **派生不落库** | ✅ **零成本** | ❌ **只能全部重算**（没有推导记录可查） |
| **落库（依赖记账）** | ❌ **全量重算** | ✅ 精确增量 |

**没有两头都便宜的选择。** 这是一条干净的对称取舍。

## 候选方案

| # | 方案 | 代价 |
|---|---|---|
| 1 | **全部重算** | 慢，但永远正确，代码最简单 |
| 2 | **依赖记账（justification set）** | 要额外存储推理链，与 I2-4 冲突 |
| 3 | **版本化 / 时间化（bitemporal）** | 存储翻倍，查询复杂 |

## 需要什么帮助

- 💬 **规模阈值**：数据量到多大时，"全部重算"开始不可接受？
- 🎯 **bitemporal 的实践**：有没有人真的在生产里用时间化方案处理撤回？
- 💬 **是否应该允许实现者自行选择**，而不是在标准里定死？
