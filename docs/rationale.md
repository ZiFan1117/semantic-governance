## 一、先分清三个词

### 1.1 三个词的准确定义

| 词 | 定义 | 不装实例也能成立吗 |
|---|---|---|
| **本体论（Ontology）** | 一套**共享概念化的形式化、显式规范**（Studer 定义）——规定"这个世界里允许存在哪些种类的东西、允许怎么关联" | ✅ 能。它是 schema 层 |
| **知识图谱（Knowledge Graph）** | 以**图结构组织的事实集合**——节点是实体，边是关系。回答"实际存在什么" | ❌ 它本身就是事实 |
| **Palantir Ontology** | Palantir 的**产品名**：一层放在原始数据与应用之间的**语义契约层 + 运营层** | ❌ 它绑定真实数据源 |

### 1.2 为什么会有"两套口径"

| 口径 | 出处 | 主张 |
|---|---|---|
| **A. 学术口径** | 学院派、腾讯云《硬核拆解》 | 本体与 KG 是**同一个东西的两层**：本体是模式层（骨架和规矩），KG 是实例层（血肉） |
| **B. 工程口径** | Palantir 实践派、53AI | 二者**不是一类东西**：KG 是"看的地图"，本体是"开的驾驶舱" |

**分歧根源**：口径 A 的"本体" = 学术本体（OWL/RDFS）；口径 B 的"本体" = Palantir 的产品名。

**混着说就永远说不清。**

### 1.3 三句最准的专业表述（备引用）

> **知识图谱是「让机器理解世界是什么」的开放标准与推理基础设施；
> Palantir Ontology 是「让机器在受治理前提下对世界做什么」的专有语义操作层。**
> —— CSDN《Ontology：Palantir 架构真正的核心》

> **数据库告诉你数据在哪，知识图谱告诉你关系在哪，
> 而 Ontology 告诉你：在这个业务里，什么是真的、什么能改、谁能改、改完留下什么。**
> —— 同上

> **知识图谱是用来"看"的地图，而本体是用来"开"的驾驶舱。**
> —— 53AI《别把 Palantir 的"本体"做成知识图谱》

## 二、理论底座：TBox 与 ABox

### 2.1 定义

TBox/ABox 来自**描述逻辑（Description Logic）**，是把"本体"和"知识图谱"说清楚的最干净的工具。

| | **TBox**（Terminology Box，术语箱） | **ABox**（Assertion Box，断言箱） |
|---|---|---|
| **中文** | 术语公理集 | 断言集 |
| **装什么** | 概念（类）、角色（关系）、公理、约束 | 个体（实例）、具体事实 |
| **回答** | **"允许什么"** | **"实际是什么"** |
| **例子** | "经理是员工的子类"；"部门最多一个负责人" | "alice 是经理"；"研发部负责人是 alice" |
| **生命周期** | 稳定、低频变更 | 持续、高频变更 |
| **类比** | 词典 + 规则手册 | 使用记录 |

**一句话**：

> **TBox 是"图纸"，ABox 是"盖好的房子"里的具体人和物。**

### 2.2 为什么用 TBox/ABox 作为本文底座

选它，不选"本体 vs 知识图谱"，有四个理由：

| 理由 | 说明 |
|---|---|
| **① 它是通用的** | 描述逻辑是数学，不绑定任何产品。用它推导出的分层不会过度拟合 Palantir |
| **② 它天然分开了两件事** | "允许什么" vs "实际是什么"——这正是分层的理论依据 |
| **③ 它有严格定义** | "约束""推理""一致性"在它里面都有精确含义，不靠类比 |
| **④ 它揭示了分水岭** | 有没有独立的 TBox（及其公理与推理）= 形式本体 vs 图数据库的分界 |

**⚠️ 但要说清这是一个"选择"：**

> 采用 TBox/ABox 框架，等于**站在形式本体这一边看问题**。
> 它会天然倾向于"应该有独立的 TBox""应该有推理机"。
> 而工程界大量系统**根本没有清晰的 TBox**——它们的"约束"写在应用代码里。
>
> **这个框架能用，但要记住它不是中立的。**

### 2.3 TBox 的完整构成（21 项要素）

这是后面核验 Ossie 的**检查清单**。

| # | TBox 要素 | 说明 | 通俗解释 |
|---|---|---|---|
| 1 | **概念 / 类** | Person、Order | 有哪几类东西 |
| 2 | **类层次（subClassOf）** | Manager ⊑ Employee | 谁是谁的子类 |
| 3 | **类构造子** | 交 ⊓、并 ⊔、补 ¬ | 用已有的类拼出新类 |
| 4 | **角色 / 属性** | hasParent、worksFor | 有哪几种关系 |
| 5 | **定义域（domain）** | 谁能当主语 | 关系的左边允许谁 |
| 6 | **值域（range）** | 谁能当宾语 | 关系的右边允许谁 |
| 7 | **逆关系（inverseOf）** | owns ↔ ownedBy | 反过来是什么 |
| 8 | **传递性（transitive）** | A→B, B→C ⟹ A→C | 会不会"传染" |
| 9 | **对称性（symmetric）** | A→B ⟹ B→A | 是否双向 |
| 10 | **自反性（reflexive）** | A→A | 是否指向自己 |
| 11 | **函数性（functional）** | 最多一个 | 一对一还是一对多 |
| 12 | **基数约束（min/max/exactly）** | 恰好 2 个 | 数量限制 |
| 13 | **存在量词（someValuesFrom）** | 至少有一个 | "必须有" |
| 14 | **全称量词（allValuesFrom）** | 全部都是 | "只能是" |
| 15 | **不相交类（disjointWith）** | A 和 B 无交集 | 互斥 |
| 16 | **等价类（equivalentClass）** | A ≡ B | 同义 |
| 17 | **个体等价/不等（sameAs / differentFrom）** | 这两个是同一个吗 | ⚠️ **开放世界的命门** |
| 18 | **值类型 / 数据类型** | xsd:string、正整数 | 值的类型 |
| 19 | **完整性约束（IC）** | "金额必须为正" | 数据校验规则 |
| 20 | **派生规则** | 由别的推出这个 | 算出来的类/关系 |
| 21 | **标识（identification）** | 怎么引用一个实体 | 主键 / 复合标识 |

### 2.4 ABox 的构成

| 要素 | 说明 |
|---|---|
| **个体（Individual）** | 一个具体对象："alice"、"订单#12345" |
| **概念断言** | `alice ∈ Manager` |
| **角色断言** | `(alice, R&D) ∈ worksIn` |
| **属性值** | `alice.age = 32` |
| **个体等价/不等** | `alice sameAs a.chen` |

### 2.5 TBox 与 ABox 的三种关系

这是**全部分层与机制的理论来源**：

| 关系 | 含义 | 对应系统能力 |
|---|---|---|
| **① 约束** | TBox 规定 ABox 里什么合法 | **校验** |
| **② 推理** | TBox 的公理在 ABox 上求闭包，推出没写的事实 | **推理** |
| **③ 撤回** | ABox 里撤掉一条，依赖它的派生结论要失效 | **真值维护** |

**这三条，就是后面所有机制的理论根。**

## 三、从 TBox/ABox 推导系统分层

### 3.1 推导过程（不是类比，是推导）

对每一样东西问："它对应 TBox/ABox 的哪个部分？"

| 理论对象 | 系统里需要什么 | 得到哪一层 |
|---|---|---|
| **TBox 本身** | 存放、版本化、提供定义 | **L3 语义定义层** |
| **ABox 的载体** | 存实例和事实，且要快 | **L2 存储与索引层** |
| **ABox 的构建过程** | 数据怎么进来、怎么不变脏 | **L1 摄取与治理层** |
| **TBox + ABox 求闭包** | 推理 | **L4 查询与推理层** |
| **对 ABox 的读** | 查询 | （并入 L4） |
| **对 ABox 的受控写** | 校验 + 权限 + 审计 | **L5 动作与写回层** |
| **使用方** | 人 / Agent / 外部系统 | **L6 使用与接口层** |

**注意 L5 是怎么来的**：

> TBox 第 ① 条关系是"约束"——它要求 ABox 只能装合法的事实。
> **那么"往 ABox 里写"这个动作，就必须过 TBox 这道关。**
> 这就是 L5 存在的理论理由，而不是"因为 Palantir 有 Action"。

**这是 v3 相对 v2 最实质的改进**：L5 不再是照抄 Palantir，而是从"TBox 约束 ABox"推导出来的必然结果。

### 3.2 得到六层（自下而上编号）

```
        ╔══════════════════════════════════════════════════╗
        ║  外部：数据源（ERP/CRM/数仓/API/流）  ← 入站      ║
        ╚═══════════════════════╤══════════════════════════╝
                                │
┌───────────────────────────────┴──────────────────────────┐
│ L6  使用与接口层   人 / Agent / 外部系统调用              │
├──────────────────────────────────────────────────────────┤
│ L5  动作与写回层   参数·校验·权限·审批·副作用·审计        │──→ 写回外部（出站）
│                    ↑ 理论来源：TBox 对 ABox 的"约束"       │
├──────────────────────────────────────────────────────────┤
│ L4  查询与推理层   对象集·遍历·推理·向量检索              │
│                    ↑ 理论来源：TBox 公理在 ABox 上求闭包   │
├──────────────────────────────────────────────────────────┤
│ L3  语义定义层     = TBox 的载体                          │
├──────────────────────────────────────────────┬───────────┤
│ L2  存储与索引层   = ABox 的载体             │  元数据   │
├──────────────────────────────────────────────┴───────────┤
│ L1  摄取与治理层   = ABox 的构建过程                       │
└──────────────────────────────────────────────────────────┘
```

**每层的理论身份：**

| 层 | 理论身份 | 一句话 |
|---|---|---|
| L1 | ABox 的**构建过程** | 怎么把现实世界填进 ABox 而不弄脏 |
| L2 | ABox 的**载体** | 事实存在哪、怎么存得快 |
| L3 | **TBox 的载体** | 允许什么 |
| L4 | TBox **在** ABox **上求值** | 能问出什么、能推出什么 |
| L5 | TBox **约束** ABox **的关口** | 能安全地改什么 |
| L6 | ABox/TBox 的**消费方** | 谁在用 |

### 3.3 两条流

| 流向 | 方向 | 说明 |
|---|---|---|
| **数据流（ABox）** | **自下而上** | 数据源 → 摄取 → 存储 → 查询/动作 → 使用 |
| **定义流（TBox）** | **自上而下** | TBox（L3）驱动摄取（L1）按什么形状抽、存储（L2）按什么类型索引 |

**分层架构里双向流是正常的，但必须说清是哪两条**，否则会误以为"数据从语义层流出来"。

### 3.4 切面（贯穿 L1~L6）

| # | 切面 | 回答什么 |
|---|---|---|
| ① | 身份与权限 | 谁能看/改哪个对象的哪个字段 |
| ② | 审计与血缘 | 谁、何时、基于什么、做了什么；数据从哪来 |
| ③ | 版本与演进 | 模型/规则改了怎么回滚 |
| ④ | **合规与删除** | 被遗忘权；数据删了，派生的结论删不删 |
| ⑤ | **成本与 SLA** | 谁能用多少算力；数据多久刷新 |
| ⑥ | **流程与组织** | 谁建模、谁评审、怎么演进 |

**⚠️ 关于 ⑥**：严格说它**不是切面，是一个独立的横跨维度**——

> **本体从来不是"建"出来的，是"谈"出来的。**

## 四、Ossie 是什么

| 项 | 值 |
|---|---|
| 全名 | Apache Ossie (incubating)，前身 **Open Semantic Interchange (OSI)** |
| 定位 | **行业规范，不是系统** |
| 格式 | 声明式 **YAML** |
| 许可 | Apache 2.0，厂商中立 |
| 仓库 | apache/ossie；2107 star / 267 fork |
| 官网 | https://ossie.apache.org/ |
| 状态 | 2026-07 进入 Apache 孵化器并改名 |
| 参与方 | Snowflake、Databricks、dbt Labs、Cube、Denodo、Collibra、DataHub 等 |

**它有两份规范：**

1. **核心语义模型**（`core-spec/`）—— 面向 BI：`datasets`、`fields`、`metrics`、`dimensions`、`relationships`
2. **本体规范**（`ontology/`，v0.2.0.dev0）—— 面向概念建模：`concept`、`relationships`、`requires`、`derived_by`

**核验语义定义能力，主要看第二份。**

### 4.1 Ossie 本体规范的完整字段

| 结构 | 字段 |
|---|---|
| `ontology` | name、description、`ai_context`、ontology(list) |
| **`concept`** | name、type(`EntityType`/`ValueType`)、description、**`extends`**、**`derived_by`**、**`identify_by`**、**`requires`**、relationships |
| **`relationships`** | name、description、**`multiplicity`**(`ManyToOne`/`OneToOne`)、**`roles`**、`derived_by`、`requires`、**`verbalizes`** |
| `roles` | concept、name |
| **内置概念** | `Any`、`Boolean`、`Date`、`DateTime`、`Decimal`、`Float`、`Integer`、`String` |
| **Ontology mappings** | `object_mappings`(concept/expression/referent_mappings)、`link_mappings`(object_mapping/relationship/children) |

## 五、【核心】TBox 要素 × Ossie 覆盖度矩阵

> 这是本文最实用的一张表。**21 项 TBox 要素逐项核验。**

| # | TBox 要素 | Ossie | 靠什么实现 | 备注 |
|---|---|---|---|---|
| 1 | **概念 / 类** | ✅ | `concept` | 分 `EntityType` / `ValueType` |
| 2 | **类层次** | ✅ | `extends`（可多继承） | |
| 3 | 类构造子（交并补） | ❌ | — | 要用 `derived_by` 近似 |
| 4 | **角色 / 属性** | ✅ | `relationships` | |
| 5 | **定义域** | ✅ | 关系声明在某个 concept 下，第一个角色即定义域 | |
| 6 | **值域** | ✅ | `roles[].concept` | |
| 7 | 逆关系 | ⚠️ **规则式** | 写 `derived_by` 交换角色 | 不是声明式公理 |
| 8 | 传递性 | ⚠️ **规则式** | 写 `derived_by` 的 base + recursive case | 见下方实例 |
| 9 | 对称性 | ⚠️ 规则式 | 写 `derived_by` 交换角色 | |
| 10 | 自反性 | ❌ | — | 很少需要 |
| 11 | **函数性** | ✅ | `multiplicity: ManyToOne` / `OneToOne` | 语义是"函数依赖" |
| 12 | 基数（min/exactly N） | ❌ | — | **只有"最多 1"，没有 min / N** |
| 13 | 存在量词 | ❌ | 要用 `derived_by` 近似 | |
| 14 | 全称量词 | ❌ | — | |
| 15 | 不相交类 | ❌ | — | |
| 16 | 等价类 | ❌ | — | |
| 17 | sameAs / differentFrom | ❌ | — | ⚠️ **开放世界的命门，也是 OWA 不可用的根因** |
| 18 | **值类型** | ✅ | `ValueType` + 8 个内置概念 | |
| 19 | **完整性约束** | ✅ | **`requires`** | 可挂 concept 或 relationship |
| 20 | **派生规则** | ✅ | **`derived_by`** | **支持递归** |
| 21 | **标识** | ✅ | **`identify_by`** | 支持复合标识 |

### 5.1 额外能力（Ossie 有、经典 TBox 没有的）

| 能力 | Ossie | 价值 |
|---|---|---|
| **n 元关系** | ✅ `roles` 列表 | ⚠️ **强于 RDF**（RDF 要 reification 才能表达三元以上关系） |
| **自然语言表述模板** | ✅ `verbalizes` | 如 `"{Person} earns {Salary}"`——**强于 `rdfs:label`，是给 LLM 用的** |
| **给 AI 的上下文** | ✅ `ai_context` | 同上，时代特征 |
| **角色命名** | ✅ `roles[].name` | 同一概念占多个角色时消歧 |
| **物理映射** | ✅ ontology mappings | 从字段到对象的映射规则（属于 ABox 侧） |

### 5.2 传递性怎么用规则实现（关键实例）

**OWL 的写法（声明式公理）：**
```turtle
:ancestor_of a owl:TransitiveProperty .
```
一句。但需要**通用推理机**，且最坏 NEXPTIME。

**Ossie 的写法（递归规则）：**
```yaml
- name: ancestor_of
  roles: [ concept: Person, name: descendant ]
  derived_by:
    - "Person.parent_of(descendant)"                # base case
    - "Person.ancestor_of.parent_of(descendant)"    # recursive case
```
两句，但**引擎只需一个规则求值器**，可控、可停、可增量。

> **这就是核心权衡：Ossie 用"规则"替代了"公理"。**

## 六、核验结论

### 6.1 结论一：**能支撑，但支撑的是一个"工程实用子集"**

统计一下：

| 类别 | 数量 | 要素 |
|---|---|---|
| ✅ **完整支持** | **12 / 21** | 概念、类层次、角色、定义域、值域、函数性、值类型、完整性约束、派生规则、标识、n 元关系、映射 |
| ⚠️ **规则式可近似** | **3 / 21** | 逆关系、传递性、对称性 |
| ❌ **不支持** | **6 / 21** | 类构造子、自反性、基数(min/N)、存在量词、全称量词、不相交类、等价类、sameAs/differentFrom |

**换句话说：**

> **Ossie 拿走了"能落地的那部分"（结构、层次、角色、约束、派生、标识），
> 扔掉了"需要推理机的那部分"（公理化的属性特征、量词、集合运算、个体等价）。**

### 6.2 结论二：这不是缺陷，是**刻意的设计选择**

它和语义网失败的四条教训完全一致：

| 教训 | Ossie 的对应选择 |
|---|---|
| 开放世界假设让企业无法用（count 不了、拒不了脏数据） | **没有 sameAs/differentFrom**，回避 OWA 命门 |
| 推理复杂度不可控（OWL DL 最坏 NEXPTIME） | **没有传递/对称/逆的公理**，改用 `derived_by` 规则 |
| W3C 那套工业界不用 | **不用 RDF/OWL，用 YAML** |
| 需要有人能强制推行 | **厂商联盟**（Snowflake、Databricks、dbt…） |

### 6.3 结论三：对"类 Palantir 系统"够用吗？

| 需求 | Ossie 够吗 | 说明 |
|---|---|---|
| 定义业务对象和关系 | ✅ 够 | |
| 定义约束（业务规则） | ✅ 够 | `requires` |
| 定义派生/推导 | ✅ 够 | `derived_by`，含递归 |
| 表达"传递关系" | ✅ 够（啰嗦） | 写规则 |
| 表达复杂公理（量词、集合运算） | ❌ 不够 | 需要 OWL 或自己写代码 |
| 表达个体同一性（消歧） | ❌ 不够 | 这是身份解析的活，本来也不该放这 |
| **Action 定义** | ❌ **完全没有** | **不属于 Ossie 的范围** |
| 权限 / 审计 / 版本 | ❌ 完全没有 | 同上 |

> **对语义定义这一层（L3）：够用。而且比自研一个 schema 强得多。**
> **对 L5 及以上：它本来就不管，你也别指望。**

## 七、缺失项的补偿方案

对 6 项不支持的要素，怎么补：

| 缺什么 | 补偿方案 | 代价 |
|---|---|---|
| **传递 / 对称 / 逆** | 写 `derived_by` 规则（已支持） | 啰嗦；每条关系都要手写 base + recursive |
| **类构造子（交并补）** | 写 `derived_by` 派生出新概念 | 表达力受限，复杂定义写不出来 |
| **基数（min / exactly N）** | 写成 `requires` 表达式 | 只能表达"值约束"，不能参与推理 |
| **量词** | 用 `requires` 近似 | 只是校验，推不出新事实 |
| **不相交 / 等价类** | 写成 `requires` | 同上 |
| **sameAs / differentFrom** | **在 L1 身份解析里解决** | ✅ 这本来就是 L1 的职责，不该放 L3 |
| **Action / 权限 / 审计** | **在 L5 自己实现** | 这是核心工作量，无捷径 |

**一句话**：

> **能声明成规则的，就写成规则；声明不了的，就写成 `requires` 校验；
> 两边都不行的（Action），自己实现。**

# 第三部分 · 实施细节

## 九、逐层详解与技术选型

> 自下而上讲解，与 §3.2 编号对应。

### L1 摄取与治理（= ABox 的构建过程，**工作量最大**）

**核心思想：不指望数据干净，指望入口干净。**

| 机制 | 干什么 | 要点 |
|---|---|---|
| **数据契约** | 与上游签协议：字段、类型、必填、值域、频率、主键 | **这是组织协议，不只是技术机制** |
| **拒收区** | 不合规数据隔离，等人来修 | ⚠️ **不要自动清洗**——那是错误放大器 |
| **身份解析** | 解决"同一实体在四个系统里四个身份" | **脏数据头号来源**；规则解决 80%，其余人工兜 |
| **金记录** | 多源冲突时谁赢 | 需要明确优先级规则 |
| **校验点前移** | 能在入口拒的，绝不留到后面 | 越往后修复成本越高 |

**⚠️ 依赖方向**：本层行为**由 L3 的映射规则驱动**（定义流自上而下）。

### L2 存储与索引（= ABox 的载体）

**分层混合（polyglot persistence），没有一种存储能全包：**

| 数据 | 存哪 | 为什么 |
|---|---|---|
| **元数据/规则（TBox）** | **关系库**（Postgres） | 量小、要事务、要版本化、要求最高 |
| 对象属性（ABox） | 列存 + KV/索引 | 点查与聚合分离 |
| 图骨架（ABox） | 图库 或 边表 | 只有这层需要多跳 |
| 原文 | 对象存储 / ES | 大块文本 |
| 向量 | 向量库 | 语义检索入口 |
| 缓存/摘要 | KV | 快 |

**两条关键工程原则：**

> **① 图管关系，表管属性。** 图里只放骨架（ID + 类型 + 边），属性放表里。
> 把几百个属性全塞进图 = 图库爆炸 + 聚合跑不动 + 更新代价高。

> **② 列存做分析 + KV/索引做点查。**
> - 分析：扫很多行、只看几列 → **列存**（IO 少 + 压缩率高）
> - 点查：只要一行、要全部列 → **行存 / KV**（一次读 vs N 次随机读）

**"关系库"是什么**：关系型数据库（MySQL/Postgres），数据存成二维表，靠**外键 + JOIN** 表达关联，靠**事务（ACID）**保证不出错。名字里的"关系"是数学术语（指"一张表本身"），**不是"关联"**。

### L3 语义定义层（= TBox 的载体，**Ossie 在这一层**）

**先澄清两个词：**

> **语义（semantics）** = 一套规定/约定，不是实体，是一份契约（YAML 文件）
> **语义层（semantic layer）** = 承载并提供这套规定的**软件组件**

**类比：法律 vs 法院**——法律是规定（不占物理位置），法院是执行机构（必须实实在在建）。
**不能说"法律不占物理位置，所以不需要建法院"。**

**本层内容：**

- 概念/类（含类型层次）
- 属性/角色
- 关系（方向、基数、n 元角色）
- 指标（算法表达式）
- 约束（声明式）
- 派生规则（声明式，可递归）
- 映射（字段 → 对象）

**本层内部还要分：**

```
L3  语义定义层（TBox 载体）
    ├── 格式 / 规范          ← ⭐ Ossie 在这里（静态文本）
    ├── 定义服务（OMS 类）    ← 读定义、校验定义本身、版本化
    └── 定义编辑器           ← 给人用的建模界面
```

**语义和存储为什么要分开？**

| 理由 | 说明 |
|---|---|
| **生命周期不同** | TBox 改动频率远低于 ABox；混在一起，改个指标定义要动数据 |
| **一次存储，多种语义投影** | 同一份 ABox，给风控看的 `Customer` 和给营销看的 `Customer` 可以不同 |
| **可替换性** | 换存储引擎不该影响语义 |
| **多方共建** | 语义是共享契约（Ossie 的意义），存储是你自己的 |

**但现实中它们经常被合在一起（实话）**：dbt（藏在 SQL 里）、传统 BI（藏在报表定义里）、数据库视图（view 就是 schema）。

> **"分开"是目标状态，不是默认状态。**

**什么时候该单独做一层？** 判断标准就一条：

> **是不是有多个系统/团队/工具需要共用同一套语义？**
> 只有你自己用 → 不用抽层；有 N 个系统用 → 不抽就是灾难。

### L4 查询与推理（TBox 在 ABox 上求值）

| 能力 | 说明 |
|---|---|
| 对象集查询 | 按类型/属性/子类过滤聚合 |
| 多跳遍历 | 邻域、路径、连通性 |
| 声明式推理 | 传递/对称/逆、分类推导 |
| 向量检索 | 自然语言 → 入口节点 |

**相关子图提取算法（喂给 LLM 用）：**

| 算法 | 适用 | 代价 |
|---|---|---|
| k-hop 邻域 | 快速看周围 | **爆炸**，必须剪枝 |
| **Personalized PageRank** | 按相关性取 top-k | ⭐ 最推荐；有 forward push 近似算法 |
| 向量 + 图混合 | 从自然语言找入口 | 依赖 embedding 质量 |
| 元路径展开 | 异构图只走有意义的路径 | 需人工定义路径 |
| Steiner Tree | 多实体间最小连通结构 | NP-hard |
| **社区摘要（Leiden）** | **全局性问题** | 预处理贵，要 LLM 生成摘要 |

**⚠️ 关键认知**：没有"把所有相关联的数据都取出来"的算法——"相关"是传染的。
真正的问题是：**在预算约束下，取哪个子图信息量最大。**

**让 LLM 输出时引用具体边**（"`api→db`，依据：`api→pg`、`pg→db`"），
这是把"让模型思考"变得可审计的关键技巧。

### L5 动作与写回（TBox 约束 ABox 的关口）

一个 Action 包含：

| 要素 | 说明 |
|---|---|
| 参数与类型 | 接受哪些输入、是否必填、取值范围 |
| 校验逻辑 | 前置条件（如"订单状态必须是待退款"） |
| 权限 | 谁能对哪个对象实例执行；可基于属性动态推导 |
| 执行 | 改对象状态，或触发服务端函数编排多步流程 |
| 副作用 | 通知、webhook、触发下游构建 |
| **写回** | 受控地回写到源系统（ERP 等）——**出站方向** |
| 留痕 | Action History：谁、何时、基于什么、结果如何 |

**这是"认知层"跨进"操作层"的唯一通道。**

**自己实现的起步形态（几百行）：**

```
一个 API 层，每个动作一个函数：
  参数校验 → 权限检查 → 前置条件 → 执行 → 副作用 → 写审计
再配一张审计表
```

**真正贵的不是 Action 本身，是周边的两件事：数据治理（L1）+ 权限模型。**

### L6 使用与接口

| 使用方 | 接口形态 | 特点 |
|---|---|---|
| **给人用** | 仪表盘、低代码、协作界面 | 看图表、点按钮 |
| **给 Agent 用** | **MCP**、工具调用 | 读结构化返回，**要求引用来源** |
| **给外部系统用** | REST / SDK / webhook | 程序化调用 |

**"给 Agent 用"值得单独拎出来**：接口设计与人用完全不同，且 Palantir 里 AIP 确实是独立产品线。

## 十一、高价值动作

### 11.1 建一个"该被拒绝的样本集"（最便宜且最有效）

收集 100 条**应该被系统拒掉**的数据/操作（非法依赖、超范围值、无权限、会形成环……），
做成测试，每次改规则跑一遍。

**同时做到三件事：**

1. 验证 TBox 规则没写错
2. 验证拒收真的生效（不只是写在文档里）
3. 防止改规则时把原来能拒的搞坏了（回归测试）

**这比任何形式化方法都实用。**

### 11.2 加规则的安全姿势

```
第 1 步：新规则写成"只记录，不拦截"
第 2 步：跑一段时间，看它会拒掉什么
第 3 步：人工审这份"本该被拒"的清单
        ├─ 都是真该拒的 → 改成强制拦截
        └─ 有误伤的   → 先修规则，别上线
第 4 步：上线，保留清单做回归测试
```

# 第四部分 · 机制澄清

---

## 十二、约束在哪一层被强制

**先分清两件事：规则"声明"在哪（TBox）vs 规则"执行"在哪（关卡）。这两个经常不在一个地方。**

| 系统 | 声明在哪 | 谁执行 | 何时执行 |
|---|---|---|---|
| **关系数据库** | DDL / `information_schema` | DBMS 引擎 | **写入时** |
| **RDF / OWL** | ⚠️ **与实例数据同一张图** | 推理机 | 读取时推理 / 批量校验 |
| **SHACL** | shape 文件 | 外挂校验器 | **事后**跑一遍 |
| **LPG 图库** | 约束定义 | 数据库引擎 | 写入时（但只到结构层） |
| **Palantir** | OMS（元数据）+ 权限系统 | Actions 服务 / OSS / Funnel | **分三层** |
| **Ossie** | YAML 里的 `requires` | ❌ **规范不定义执行者** | 由实现方决定 |

### 12.1 核心分水岭：开放世界 vs 闭合世界

| | 开放世界（OWL） | 闭合世界（关系库 / Palantir） |
|---|---|---|
| 假设 | 没写 ≠ 没有 | 没写 = 没有 |
| 能否在写入时拒绝 | ❌ **原理上不能** | ✅ 能 |
| 违反约束的表现 | 本体"不一致" | 直接抛错、回滚 |
| 能否 count | ❌ "至少 N 个，可能更多" | ✅ 精确 |
| 能否判断完整性 | ❌ "也许只是没告诉我" | ✅ 能 |

> **一条就够：一个连"有多少个"都答不了的系统，企业没法用来做报表。**
>
> 而 OWA 下 count 答不了的根因，正是 TBox 第 17 项 **`differentFrom` 的缺失**——
> 你不知道 alice 和 bob 是不是同一个人，所以数不准。

### 12.2 "知识图谱有没有约束"的准确回答

- **RDF 本身**：几乎没有约束（什么都能说）
- **LPG 引擎**：有，但只到"结构"层（唯一性、属性存在性）——相当于 `UNIQUE` / `NOT NULL`
- **SHACL / ShEx**：真正的语义约束，但**外挂、事后跑、不在写入路径**
- **OWL 公理**：违反表现为"不一致"，不是"拒绝"

**反直觉结论：Palantir 的约束模型更像关系数据库，而不是知识图谱。**

---

## 十三、物化 vs 查询时展开

**核心机制**：子类展开是**改写查询条件**（`type = Component` → `type IN (Component, Service, ...)`），
不是"推出新事实存下来"。

| 模式 | 存不存 | 速度 | 一致性 | 可追溯 |
|---|---|---|---|---|
| **物化** | 存下来 | 快 | **差**（TBox 改了要重算） | 好 |
| **查询时展开** | 不存 | 慢一点 | **好**（永远同步） | **差**（事实没存在过） |
| **混合** | 存 + 标记 | 快 | 中 | 中 |

**Palantir 选"不落库"的三个理由：**

1. **一致性**——TBox 持续演进，物化的话每次改都要全量重算
2. **存储不膨胀**——深层继承下实例会被推出几十条归属事实
3. **动态权限必须当时算**——同样一条隐含事实，不同权限的人看到的不一样；**动态权限原理上不能物化**

**⚠️ 关键区分：**

> **"事实不落库"和"过程不落库"是两件事，可以分开设计。**
> - 事实不落库 → 换来一致性、存储、权限正确
> - 过程随响应返回 → 换来可解释、可审计

（`dsh-ontology` 就是两者兼顾的例子：`derived on read and never stored`，
但每条推导事实带 `via` 字段标明来源。）

---

## 十四、推理原理：一个推一个

**术语**：推理链（inference chain）→ 闭包（closure）→ 不动点（fixpoint）

**三种基本套路：** 传递、对称、逆

**必须"反复推"——走到不动点：**

```
已知：api→auth, auth→pg, pg→db

第 1 轮：新增 api→pg（api→auth + auth→pg）
                 auth→db（auth→pg + pg→db）
第 2 轮：新增 api→db（api→pg + pg→db）   ← 用了第1轮的产物
第 3 轮：无新增
第 4 轮：确认 → 不动点，停止
```

> **链有多长，就要推几轮。** 4 个节点的链最多 3 轮。

**会不会停？**

| 系统 | 会不会停 | 为什么 |
|---|---|---|
| Datalog | **一定停** | 事实组合有限 |
| OWL | **一定停** | 特意设计成可判定，代价是表达力受限 |
| **Ossie `derived_by`** | ⚠️ **规范未规定** | 递归规则可能不终止，要实现方保证 |
| 图灵完备代码 | 不保证 | 表达力最强，但没人保证它停 |

**两个方向：**

- **前向链**：从事实往前推，数据驱动 → "把 ABox 补全"
- **后向链**：从问题往回找，目标驱动 → "回答一个查询"（如 `path` 查询）

**三种实现：**

| 实现 | 怎么干 | 谁在用 |
|---|---|---|
| **迭代不动点** | 反复扫描（优化成 semi-naive） | Datalog 引擎、dsh-ontology |
| **Rete 网络** | 规则编译成匹配网络，增量更新 | 专家系统；**Semantica v0.6.8 已实现** |
| **查询重写 / 图遍历** | 不算闭包，按需展开 | **Palantir** |

**Palantir 的三块拼起来看：**

1. **子类/接口展开** —— 读元数据 + 递归展开，**不算推理**
2. **多跳遍历** —— 是真的"一个推一个"，但**按需、局部**
3. **通用推理引擎** —— **没有**。复杂推理要写 Function

## 十五、撤回与真值维护

> **理论上讲，这是 TBox/ABox 第三条关系（撤回）的工程实现，也是最难的一条。**

**难点 1：同一结论可能有多条推导路径**

```
api→auth, auth→pg   ⟹  api→pg     （路径1）
api→cache, cache→pg ⟹  api→pg     （路径2）
```

撤回 `pg→db` 时，`api→db` 该不该消失？**不该**——路径 2 还在。
所以**不能"谁引用我就删谁"**，必须知道每条结论**有几条独立支撑**（justification set）。

**难点 2：环** —— 按"谁引用我删谁"走会无限绕圈

**难点 3："撤回"有三种，语义完全不同**

| 意思 | 正确处理 |
|---|---|
| 当初**录错了** | 永远不该存在 → 依赖它的全部失效 |
| **暂时**不成立 | 有时限的事实 → 要能自动恢复 |
| 出现了**例外** | 默认推理 → 只失效部分结论 |

**三种工程解法：**

| 方案 | 怎么做 | 代价 |
|---|---|---|
| **全部重算** | 撤回后丢掉整个闭包重推 | 慢，但**永远正确**，代码最简单 |
| **依赖记账** | 记"我依赖什么"，反向传播失效 | 要额外存储推理链，**与"不落库"直接冲突** |
| **版本化/时间化** | 不删，改为"T1~T2 有效" | 存储翻倍，查询复杂 |

### 15.1 那个"悖论"的真正形状

| | TBox 改了（改规则） | ABox 撤回（改事实） |
|---|---|---|
| **不落库** | ✅ **零成本** | ❌ 只能全部重算 |
| **落库（依赖记账）** | ❌ **全量重算** | ✅ 精确增量 |

**没有两头都便宜的选择。** Palantir 选"不落库"，正因为它**TBox 改动比 ABox 撤回来得频繁**。

### 15.2 破解方式：分层

1. **ABox 层（撤回事实）** —— 从小数据量起步，用最笨的**全部重算**；别一上来就上 TMS
2. **TBox 层（改规则）** —— **永远不撤回，只版本化**
3. **推导结果不落库，但过程随响应返回**
4. **撤回分级** —— 至少区分"录错了"和"暂时不成立"
5. **LLM 永不进推理链**

### 15.3 LLM 的位置（贯穿全部）

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 非结构化 → 结构化断言（构建 ABox） | **LLM** | 只有它干得了 |
| 从断言推结论 | **确定性引擎** | 必须可复现、可审计 |
| 判断断言是否合法 | **TBox 规则** | 同上 |
| 读检索结果下结论 | **LLM** | 但要**引用具体边**，才可验证 |

> **LLM 只能"提议"，不能"落库"。**

## 十六、Palantir Ontology 对照

### 16.1 官方定义与五个构建块

> "an **operational layer**"，包含 **semantic elements**（objects, properties, links）
> 与 **kinetic elements**（actions, functions, dynamic security）。

| 构建块 | 干什么 | 本文哪一层 | 编程类比 |
|---|---|---|---|
| **Object Types** | 定义有哪几类东西 | L3（TBox） | `class` |
| **Link Types** | 类型化关系（方向、基数） | L3（TBox） | 外键 + 图边（边是一等公民） |
| **Action Types** | 把写操作封装成受治理事务 | **L5** | **syscall** |
| **Functions** | 服务端计算 | L4/L5 | UDF |
| **Interfaces** | 多态 | L3（TBox） | `interface` |

### 16.2 后端微服务 → 对应本文分层

| Palantir 组件 | 本文哪一层 |
|---|---|
| **Funnel** | L1（摄取编排 + CDC 保鲜） |
| **Object Databases** | L2（索引存储 = ABox 载体） |
| **OMS** | L3（定义服务 = TBox 载体）+ L2（元数据存储） |
| **OSS** | L4（读服务） |
| **Actions service** | L5（写服务） |

**关键：重物化 + 索引，不是联邦查询层。数据要接进来，不能原地查。**

### 16.3 与知识图谱的本质差异（用 TBox/ABox 表述）

| 维度 | 传统 KG | Palantir Ontology |
|---|---|---|
| **TBox 独立性** | 有，但常很薄（甚至没有公理） | **强 TBox**，且被系统强制 |
| **逻辑范式** | 开放世界（OWA） | **闭合世界** |
| 推理 | 有通用引擎，可追溯 | **无通用引擎**，靠代码/遍历 |
| 写操作 | 技术上可写，典型是只读分析视图 | **可写，且受治理** |
| 数据新鲜度 | 常离线、易陈旧 | 高（CDC） |
| 权限 | 通常粗粒度 | 单一权限面，可到属性级 |
| 标准化 | W3C 标准，可移植 | 专有，**带不走** |
| **建模能否收敛** | 不收敛 | **能收敛**（业务流程相对固定） |

## 十七、自批判

> **照着一个不可靠的模型建系统会建错。这一节诚实记录缺陷。**

### 17.1 已修正的错误（v2 → v3）

| # | 问题 | v3 的处理 |
|---|---|---|
| 1 | **分层是从 Palantir 反推的**（过度拟合具体产品） | **改用 TBox/ABox 推导**（§3.1） |
| 2 | **L5 的存在理由是"Palantir 有 Action"** | 改为**理论推导**：TBox 第①条关系（约束）要求写入必须过关 |
| 3 | 编号在不同章节不一致 | 全文统一 L1~L6 |
| 4 | **L2/L3 位置反了**（存储画在语义上面） | 对调：**语义（TBox）在上、存储（ABox）在下** |
| 5 | **L1 依赖方向反了** | 明确**两条流**：ABox 自下而上 / TBox 自上而下 |
| 6 | 编造的工作量百分比 | **删除**，只留可确证的定性判断 |
| 7 | 切面不全 | 补上**合规删除、成本与 SLA、流程与组织** |

### 17.2 仍然存在的弱点（未解决）

**弱点 1：采用 TBox/ABox 框架本身就是"选边站"**

> 这个框架倾向于"应该有独立 TBox""应该有推理机"。
> 而工程界大量系统**根本没有清晰的 TBox**——约束写在应用代码里。
>
> **框架能用，但不中立。**（已在 §2.2 标注）

**弱点 2：分层是"强 TBox 派"的分层**

如果目标系统**没有独立 TBox**（约束全在代码里），那么 L3 会塌掉，六层变五层。

> **这个分层预设了"语义定义应当独立成层"，而这不是普遍事实。**

**弱点 3：表达不了闭环**

```
改动作 → ABox 变了 → 下次查询看到 → 可能发现 TBox 要改 → 改 TBox → ...
```

**静态分层图完全没有这个循环。** 而这恰恰是最重要的动态。

**弱点 4：仍然过度依赖 Palantir 作为参照**

§16 整节是 Palantir 对照。虽然分层已改为理论推导，但**验证仍在用 Palantir 当标尺**——存在确认偏差。

**弱点 5：对"只读场景"是过度的**

v1 写"L5 是差异化核心"是**场景相关的判断，被写成了普适结论**。
只读场景下 **L5 可整层砍掉**。（已在 §10 标注）

### 17.3 这个模型还能用吗？

| 用途 | 好不好用 |
|---|---|
| **作为检查清单**（TBox 21 项我漏了什么） | ✅ 很好用 |
| **作为定位工具**（某项目在哪一层） | ✅ 好用 |
| **作为能力核验框架**（Ossie 够不够） | ✅ **很好用**（§5 的矩阵） |
| **作为通用架构模板** | ⚠️ 预设了"强 TBox"，不普遍适用 |

### 17.4 对照验证（用四个真实系统检验）

| 系统 | 覆盖的层 | 验证了什么 |
|---|---|---|
| **Palantir** | L1~L6 全覆盖 | 官方分法是 Language / Engine / Toolchain **三层**，本文拆六层——**是我的拆法，非官方** |
| **Apache Ossie** | **只有 L3 的"格式"部分**，TBox 12/21 | 约全系统 5~10%，但它是契约 |
| **Semantica** | L1~L4、L6，**无 L5** | ✅ 验证"多数系统缺 Action 层" |
| **dsh-ontology** | L3 + L2 + L4 + 一点 L5 | ✅ 它是**纵向切片**——说明分层可用于定位插件 |

## 十八、常见误区

| 误区 | 纠正 |
|---|---|
| 把"本体"等同于"知识图谱" | 取决于"本体"指学术本体还是 Palantir 产品名（§1） |
| 认为本体论只是"理论/层次划分" | 它还包括值域、基数、传递性等约束，且**可执行、可判定** |
| 认为知识图谱是"高级的关系数据库" | 差别不在高低，在**查询代价模型**（join vs 指针游走） |
| 认为 KG 只能读 | KG 也能写；准确说法是"**典型角色是只读分析视图**" |
| 把所有数据都存成三元组 | 工程上自虐；**分层混合**才对 |
| 把属性全塞进图里 | **图管关系，表管属性** |
| 指望"把所有相关数据都取出来" | "相关"会传染；真正的问题是**预算下最大信息量** |
| 认为"声明了约束"就等于"约束生效" | **声明 ≠ 强制**（如 Ossie 的 `requires` 不定义执行者） |
| 认为"开源 Palantir"唾手可得 | 语义层开源充分；**运行时那一半基本没人做** |
| 让 LLM 参与推理链 | LLM 只能提议，**不能落库** |
| 把"语义"和"语义层"混为一谈 | 前者是规定，后者是要实现的软件 |
| 把运行时分层当成建设顺序 | **两个不同的视图，别混用**（§10） |
| 以为 Ossie 有 Action | **完全没有**，那不在它范围内（§5） |

# 第六部分 · 用了 Ossie 之后还差什么

## 二十、缺口清单与标准选型

> **战略前提**：Ossie 打底（L3 的 TBox 格式）；Ossie 没有的，按 **TBox/ABox 理论 + Palantir 概念**补；
> **能找现成标准/协议的，绝不自己发明。**

### 20.1 总账：Ossie 白拿了多少

| | 占比 | 说明 |
|---|---|---|
| **Ossie 直接给你** | ~5~10% | L3 的格式部分，TBox 21 项中的 12 项 |
| **需要做，但有标准/开源可参照** | ~70% | L1、L2、L4、L6、大部分切面 |

> **90% 要做，但只有一小块是"没有标准可循"的。**
> **那一小块恰好是 Palantir 的核心，也是这个系统的差异化所在。**

| **切面·审计** | ❌ | 不可变日志 | **CloudEvents**（事件格式）+ 追加写表 | 半标准 |
| **切面·版本** | ❌ | 模型/规则回滚 | 无标准；Git + 快照 | 自己写 |
| **切面·合规删除** | ❌ | 跨存储删除 | 无技术标准（**GDPR 是法规**）；可参照 Semantica 的 `ErasureCoordinator` 设计 | 自己写 |
| **切面·成本/SLA** | ❌ | 计量与承诺 | 无标准 | 自己写 |
| **切面·流程组织** | ❌ | 建模流程 | 无标准 | **非技术问题** |

### 20.3 唯一的真空区：Action 层（L5）

**这是整个系统里唯一"没有标准可循"的地方**，也是 Palantir 的核心壁垒。

**抄 Palantir 的是概念，不是实现：**

| 从 Palantir 抄什么 | 说明 |
|---|---|
| **四元组里的"动作"** | 对对象执行改变的**唯一合法入口** |
| **参数的强类型化** | 输入类型、必填、取值范围 |
| **前置条件（submission criteria）** | "谁能提交" + "什么条件下能提交" |
| **副作用声明** | 通知、webhook、触发下游 |
| **写回（write-back）** | 受控回写源系统 |
| **Action History** | 谁、何时、基于什么输入、做了什么、结果如何 |
| **"治理落在 Action 上"** | 无论谁提交（界面/API/Agent），规则一次生效 |

**但周边全部用现成标准，不要自己发明：**

| 要素 | 用什么 | 为什么 |
|---|---|---|
| 权限判定 | **OPA** 或 **Cedar** 或 **OpenFGA** | 别自己写授权引擎 |
| 跨系统可靠写回 | **Transactional Outbox** 模式 | 成熟模式，解决"改了库但没发出去" |
| 跨系统长事务 | **Saga** 模式 | 补偿事务 |
| 审批/流程编排 | **Temporal** / Cadence | 别用状态机硬写 |
| 幂等 | 幂等键 + 去重表 | 成熟做法 |
| 审计事件格式 | **CloudEvents** | 有标准，别自定义 |
| 接口描述 | **OpenAPI** | 有标准 |

**所以 Action 层的真实工作内容是：**

```
设计部分（无标准，必须自己定）：
  · Action 的抽象模型（参数/前置/执行/副作用/写回的契约）
  · 动作的注册与发现机制
  · 与 TBox（Ossie 定义）的关联方式：动作读写哪些 concept/relationship

实现部分（全部用现成）：
  · 授权 → OPA / OpenFGA
  · 编排 → Temporal
  · 可靠写回 → Outbox 模式
  · 审计 → CloudEvents + 追加写表
  · 接口 → OpenAPI + 代码生成
```

> **结论：Action 层"没有标准"指的是它的抽象模型，不是它的实现手段。**

### 20.4 权限：有成熟标准，**千万不要自己发明**

这是最容易重复造轮子的地方。四种可选模型：

| 方案 | 模型 | 适合 |
|---|---|---|
| **OPA / Rego** | 策略即代码（通用） | 规则复杂、需要集中管理策略 |
| **Cedar** | 策略语言（AWS，可形式化验证） | 需要可验证性 |
| **OpenFGA / Zanzibar** | **关系元组**（Google 论文） | ⭐ **最贴合本场景**：对象-关系-权限天然匹配 |
| **Casbin** | 访问控制模型库 | 轻量、快速起步 |

**推荐 Zanzibar 模型（OpenFGA）的理由**：它把权限表达为 `(对象, 关系, 用户)` 元组，
**与 TBox 的 relationship 结构天然同构**——你的链接类型可以直接映射成权限关系。

> Palantir 的"对象实例级 + 属性级动态权限"，本质上就是 Zanzibar 那套 + 属性推导。

### 20.5 最小可行技术组合

| 层 | 起步选型 | 理由 |
|---|---|---|
| **L3 语义定义** | **Apache Ossie**（YAML） | 白拿标准 |
| L3 定义服务 | Git + Postgres | 定义量小 |
| **L1 摄取** | 手写连接器 + **Debezium**（如需 CDC） | 起步数据源少 |
| L1 契约/质量 | 先手写校验；量大了再上 Great Expectations | 别一上来上重工具 |
| L1 身份解析 | 先规则；量大了上 **Splink** | 这层最费工 |
| **L2 存储** | **Postgres**（一张表 + 一张边表） | 图库不是必需品 |
| **L4 查询** | SQL + 递归 CTE（表达传递闭包） | Postgres 能扛很久 |
| L4 推理 | 自己写不动点循环（几个性质而已） | 别上通用推理机 |
| **L5 动作** | **自己写**（API 层 + 审计表） | 核心，必须自己做 |
| L5 权限 | **OpenFGA** | Zanzibar 模型天然匹配 |
| L5 编排 | 先直写；需要审批流再上 **Temporal** | 别提前引入 |
| **L6 Agent** | **MCP** | 事实标准 |
| L6 只读 | Superset / Metabase | 别自己写 BI |

### 20.6 分阶段路线

**阶段一：跑通一条链路（最小闭环）**

```
Ossie 定义 3~5 个概念  →  手工灌几条数据  →  SQL 查询
      →  1 个 Action（自己写）  →  1 个 MCP 工具
```
目标：**证明"定义 → 数据 → 查询 → 动作 → Agent"这条链是通的**。

**阶段二：补治理**

```
数据契约 + 拒收区 + 身份解析（先用规则）
```
目标：**数据能持续进来而不变脏**。

**阶段三：补权限与审计**

```
OpenFGA + 审计表 + CloudEvents
```
目标：**能对外承诺"谁做了什么有记录、有管控"**。

**阶段四：规模化**

```
CDC + 列存 + 图库（如需要）+ 规则引擎 + 流程引擎
```
目标：**量上来了才换，别提前。**

### 20.7 一句话总结

> **用了 Ossie，L3 的格式白拿了；剩下 90% 要做，但其中 80% 有标准或开源可参照。
> 真正需要自己设计的只有一块：Action 的抽象模型。
> 而它的实现手段（权限、编排、可靠写回、审计、接口）全都有现成标准。**

**这就是"仿造 Palantir"的实际工作量分布：不是 90% 都要发明，是 10% 要发明、80% 要组装、10% 白拿。**

【理论底座】TBox（术语，"允许什么"） / ABox（断言，"实际是什么"）

【六层 · 运行时视图】（自下而上，上层定义并驱动下层）

  两条流：ABox 数据流自下而上 ｜ TBox 定义流自上而下
