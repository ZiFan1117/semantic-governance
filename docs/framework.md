# 第零部分 · 理念与定位

---

## 0. 语义治理是什么

### 0.1 问题陈述

**现状**：企业的业务语义散落在应用代码、报表定义、数仓模型、文档里。后果是——

- 同一个"客户"在四个系统里四个定义
- 同一个"营收"在四个看板里四个数字
- AI 拿到互相冲突的业务逻辑，只能胡说
- 想改一个规则，要改几十个地方，还改不全

**Palantir 的解法**：把业务语义抽出来，做成一层**可声明、可校验、可执行、可交换的契约**，
让所有读写都必须经过它。**但这个解法是专有的。**

**本框架要给出一个通用、公开、可开源的等价物。**

### 0.2 为什么叫「语义治理」而不是「本体论」

| 词 | 隐含的重心 | 问题 |
|---|---|---|
| 本体论 | **建模** | 听起来像学术活动，做完就完了 |
| 知识图谱 | **数据** | 听起来像存储选型 |
| Palantir Ontology | **产品** | 专有 |
| **语义治理** | **权责 + 契约 + 技术** | ✅ 点出了"这是一件持续治理的事" |

**"治理"三个字要求框架必须回答：谁有权定义、怎么改、有分歧怎么办、怎么退出。**

> **如果一个叫"语义治理"的框架不回答这些问题，它名不副实。**
>
> 这是 v0.1 最大的缺陷——它把治理当成了技术机制（约束/权限/审计），
> 而那些只是治理的**执行手段**，不是治理本身。

### 0.3 核心命题

> **把业务语义从应用代码里抽出来，做成一份可声明、可校验、可执行、可交换的权威契约；
> 规定六个接口，让所有读写都必须经过它；
> 并用一套治理机制保证这份契约能持续演进而不失控。**

### 0.4 范围

| 管 | 不管 |
|---|---|
| 语义的**声明格式** | 具体行业的本体内容 |
| 语义与数据的**映射** | 物理存储实现 |
| 约束的**表达** | 推理算法选型 |
| 动作的**契约** | 具体动作的业务逻辑 |
| 层间的**接口** | 各层的产品选型 |
| **治理机制** | 商业模型、部署形态 |
| **合规等级** | 组织内部的政治 |

### 0.5 【关键】形态选择：中央式权威及其代价

**本框架采用中央式：一套权威语义，所有系统向它对齐。**

**它给你什么：**

| 收益 | 说明 |
|---|---|
| **强一致** | 一处改，处处生效；不存在"你的客户"和"我的客户" |
| **无歧义** | 只有一个"营收"的定义 |
| **可治理** | 有明确的权责主体，能追责 |
| **可推理** | 全局闭包可算，不存在跨域的语义断层 |

**它要你放弃什么——必须说清，这是本框架最重要的诚实：**

| 放弃的 | 说明 |
|---|---|
| ❌ **"任何人都能改核心"** | 不可能。改核心要提案、要评审、要公示 |
| ❌ **域之间的完全自治** | 各域必须向核心对齐，不能各说各话 |
| ⚠️ **中央成为瓶颈** | 核心团队的能力决定全局；核心改动要排队 |
| ⚠️ **中央成为风险点** | 核心定义出错，影响所有消费者 |

**所以本框架的"开放"具体指什么：**

| ✅ 开放的 | ❌ 不开放的 |
|---|---|
| 规范本身（开源、任何人可自由实现） | **核心定义的直接修改权** |
| 提案权（任何人可提变更提案） | |
| 扩展命名空间（域内自定义，不受核心约束） | |
| **分叉权**（可 fork 核心，另立门户） | |
| **退出权**（可导出全部定义与事实并离开） | |

> **一句话：开放的是「加入、提案、分叉、退出」，不是「就地修改」。**

**这不是妥协。这是所有成功标准的共同形态：**

| 标准 | 提案 | 权威 |
|---|---|---|
| IETF | 任何人可提 Internet-Draft | 集中（IESG/IAB 批准） |
| W3C | 任何人可提 | 集中（工作组 + 会员投票） |
| Kubernetes | 任何人可提 KEP | 集中（SIG + TOC 批准） |
| **本框架** | 任何人可提变更提案 | **集中（治理机构批准）** |

> **"提案开放 + 权威集中"是唯一被验证过能同时做到"开放"和"稳定"的形态。**
>
> 而那些试图做到"谁都能改"的尝试（语义网的全球共享本体），**全部失败了**。

> **v0.2 把治理提升为第一部分。因为对一个叫"语义治理"的框架，这是主体，不是附录。**

## 1. 治理的六件事

### 1.1 命名空间与权威（谁的地盘）

**核心设计：分层命名空间。**

```
urn:sem:<authority>:<domain>:<concept>
         ↑           ↑         ↑
      权威机构      域        概念
```

| 命名空间层 | 谁有权定义 | 变更流程 |
|---|---|---|
| **核心层** `urn:sem:core:*` | 治理机构 | **正式提案 + 评审 + 弃用期** |
| **领域层** `urn:sem:<org>:*` | 组织/域的建模负责人 | 内部评审 |
| **扩展层** `urn:sem:<org>:<domain>:ext:*` | 任何消费者 | **自由定义，无需批准** |
| **本地层**（不进标准） | 单个应用 | 随意 |

**规则：**

- **核心层 MUST 极简**——只放跨域必需的概念（客户、组织、时间、金额……）。
  **核心层越胖，治理成本越高，且越容易变成瓶颈。**
- **扩展层是安全阀**——想让所有人都改核心的冲动，应该被引导到扩展层
- **跨层引用只能向上，不能向下**：扩展层可引用核心层；核心层 MUST NOT 引用任何扩展层

### 1.2 变更流程

```
① 提案     任何人可提（不限身份）
   ↓
② 影响分析  自动算出：影响哪些概念、哪些消费者、哪些动作
   ↓
③ 公示期    至少 N 天（核心层 N 大，扩展层 N=0）
   ↓
④ 评审      治理机构 / 域主
   ↓
⑤ 发布      新版本号；旧版本进入弃用期
   ↓
⑥ 弃用      弃用期结束才可移除
```

**三条硬规则：**

| # | 规则 | 为什么 |
|---|---|---|
| **H1** | **定义一经发布即不可原地修改** | 否则无法回溯、无法追责 |
| **H2** | **破坏性变更 MUST 有弃用期** | 否则消费者会被静默打断 |
| **H3** | **变更必须能算出影响面** | 否则治理是盲的 |

### 1.3 争议解决

**当两个人对同一个概念有不同意见：**

| 情形 | 解法 |
|---|---|
| 命名冲突（都想叫"客户"） | 命名空间隔离 → 各自用全限定名 |
| 语义冲突（"客户"含义不同） | **必须拆成两个概念**，不能强行统一 |
| 粒度冲突（一个要粗一个要细） | 细的为基，粗的用派生规则算出来 |
| 无法调和 | **分叉**（见 1.5） |

**原则：**

> **共识是"谈"出来的，不是"统一"出来的。**
> **强行统一两个不同的概念，是语义治理中最常见的错误。**

### 1.4 版本与兼容性

| 变更类型 | 兼容性 | 处理 |
|---|---|---|
| 新增概念 / 关系 | ✅ 向后兼容 | 小版本号 |
| 新增可选属性 | ✅ 兼容 | 小版本号 |
| 新增必填属性 | ⚠️ **破坏性** | 弃用期 + 大版本号 |
| 删除 | ❌ **破坏性** | 弃用期 + 大版本号 |
| 改语义（同名不同义） | ❌ **欺骗性** | **MUST NOT** —— 必须新建概念 |
| 改约束 | ⚠️ 视情况 | 影响分析 |

> **"改语义但保留名字"是最危险的变更——它让所有消费者静默出错。**

### 1.5 分叉与退出（**最容易被忽略，也最重要**）

**没有退出权的标准是枷锁，不是标准。**

| 权利 | 怎么保证 |
|---|---|
| **分叉权** | 全部定义以**开放格式**提供（Ossie YAML）——任何人可 fork |
| **退出权** | MUST 提供**完整导出**：定义 + 事实 + 血缘 + 审计 |
| **回归权** | 分叉后仍可提交提案回来 |

**MUST 提供导出，且导出格式 MUST 可独立于本实现使用。**

### 1.6 权责矩阵

| 事 | 谁负责（R） | 谁批准（A） | 谁咨询（C） | 谁知会（I） |
|---|---|---|---|---|
| 核心概念新增 | 提案人 | 治理机构 | 消费者代表 | 全体 |
| 核心概念修改 | 提案人 | 治理机构 | 消费者代表 | 全体 |
| 领域概念 | 域建模负责人 | 域主 | 域内消费者 | 治理机构 |
| 扩展概念 | 任何人 | 无需 | — | — |
| 动作定义 | 域建模负责人 | 域主 + 安全负责人 | 审计 | 治理机构 |
| 权限模型 | 安全负责人 | 安全负责人 | 域主 | 审计 |

## 2. 三类角色与权责

| 角色 | 干什么 | 关心什么 |
|---|---|---|
| **治理机构**（中央） | 维护核心层、批准变更、解决争议 | 长期稳定性、跨域一致性 |
| **域主**（Domain Owner） | 维护本域概念、审批本域变更 | 本域业务的准确性、变更成本 |
| **消费者** | 使用语义、提交提案 | 别被破坏性变更打断 |

**⚠️ 反模式：把治理机构变成"审批机器"。**

> 如果所有变更都要中央批，中央就成了瓶颈，各域会绕过它自己搞——
> **这正是一切中央式治理失败的路径。**
>
> **解法：扩展层无需批准（安全阀）+ 核心层极简（减少必须走流程的量）。**

## 3. 三种剖面（Profile）

**v0.1 的错误：用一套要求覆盖所有用途。但三种用途的需求差别极大。**

| | **Profile A · 轻量** | **Profile B · 组织** | **Profile C · 严格** |
|---|---|---|---|
| **适用** | Agent 记忆库、个人知识 | 部门数据治理、单组织多系统 | 跨系统权威语义、受监管场景 |
| **语义稳定性** | 低（随时改） | 中 | 高 |
| **消费者** | 1 个 | 几个人 | 多系统多团队 |
| **命名空间** | 只用扩展层/本地 | 领域层 + 扩展层 | **核心层 + 领域层 + 扩展层** |
| **变更流程** | 无需提案 | 内部评审 | **正式提案 + 公示 + 弃用期** |
| **必须实现** | I1 + I2 + I3 | + I4 + 审计 | **全部六个接口 + 全部治理机制** |
| **合规等级** | L0~L1 | L0~L3 | L0~L4 |
| **典型规模** | 单机 | 单组织 | 跨组织 |

**判定规则：**

```
只有一个消费者，且语义可随时改         → Profile A
多个消费者，但都在一个组织内           → Profile B
跨组织 / 受监管 / 改动会影响外部系统    → Profile C
```

> **⚠️ Profile 是"当前状态"，可以升级。**
> **记忆库长成了部门资产，就该升到 B。**

## 4. 术语表

> **标准的第一件事是统一术语。以下 12 个词在本框架内有且仅有以下含义。**

| # | 术语 | 英文 | 定义 | 例子 |
|---|---|---|---|---|
| 1 | **域** | Domain | 一个独立的语义空间（限界上下文）。**一切从域开始** | 供应链域、财务域 |
| 2 | **概念** | Concept | 一类业务对象 | 订单、客户、设备 |
| 3 | **属性** | Property | 概念的字段 | 订单金额、下单时间 |
| 4 | **关系** | Relation | 概念之间的**类型化连接** | 订单—属于→ 客户 |
| 5 | **角色** | Role | 关系中的位置 | 关系「运输」有角色：起运地、目的地 |
| 6 | **基数** | Multiplicity | 角色的数量约束 | 一个订单最多一个客户 |
| 7 | **约束** | Constraint | 对实例或事实的**合法性要求** | 金额必须为正 |
| 8 | **派生** | Derivation | 由其他事实**推出**的事实 | 祖先是父的传递闭包 |
| 9 | **实例** | Instance | 一个具体的业务对象 | 订单 #12345 |
| 10 | **事实** | Fact | 实例之间的连接，或实例的属性值 | 订单 #12345 属于客户 acme |
| 11 | **动作** | Action | 对实例的**受控修改** | 取消订单、发放优惠券 |
| 12 | **视图** | View | 对事实的查询结果（**不落库**） | "api 的所有上游依赖" |

**三个容易混的点：**

| 容易混 | 区别 |
|---|---|
| 概念 vs 实例 | 概念是"订单这一类"，实例是"订单 #12345 这一个" |
| 属性 vs 关系 | 属性指向**值**（金额=100），关系指向**另一个实例**（属于客户 acme） |
| 事实 vs 视图 | 事实是**存下来的**，视图是**算出来的** |

## 5. 六个可声明原语

> **"可声明"= 可以写进契约文件的东西。** 其余（实例、事实）是运行时的。

| # | 原语 | 声明什么 | 理论归属 | Ossie 对应 |
|---|---|---|---|---|
| 1 | **概念** | 有哪些类东西、层次、接口 | TBox | `concept`、`extends`、`type` |
| 2 | **关系** | 类之间怎么连（角色、基数、方向） | TBox | `relationships`、`roles`、`multiplicity` |
| 3 | **约束** | 什么合法 | TBox | `requires` |
| 4 | **派生** | 什么能推出来 | TBox | `derived_by`（支持递归） |
| 5 | **动作** | 允许怎么改、带什么条件、连带动什么 | TBox↔ABox | ❌ **Ossie 没有** |
| 6 | **映射** | 物理数据怎么变成概念和事实 | TBox→ABox | ontology mappings |

```
     映射 ──────────→ 概念 ──→ 实例
     （怎么进来）      ↑        （是什么）
                      │
                    关系 ──→ 事实
                      ↑        （怎么连）
                      │
        约束 ─────────┘  派生
        （什么合法）      （能推出什么）

     动作 ──→ 受控地产生新的实例和事实
     （怎么改）
```

**Ossie 覆盖前四个 + 映射；第 5 个（动作）是空白——这是本框架的原创部分。**

---

## 6. 理论根基：TBox / ABox

| | **TBox** | **ABox** |
|---|---|---|
| 装什么 | 概念、关系、公理、约束 | 实例、具体事实 |
| 回答 | **"允许什么"** | **"实际是什么"** |
| 变更频率 | 低 | 高 |

### 6.1 三条关系（全部机制的理论来源）

| 关系 | 含义 | 对应能力 |
|---|---|---|
| **① 约束** | TBox 规定 ABox 里什么合法 | **校验** |
| **② 推理** | TBox 公理在 ABox 上求闭包 | **推理** |
| **③ 撤回** | 撤掉一条事实，依赖它的派生结论要失效 | **真值维护** |

### 6.2 由理论推导出的两个关键结论

**结论 1：为什么必须有"动作层"**

> TBox 第 ① 条关系是"约束"——它要求 ABox 只能装合法的事实。
> **那么"往 ABox 里写"这个动作，就必须过 TBox 这道关。**
>
> 这是动作层存在的**理论理由**，而非"因为 Palantir 有 Action"。

**结论 2：为什么"概念"和"存储"必须分层**

> TBox 与 ABox 生命周期不同（一个低频、一个高频），
> 且同一份 ABox 可以有多种 TBox 投影。
> 混在一起，改一个定义就要动数据。

## 7. 六层架构

```
        ╔══════════════════════════════════════════════════╗
        ║  外部：数据源（ERP/CRM/数仓/API/流）  ← 入站      ║
        ╚═══════════════════════╤══════════════════════════╝
                                │  I5 接入接口
┌───────────────────────────────┴──────────────────────────┐
│ L6  消费层     人 / Agent / 外部系统                      │
├──────────────────────────────────────────────────────────┤
│ L5  动作层     受控修改         ┌────────────────────────┼──→ 写回外部（出站）
│                                │ 一致性读路径（见 §8）   │
├────────────────────────────────┴─────────────────────────┤
│ L4  查询层     读取、遍历、推理                           │
├──────────────────────────────────────────────┬───────────┤
│ L3  语义层     = TBox 的载体（权威契约）      │           │
├──────────────────────────────────────────────┤  I1/I2    │
│ L2  事实层     = ABox 的载体                 │  语义接口 │
├──────────────────────────────────────────────┴───────────┤
│ L1  接入层     把外部数据变成合法事实                     │
└──────────────────────────────────────────────────────────┘
```

| 层 | 理论身份 | 一句话 | 关键问题 |
|---|---|---|---|
| **L1 接入** | ABox 的构建过程 | 把外部数据变成合法事实 | 数据不脏 |
| **L2 事实** | ABox 的载体 | 事实存在哪、怎么存得快 | 快 |
| **L3 语义** | TBox 的载体 | 允许什么（**权威**） | 统一语言 |
| **L4 查询** | TBox 在 ABox 上求值 | 能问出什么、能推出什么 | 问得出来 |
| **L5 动作** | TBox 约束 ABox 的关卡 | 能安全地改什么 | **安全地改** |
| **L6 消费** | 消费方 | 谁在用 | 用得上 |

## 8. 三条流（含修正后的 L5 读路径）

| 流 | 方向 | 内容 |
|---|---|---|
| **① 定义流（TBox）** | **自上而下** | L3 的定义驱动 L1 按什么形状抽、L2 按什么类型索引 |
| **② 数据流（ABox）** | **自下而上** | 数据源 → L1 → L2 → L4/L5 → L6 |
| **③ 控制流** | **横切** | L5 通过**专用一致性读路径**访问 L2 |

### 8.1 ⚠️ 修正：L5 的读路径（v0.1 的错误）

**v0.1 的说法**：「L5 直调 L2，不经过 L4」。

**这个说法是错的**，因为动作的前置条件需要读当前状态，而它必须：

| 需求 | 为什么 | "直调 L2"能满足吗 |
|---|---|---|
| **事务内一致读** | 读到的状态必须和执行时的状态一致，否则前置条件失效 | ⚠️ 不一定 |
| **能读到派生事实** | 前置条件常需派生值（"客户订单总额"） | ❌ 不能（派生不在 L2） |
| **带权限上下文** | 读本身也要受权限约束 | ❌ 不能（L2 不认识权限） |

**修正后的设计：L5 使用一条专用的「一致性读路径」**

```
L5 动作层
   │
   ├─→ 一致性读路径（专用）
   │     · 事务内快照读（保证前置条件与执行同源）
   │     · 可读派生事实（在事务快照上现算）
   │     · 带调用者权限上下文
   │
   └─→ 写入路径（经 I2）
         · 写前过约束校验
         · 写后记审计
```

**这条路径 MUST 满足：**

| # | 要求 | 理由 |
|---|---|---|
| **R1** | **快照一致** | 前置条件读到的状态 = 执行时的状态 |
| **R2** | **可读派生** | 否则写不出"总额超限"这类前置条件 |
| **R3** | **带权限上下文** | 否则动作能读到调用者无权看的数据 |
| **R4** | **不产生副作用** | 它只是读，不能触发任何写 |

> **v0.1 把这个难点简化成"直调 L2"，掩盖了真实的设计复杂度。**

### 8.2 ⚠️ 未解决的冲突：派生不落库 vs 前置条件

**这是一个真实的、本框架尚未解决的冲突：**

- 保证 I2-G4 说"派生事实不落库"
- 但前置条件经常需要派生事实（R2）
- 于是每次动作提交都要**在事务内现算闭包**

**后果：**

| 问题 | 说明 |
|---|---|
| **性能** | 事务内算不动点，可能超时 |
| **正确性** | 算到一半规则变了怎么办 |
| **成本** | 高频动作场景下不可接受 |

**候选解法（尚无定论，见 §24）：**

1. **限定深度**——只允许有限深度的派生参与前置条件
2. **物化 + 版本**——对高频用到的派生值做物化，绑定定义版本
3. **前置条件改写**——把派生条件改写成对基础事实的条件（不总是可行）
4. **两阶段**——先在快照上算派生，再进事务校验（有窗口期）

# 第四部分 · 接口视图 ★核心

> **模块之间靠什么对话。这一部分是本框架真正的"标准"内容——分层是描述，接口才是约束。**

---

## 9. 五个接口 + 一个能力

| # | 名称 | 谁调谁 | 方向 | 契约核心 | 现有标准 |
|---|---|---|---|---|---|
| **I1** | **语义接口** | 所有层 → L3 | 读 | 读定义，定义不可变 | ✅ **Ossie** |
| **I2** | **事实接口** | L4/L5 → L2 | 读+写 | **写入必须过约束** | ⚠️ GQL（半覆盖） |
| **I3** | **查询接口** | L6 → L4 | 读 | **结果必须可追溯** | ⚠️ MCP（半覆盖） |
| **I4** | **动作接口** | L6 → L5 | 写 | **全套待定义** | ❌ **无** |
| **I5** | **接入接口** | 外部 → L1 | 入 | 契约先于数据 | ✅ **ODCS** |
| **I6** | **发现能力** | 任何方 → 全域 | 读 | **不知道有什么时能列出来** | ❌ 无（v0.2 新增） |

**一句话看懂：**

> **六个接口里，两个有完整标准（I1、I5），两个需要补一条关键约束（I2、I3），
> 两个需要原创（I4、I6）。**
>
> **要发明的只有两个，其余全是选型和组合。**

---

## 10. I1 语义接口

**方向**：只读（定义由治理流程写）

| 操作 | 输入 | 输出 |
|---|---|---|
| `GetConcept(name)` | 概念名 | 属性、层次、接口、约束 |
| `ListRelations(concept)` | 概念名 | 该概念下的关系（含角色、基数） |
| `GetConstraints(target)` | 概念/关系名 | 适用的约束表达式 |
| `GetDerivations(target)` | 概念/关系名 | 派生规则 |
| `GetActions(concept)` | 概念名 | 可对该概念执行的动作 |
| `GetMappings(concept)` | 概念名 | 字段 → 概念的映射规则 |
| `GetVersion()` | — | 当前定义版本 |
| `Diff(v1, v2)` | 两个版本 | 差异（供影响分析用） |

**保证：**

| # | 保证 | 为什么重要 |
|---|---|---|
| **G1** | **定义不可变** | 一经发布只能新增版本，不能原地改 → 让回溯和撤回成为可能 |
| **G2** | **读取一致** | 同一次操作内读到的定义来自同一版本 |
| **G3** | **可自检** | 定义本身可被校验（环、悬空引用、冲突） |
| **G4** | **可差异对比** | 任意两版本可算出差异 → 影响分析的前提 |

**格式**：定义态用 **Apache Ossie YAML**；运行态 API 各实现自定，但 MUST 满足 G1~G4。

---

## 11. I2 事实接口

**方向**：读 + 写（写仅限 L5）

| 操作 | 调用方 | 说明 |
|---|---|---|
| `GetInstance(concept, id)` | L4/L5 | 取一个实例 |
| `ListFacts(pattern)` | L4 | 按模式取事实 |
| `WriteFact(fact)` | **仅 L5** | 写入一条事实 |
| `DeleteFact(fact)` | **仅 L5** | 删除一条事实 |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **G1** | **写入必须过约束** ⭐ | 任何写入必须已通过 L3 约束校验，失败即拒绝且**无副作用** |
| **G2** | **写入必须带来源** | 记录从哪来（哪个动作 / 哪个数据源） |
| **G3** | **只有 L5 能写** | L4、L6 一律只读——**本框架的硬约束** |
| **G4** | **派生事实不落库** | 推出的结论是视图，不是事实 |

### 11.1 ⚠️ 这里需要补的约束

> **GQL / Cypher 定义了"怎么写"，但没有定义"写入必须过约束"。**
>
> **本框架在 GQL 之上加一条：任何 `WriteFact` 必须原子地包含约束校验，失败即拒绝。**
>
> 这一条把图数据库从"能写的存储"变成"**受治理的事实层**"。

---

## 12. I3 查询接口

**方向**：只读

| 操作 | 说明 |
|---|---|
| `Query(pattern)` | 按模式查事实 |
| `Traverse(from, relation, depth)` | 多跳遍历 |
| `Infer(query)` | 含派生事实的查询 |
| `Search(text)` | 向量 / 全文检索，返回入口实例 |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **G1** | **只读** | 查询接口**永不产生写入** |
| **G2** | **可追溯** ⭐ | 每条返回的事实必须带来源：是存的，还是推出来的；推出来的依据是什么 |
| **G3** | **权限过滤** | 结果必须已按调用者权限过滤 |
| **G4** | **预算可限** | 支持限制返回量（节点数 / token 数）——**为 Agent 设计** |

### 12.1 ⚠️ 这里需要补的约束

> MCP 定义了"怎么把工具暴露给 Agent"，**但没有定义"结果必须可追溯"**。
>
> **本框架加一条：`Infer` 的每条派生结果 MUST 带 `via` 字段，标明由哪条规则、从哪几条事实推出。**
>
> **这是让 LLM 的结论可验证的关键**——它必须能引用具体事实，而不是只给结论。

**实现示例（`dsh-ontology` 的做法）：**

```
api depends_on pg (inferred: transitive)
                      ↑ via 字段
```

## 13. I4 动作接口

**方向**：写 · **现有标准**：❌ 无

> **本框架唯一需要原创设计的核心部分。**

> 📄 **实现规范见 [`spec/i4-action-minimal.md`](../spec/i4-action-minimal.md)（v0.1）。**
>
> 该规范刻意收窄范围：**单实例 · 同步 · 无副作用 · 有审计**。
> 多实例事务、异步、副作用、补偿留给 v0.2 / v0.3。
> **本节以下内容是设计要素清单；具体条款以该规范为准。**

### 13.1 动作的描述格式（静态）

| 要素 | 说明 |
|---|---|
| 标识 | 动作名、所属域、命名空间 |
| **作用对象** | 读写哪些概念 / 关系（**与 L3 定义的关联**） |
| **参数** | 名称、类型、是否必填、取值范围 |
| **前置条件** | 什么状态下允许执行 |
| **副作用** | 会触发什么（通知 / webhook / 触发下游） |
| **写回目标** | 是否回写外部系统，回写到哪 |
| **幂等性** | 是否幂等；非幂等时幂等键怎么取 |
| **权限** | 谁能执行（可基于属性动态推导） |

### 13.2 提交的语义（动态）

| 要素 | 待定义 |
|---|---|
| 同步 / 异步 | 什么时候返回？长动作怎么处理 |
| **事务边界** | 涉及多个实例时，原子性范围是什么 |
| **幂等键** | 重复提交怎么识别 |
| **失败语义** | 拒绝（全无副作用）／部分成功（怎么补偿）／补偿（Saga） |
| **并发** | 两个动作同时改同一实例，怎么办 |

### 13.3 审计记录的格式

每次提交 MUST 产生一条不可变记录：

```
谁 · 何时 · 提交了哪个动作 · 参数是什么
· 基于什么（读取了哪些事实）· 结果如何 · 副作用有哪些 · 是否可回滚
```

> **"基于什么"这一项最关键**——它是"为什么批准/拒绝了这笔操作"的答案，也是合规审计的核心。

### 13.4 拒绝的格式（**为 Agent 而设计**）

拒绝 MUST 说清违反了哪条约束：

```
REJECTED cancel_order(order:12345)
  原因：前置条件不满足
  违反：order:12345 的状态为「已发货」，而 cancel_order 要求「未发货」
  依据：约束 Constraint#17「已发货订单不可取消」
  建议：可执行 return_order 走退货流程          ← 可选，但对 Agent 极有价值
```

> **这一条是"可用性"的关键**——人看到报错会去问人，**Agent 只能靠自己重试**，
> 所以拒绝信息必须**足以让它自己纠正**。

### 13.5 周边全部用现成标准

| 要素 | 用什么 | 标准 / 模式 |
|---|---|---|
| 接口描述 | **OpenAPI** | 有标准 |
| 权限判定 | **OpenFGA**（Zanzibar 模型） | 有标准 |
| 策略表达 | **OPA / Rego** 或 **Cedar** | 有标准 |
| 跨系统可靠写回 | **Transactional Outbox** | 成熟模式 |
| 跨系统长事务 | **Saga** | 成熟模式 |
| 审批 / 编排 | **Temporal** / Cadence | 有实现 |
| 审计事件格式 | **CloudEvents** | 有标准 |
| 幂等 | 幂等键 + 去重表 | 成熟做法 |

> **I4 的工作量 = 定义抽象模型（10%）+ 组装现成组件（90%）。**

### 13.6 为什么权限天然匹配

| 本框架 | OpenFGA |
|---|---|
| 概念 | `type` |
| 关系 | `relation` |
| 实例 | `object` |
| 事实 | `relationship tuple` |

**推论：授权模型可以从 L3 的定义自动生成，且"权限沿业务关系继承"是原生的。**

## 14. I5 接入接口

**方向**：入

| 操作 | 说明 |
|---|---|
| `DeclareContract(source)` | 声明数据源的数据契约 |
| `ValidateContract(source)` | 校验上游是否满足契约 |
| `Ingest(source, mode)` | 摄取（增量 / 全量） |
| `Quarantine(badRecords)` | 拒收不合规记录 |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **G1** | **契约先于数据** | 没有契约的数据源不得接入 |
| **G2** | **不合规即拒收** ⭐ | **绝不自动清洗**——隔离等人来修 |
| **G3** | **拒收可解释** | 说清违反了契约的哪一条 |
| **G4** | **身份先于属性** | 实例身份必须能稳定解析 |

### 14.1 最强的一条原则

> **不指望数据干净，指望入口干净。**
>
> **不合规的数据不是"清洗掉"，是"隔离出来逼人解决"。**
> 自动清洗是错误放大器——它把业务问题藏起来，而且越藏越深。

**格式**：**ODCS（Open Data Contract Standard，Bitol / Linux Foundation）**——直接采用。

## 15. I6 发现能力（v0.2 新增）

**方向**：只读 · **现有标准**：❌ 无

**v0.1 的缺陷**：只有"已知名字去查"（`GetConcept(name)`），
**没有"我不知道有什么，先列一遍"**。

**为什么这是刚需：**

| 场景 | 需要什么 |
|---|---|
| 新系统接入 | 有哪些域？各提供什么？ |
| 新 Agent 上线 | 我能用什么概念、什么动作？ |
| 跨域对接 | 对方的"订单"和我的能不能对上？ |
| 影响分析 | 改这个概念会影响谁？ |

| 操作 | 说明 |
|---|---|
| `ListDomains()` | 列出所有域 |
| `ListConcepts(domain, filter)` | 列出概念（可按标签/关键词过滤） |
| `ListActions(concept)` | 列出可用动作 |
| `DescribeCapability(name)` | 描述一个能力的完整契约 |
| `FindByCapability(need)` | **按需求找能力**（"我需要一个能取消订单的动作"） |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **G1** | **可枚举** | 域、概念、动作必须可被完整列出 |
| **G2** | **权限过滤** | 只列出调用者有权知道的 |
| **G3** | **自描述** | 发现的结果本身符合标准格式 |

> **在中央式架构里，发现机制是"对齐"的入口——新系统靠它知道该向什么对齐。**

## 16. 接口 × 现有标准对照

| 接口 | 直接采用 | **本框架需要补的** |
|---|---|---|
| **I1 语义** | **Ossie YAML** | 运行态 API 四条保证（G1~G4） |
| **I2 事实** | **GQL**（ISO/IEC 39075:2024） | ⭐ **写入必须过约束**；只有 L5 能写 |
| **I3 查询** | **MCP** | ⭐ **结果必须可追溯**（`via` 字段）；预算可限 |
| **I4 动作** | OpenAPI / OpenFGA / Outbox / Saga / CloudEvents | ⭐ **抽象模型全套** |
| **I5 接入** | **ODCS** | 拒收区与身份解析的实现约定 |
| **I6 发现** | — | ⭐ **能力模型全套** |

**这就是本框架的"贡献清单"：**

> **两条必须补的约束（I2-G1、I3-G2）**
> **两个必须原创的模型（I4、I6）**
> **其余全是选型和组合。**

# 第六部分 · 合规等级

---

## 18. 五级阶梯 × 三种剖面

```
Level 4  可运营   + 全部切面（合规删除、成本、SLA、治理流程）
   ↑
Level 3  可治理   + 授权 + 审计 + 版本
   ↑
Level 2  可写     + 动作接口（I4）          ← ⭐ 分水岭
   ↑
Level 1  可读     + 事实 + 查询 + 发现接口
   ↑
Level 0  可声明   + 语义接口（I1）           ← Ossie 已给
```

| Profile | 目标等级 | 必须实现 |
|---|---|---|
| **A · 轻量** | L0 ~ L1 | I1 + I2 + I3 |
| **B · 组织** | L0 ~ L3 | + I4 + I6 + 审计 |
| **C · 严格** | L0 ~ L4 | **全部六个接口 + 全部治理机制** |

> **Level 1 → 2 是分水岭：以下只能"看"，以上才能"安全地改"。**
> **绝大多数开源方案停在 Level 1。**

---

## 19. 验收标准

| 级别 | 必须满足 | 验收方法 |
|---|---|---|
| **L0** | 能用 Ossie YAML 描述本域概念、关系、约束、派生 | 通过 Ossie 校验器 |
| **L1** | 按 I1 读定义；按 I2 读事实；按 I3 查询（含派生，带 `via`）；按 I6 发现 | 给定事实集，能答出派生问题并给出依据 |
| **L2** | 按 I4 提交动作；**写入必须过约束**；拒绝可解释 | ✅ **"该被拒绝的样本集"全部被拒，且拒绝原因正确** |
| **L3** | 授权 + 审计 + 版本 | 能回答"谁在何时基于什么做了什么"；能回滚定义 |
| **L4** | 合规删除 + 成本计量 + SLA + **治理流程** | 能执行一次跨存储实体删除并验证无残留；能跑通一次变更提案 |

### 19.1 最便宜也最有效的验收方法

> **建一个"该被拒绝的样本集"：收集 100 条应该被系统拒掉的数据/操作**
> （非法关系、超范围值、无权限、会形成环……），做成测试，每次改规则跑一遍。

**同时做到三件事：**

1. 验证规则没写错
2. 验证拒收真的生效（不只是写在文档里）
3. 防止改规则时把原来能拒的搞坏了（回归测试）

**这是 L2 验收的核心手段，几乎零成本。**

### 19.2 加规则的安全姿势

```
第 1 步：新规则写成"只记录，不拦截"
第 2 步：跑一段时间，看它会拒掉什么
第 3 步：人工审这份"本该被拒"的清单
        ├─ 都是真该拒的 → 改成强制拦截
        └─ 有误伤的   → 先修规则，别上线
第 4 步：上线，保留清单做回归测试
```

## 20. MUST / MUST NOT / SHOULD 清单

### 20.1 治理

| # | 条款 |
|---|---|
| G-1 | 每个定义项 **MUST** 属于某个命名空间 |
| G-2 | 定义一经发布 **MUST NOT** 被原地修改，变更 **MUST** 产生新版本 |
| G-3 | 改变语义时 **MUST** 新建概念，**MUST NOT** 复用旧名 |
| G-4 | 破坏性变更 **MUST** 提供弃用期 |
| G-5 | 核心层定义 **MUST** 支持完整导出，格式 **MUST** 独立于实现 |
| G-6 | 变更 **MUST** 可自动计算影响面 |
| G-7 | 核心层 **MUST NOT** 引用任何扩展层 |

### 20.2 I1 语义接口

| # | 条款 |
|---|---|
| I1-1 | **MUST** 支持按版本读取定义 |
| I1-2 | **MUST** 提供定义自检（环、悬空引用、冲突） |
| I1-3 | **MUST** 支持任意两版本的差异对比 |
| I1-4 | 同一次操作内 **MUST** 读到同一版本的定义 |

### 20.3 I2 事实接口

| # | 条款 |
|---|---|
| I2-1 | 所有写入 **MUST** 经过约束校验；校验失败 **MUST** 拒绝且**无副作用** |
| I2-2 | **MUST NOT** 允许 L4、L6 执行写操作 |
| I2-3 | 每条事实 **MUST** 记录来源 |
| I2-4 | 派生事实 **MUST NOT** 被持久化 |

| # | 条款 |
|---|---|
| I3-1 | 查询 **MUST NOT** 产生任何写入 |

| I3-4 | **SHOULD** 支持返回量的预算限制 |

### 20.5 I4 动作接口

| # | 条款 |
|---|---|

| I4-4 | 审计记录 **MUST** 包含"基于哪些事实" |
| I4-5 | 拒绝 **MUST** 说明违反的具体约束条款 |
| I4-6 | **MUST** 支持幂等键 |
| I4-7 | 动作的读 **MUST** 使用满足 §8.1 R1~R4 的一致性读路径 |
| I4-8 | **SHOULD** 在拒绝时提供纠正建议 |
| I4-9 | **SHOULD** 支持长事务的补偿（Saga） |

### 20.6 I5 接入接口

| # | 条款 |
|---|---|
| I5-1 | **MUST** 契约先于数据 |
| I5-2 | 不合规数据 **MUST** 被拒收，**MUST NOT** 被自动清洗 |
| I5-3 | 拒收 **MUST** 说明违反的契约条款 |

| # | 条款 |
|---|---|

# 第八部分 · 实施指南（Informative）

> **本部分是指导性的，不构成合规要求。**

---

## 21. 四阶段路线

### 阶段一：跑通一条链路

```
Ossie 定义 3~5 个概念 → 手工灌数据 → SQL 查询 → 1 个动作 → 1 个 MCP 工具
```
**交付物**：能演示"定义 → 事实 → 查询 → 动作 → Agent"的最小系统。

### 阶段二：补治理

```
数据契约（ODCS）+ 拒收区 + 身份解析（先规则）
```
**交付物**：一个数据源稳定接入，脏数据被隔离而非污染。

### 阶段三：补权限与审计

```
OpenFGA + 审计表 + CloudEvents
```
**交付物**：能回答"谁在何时基于什么做了什么"。

### 阶段四：补治理流程与规模化

```
提案/评审工作流 + CDC + 列存 + 图库（如需要）
```
**交付物**：能跑通一次完整的变更提案。

### 21.1 工作量分布（定性）

| 层 | 相对工作量 | 性质 |
|---|---|---|
| **L1 接入与治理** | **最大** | 无标准可循，要对付"多源、异构、脏、身份不一致" |
| L5 动作 | 大 | 抽象模型要自己定 |
| L3 语义 | **最小** | **Ossie 白拿** |
| L2/L4 | 中 | 有现成产品 |
| 治理流程 | 中 | 组织成本 > 技术成本 |

> **最费工的一层最不性感；最值钱的一层（L5）最容易被忽略；
> 而大家都在做的 L3，恰恰是最便宜的那块。**

---

## 22. Agent-first 设计原则（v0.2 新增为显式原则）

**v0.1 的缺陷：把 Agent 相关的设计散落在各处，没有上升为原则。**

**Agent 和人消费语义的方式根本不同：**

| | 人 | Agent |
|---|---|---|
| 消费方式 | 看图表、点按钮、读文字 | **读结构化能力描述** |
| 出错时 | 问人、查文档 | **只能靠自己重试** |
| 需要 | 可读性、美观 | **可验证的来源 + 预算感知 + 可自纠的拒绝** |
| 规模 | 几个 | **可能几百个并发** |

**四条设计原则：**

| # | 原则 | 体现 |
|---|---|---|
| **1** | **一切可枚举** | Agent 无法"猜"有什么，必须能列出来（I6） |
| **2** | **一切可溯源** | Agent 的结论必须能指回具体事实（I3-G2） |
| **3** | **拒绝即可自纠** | 拒绝信息必须足以让 Agent 自己改对（I4-5、I4-8） |
| **4** | **一切有预算** | Agent 会无意识烧钱，接口必须能限（I3-G4、A-3） |

> **这四条不是"为 Agent 优化"，而是"为 Agent 而设计"——因为 Agent 是这套语义背景的主要消费者。**

---

## 23. 最小实现

| 模块 | 最小实现 | 完整实现 |
|---|---|---|
| 契约存储 | **Git 里的 YAML** | 带版本、分支、审批的服务 |
| 契约校验器 | **一个 Python 脚本** | CI 集成 + 质量门禁 |
| 映射引擎 | **手写脚本** | 声明式映射 + 增量 |
| 拒收区 | **一张表** | 带修复工作流 |
| 身份解析 | **规则匹配** | 概率匹配 + 人工复核 |
| 事实存储 | **Postgres 两张表**（实体表 + 边表） | 多后端 polyglot |
| 一致性读路径 | **Postgres 事务 + 递归 CTE** | 专用快照读服务 |
| 查询引擎 | **SQL + 递归 CTE** | 图查询引擎 |
| 推理引擎 | **一个不动点循环** | 增量 / Rete |
| 检索引擎 | **Postgres 全文** | 向量库 |
| 动作引擎 | **一个 API + 一张审计表** | 编排引擎 + 补偿事务 |
| 发现服务 | **读契约文件生成目录** | 独立目录服务 |
| 授权引擎 | **一张权限表** | OpenFGA |
| 审计日志 | **追加写表** | CloudEvents + 不可变存储 |
| 接口网关 | **FastAPI + MCP server** | 网关 + SDK 生成 |
| 治理流程 | **Git PR + CODEOWNERS** | 提案系统 + 影响分析 |

> **最小实现的量级：一个熟手 2~4 周可以跑通 L1~L6 的一条链路。**
> **别一上来就上完整实现——那是个几年的工程。**

## 24. 尚未解决的问题

### 24.1 v0.1 的九条批判及处理

| # | 批判 | 处理 |
|---|---|---|
| 1 | 「共同」与「开放修改」矛盾 | ✅ 已在 §0.5 明确取舍：开放提案/分叉/退出，不开放就地修改 |
| 2 | 三种用途一套要求 | ✅ 已在 §3 引入 Profile A/B/C |
| 3 | 单域架构 vs 多域 | ✅ 中央式确认；域作为内部划分；**发现机制（I6）成为对齐入口** |
| 4 | 「L5 直调 L2」掩盖难点 | ✅ 已在 §8.1 修正为专用一致性读路径（R1~R4） |
| 5 | 派生不落库 vs 前置条件冲突 | ⚠️ **仅提出候选解法，未解决**（见 §24.2-1） |
| 6 | 缺发现能力 | ✅ 已新增 I6 |
| 7 | 「治理」被当成技术问题 | ✅ 已提升为第一部分（§1~3） |
| 8 | Normative / Informative 混杂 | ✅ 已分列第七、第八部分 |
| 9 | 无 Agent-first 原则 | ✅ 已在 §22 设为显式原则 + 规范性条款 §20.8 |

### 24.2 仍然未解决的（诚实）

| # | 问题 | 为什么难 |
|---|---|---|
| **1** | **派生不落库 vs 前置条件** | 事务内算闭包——性能、正确性、成本三难。候选解法均无定论（§8.2） |
| **2** | **撤回与派生的冲突** | 撤一条前提，依赖它的派生结论要失效；"多条独立支撑"的记账成本高 |
| **3** | **动作抽象模型没有先例** | Palantir 未公开。本框架给的是**候选设计**，不是定论 |
| **4** | **身份解析的准确率上限** | 规则解决约 80%，剩下 20% 必须人工。**且它是脏数据的头号来源** |
| **5** | **合规删除的完整性** | 删了实例，派生的向量 / 摘要 / 缓存要不要删？怎么验证删干净了 |
| **6** | **定义变更的影响分析** | 需要自动算爆炸半径，尚无标准做法（G-6 只规定了"必须能算"，没规定怎么算） |
| **7** | **核心层该多"瘦"** | 太瘦则各域重复定义，太胖则治理成本爆炸。**没有客观标准** |
| **8** | **治理的组织成本** | **本体不是"建"出来的，是"谈"出来的。** 技术解决不了 |
| **9** | **"强 TBox"是否普遍适用** | 本框架预设"语义定义应当独立成层"。**若语义本就稳定、消费者很少，本框架是过度的** |

**⚠️ 第 8、9 条是对本框架本身的质疑，值得认真对待：**

> **第 8 条**：本框架给了治理的技术机制（§1），但**治理真正难的是让人达成共识**。
> 一个高效的提案系统也救不了一群谈不拢的人。
>
> **第 9 条**：采用本框架 = 选择"强 TBox"路线。
> **如果你的场景里语义稳定、消费者很少，那用一张表 + 一段代码就够了，不要用这个框架。**
