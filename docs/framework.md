## 0. 语义治理是什么

### 0.1 问题陈述

**现状**：企业的业务语义散落在应用代码、报表定义、数仓模型、文档里。后果是——

- 同一个"客户"在四个系统里有四个定义
- 同一个"营收"在四个看板上有四个数字
- 改一个规则要改几十个地方，而且改不全
- Agent 拿到互相冲突的业务逻辑，只能胡说

**Palantir 的解法**：把业务语义抽出来，做成一层**可声明、可校验、可执行、可交换的契约**，
并在这层契约之上提供**受控的修改能力**（动作）——即"语义层 + 动能层"。

**本框架要给出一个通用、公开、可开源的等价物。**

### 0.2 为什么叫「语义治理」而不是「本体论」

| 词 | 隐含的重心 | 问题 |
|---|---|---|
| 本体论 | 建模 | 听起来像学术活动，做完就完了 |
| 知识图谱 | 数据 | 听起来像存储选型 |
| **语义治理** | **权责 + 契约 + 技术** | ✅ 点出了"这是一件持续治理的事" |

**"治理"三个字要求框架必须回答：谁有权定义、怎么改、有分歧怎么办、怎么退出。**
一个不回答这些问题的"语义"框架，只是又一份 schema 规范。

### 0.3 核心命题

> **把业务语义从应用代码里抽出来，做成一份可声明、可校验、可执行、可交换的权威契约；
> 规定六个契约，让所有读写都必须经过它；
> 并用一套治理机制保证这份契约能持续演进而不失控。**

### 0.4 【架构】东西都放在哪

```
     ┌──────────────────────────────────────────────────────┐
     │   使用者：人 ／ 智能体                                │   ← 在外：调用方
     │   （不拥有数据、不内置规则，只走契约）                 │
     └───────────────────────▲──────────────────────────────┘
                             │ 一整套契约
                             │ 语义 · 事实 · 查询 · 动作 · 接入 · 发现
     ┌───────────────────────┴──────────────────────────────┐
     │                 本 体 空 间                           │   ← 主体
     │                                                       │
     │   五个要素（各一份，统一管理，不重复定义）             │
     │     对象 · 关系 · 规则 · 策略 · 动作                  │
     │                                                       │
     │   ★ 定义侧（TBox 角色）：允许什么、该怎样              │
     └───────────────────────▲──────────────────────────────┘
                             │ 数据上行 ／ 指令下行
                             │ 经统一映射：字段 → 对象与事实
     ┌───────────────────────┴──────────────────────────────┐
     │                 数 据 来 源                           │   ← 在外：从哪来
     │   （外部系统 · 设备 · 数据库）                        │
     │   ★ 事实侧（ABox 角色）：实际是什么                    │
     └──────────────────────────────────────────────────────┘

        本体构建与管理工具 ──指向──▶ 本体空间
        （建 · 改 · 管 · 发布；不与本体空间并列，也不连使用者）
```

**这张图要读出三件事：**

| # | 要点 |
|---|---|
| 1 | **本体空间是主体**，五个要素在里面。使用者和数据来源都在**外面** |
| 2 | **使用者不是被建模的对象**——它只有权限与审计记录（§5.3） |
| 3 | **数据来源也不是对象**——只有经**映射**进来的那部分才成为对象与事实（§5.3） |

**工具不与本体空间并列**——它是一条指向本体空间的箭头：只负责"建、改、管、发布"，
既不下连数据来源，也不经过使用者。

> **⚠️ 这张图是架构的唯一表述。** v0.3 曾另有一套 "L1~L6 六层架构"，与它重复且无公开出处，
> **v0.4 已删除**（理由见附录 B）。

### 0.5 【关键】形态选择：中央式权威及其代价

**本框架采用中央式：一套权威语义，所有系统向它对齐。**

**它给你什么：**

| 收益 | 说明 |
|---|---|
| **强一致** | 一处改，处处生效；不存在"你的客户"和"我的客户" |
| **无歧义** | 只有一个"营收"的定义 |
| **可治理** | 有明确的权责主体，能追责 |
| **可推理** | 全局闭包可算，不存在跨域的语义断层 |

**它要你放弃什么——必须说清，这是本框架最重要的诚实：**

| 放弃的 | 说明 |
|---|---|
| ❌ **"任何人都能改核心"** | 不可能。改核心要提案、要评审、要公示 |
| ❌ **域之间的完全自治** | 各域必须向核心对齐，不能各说各话 |
| ⚠️ **中央成为瓶颈** | 核心团队的能力决定全局；核心改动要排队 |
| ⚠️ **中央成为风险点** | 核心定义出错，影响所有消费者 |

**所以本框架的"开放"具体指什么：**

| ✅ 开放的 | ❌ 不开放的 |
|---|---|
| 规范本身（开源、任何人可自由实现） | **核心定义的直接修改权** |
| 提案权（任何人可提变更提案） | |
| 扩展命名空间（域内自定义，不受核心约束） | |
| **分叉权**（可 fork 核心，另立门户） | |
| **退出权**（可导出全部定义与事实并离开） | |

> **一句话：开放的是「加入、提案、分叉、退出」，不是「就地修改」。**

**这不是妥协。这是所有成功标准的共同形态：**

| 标准 | 提案 | 权威 |
|---|---|---|
| IETF | 任何人可提 Internet-Draft | 集中（IESG/IAB 批准） |
| W3C | 任何人可提 | 集中（工作组 + 会员投票） |
| Kubernetes | 任何人可提 KEP | 集中（SIG + TOC 批准） |
| **本框架** | 任何人可提变更提案 | **集中（治理机构批准）** |

> **"提案开放 + 权威集中"是唯一被验证过能同时做到"开放"和"稳定"的形态。**
>
> 而那些试图做到"谁都能改"的尝试（语义网的全球共享本体），**全部失败了**。

> **⚠️ 这两句是判断，不是引证。** 依据与失败原因的展开见
> [`rationale.md`](rationale.md) 第六节「语义网失败的原因」与第十九节「参考来源」
> （那里列了 schema.org、Freebase 等具体案例与文献）。**上游依据在那边，本节只给结论。**

## 1. 治理的六件事

### 1.1 命名空间与权威（谁的地盘）

**核心设计：分层命名空间。**

```
urn:sem:<authority>:<domain>:<concept>
         ↑           ↑         ↑
      权威机构      域        对象
```

| 命名空间层 | 谁有权定义 | 变更流程 |
|---|---|---|
| **核心层** `urn:sem:core:*` | 治理机构 | **正式提案 + 评审 + 弃用期** |
| **领域层** `urn:sem:<org>:*` | 组织/域的建模负责人 | 内部评审 |
| **扩展层** `urn:sem:<org>:<domain>:ext:*` | 任何消费者 | **自由定义，无需批准** |
| **本地层**（不进标准） | 单个应用 | 随意 |

**规则：**

- **核心层 MUST 极简**——只放跨域必需的对象（客户、组织、时间、金额……）。
  **核心层越胖，治理成本越高，且越容易变成瓶颈。**
- **扩展层是安全阀**——想让所有人都改核心的冲动，应该被引导到扩展层
- **跨层引用只能向上，不能向下**：扩展层可引用核心层；核心层 MUST NOT 引用任何扩展层

### 1.2 变更流程

```
① 提案     任何人可提（不限身份）
   ↓
② 影响分析  自动算出：影响哪些对象、哪些消费者、哪些动作
   ↓
③ 公示期    至少 N 天（核心层 N 大，扩展层 N=0）
   ↓
④ 评审      治理机构 / 域主
   ↓
⑤ 发布      新版本号；旧版本进入弃用期
   ↓
⑥ 弃用      弃用期结束才可移除
```

**三条硬规则：**

| # | 规则 | 为什么 |
|---|---|---|
| **H1** | **定义一经发布即不可原地修改** | 否则无法回溯、无法追责 |
| **H2** | **破坏性变更 MUST 有弃用期** | 否则消费者会被静默打断 |
| **H3** | **变更必须能算出影响面** | 否则治理是盲的 |

### 1.3 争议解决

**当两个人对同一个对象有不同意见：**

| 情形 | 解法 |
|---|---|
| 命名冲突（都想叫"客户"） | 命名空间隔离 → 各自用全限定名 |
| 语义冲突（"客户"含义不同） | **必须拆成两个对象**，不能强行统一 |
| 粒度冲突（一个要粗一个要细） | 细的为基，粗的用派生规则算出来 |
| 无法调和 | **分叉**（见 1.5） |

**原则：**

> **共识是"谈"出来的，不是"统一"出来的。**
> **强行统一两个不同的对象，是语义治理中最常见的错误。**

### 1.4 版本与兼容性

| 变更类型 | 兼容性 | 处理 |
|---|---|---|
| 新增对象 / 关系 | ✅ 向后兼容 | 小版本号 |
| 新增可选属性 | ✅ 兼容 | 小版本号 |
| 新增必填属性 | ⚠️ **破坏性** | 弃用期 + 大版本号 |
| 删除 | ❌ **破坏性** | 弃用期 + 大版本号 |
| 改语义（同名不同义） | ❌ **欺骗性** | **MUST NOT** —— 必须新建对象 |
| 改约束 | ⚠️ 视情况 | 影响分析 |

> **"改语义但保留名字"是最危险的变更——它让所有消费者静默出错。**

### 1.5 分叉与退出（**最容易被忽略，也最重要**）

**没有退出权的标准是枷锁，不是标准。**

| 权利 | 怎么保证 |
|---|---|
| **分叉权** | 全部定义以**开放格式**提供（Ossie YAML）——任何人可 fork |
| **退出权** | MUST 提供**完整导出**：定义 + 事实 + 血缘 + 审计 |
| **回归权** | 分叉后仍可提交提案回来 |

**MUST 提供导出，且导出格式 MUST 可独立于本实现使用。**

### 1.6 权责矩阵

| 事 | 谁负责（R） | 谁批准（A） | 谁咨询（C） | 谁知会（I） |
|---|---|---|---|---|
| 核心对象新增 | 提案人 | 治理机构 | 消费者代表 | 全体 |
| 核心对象修改 | 提案人 | 治理机构 | 消费者代表 | 全体 |
| 领域对象 | 域建模负责人 | 域主 | 域内消费者 | 治理机构 |
| 扩展对象 | 任何人 | 无需 | — | — |
| 动作定义 | 域建模负责人 | 域主 + 安全负责人 | 审计 | 治理机构 |
| 权限模型 | 安全负责人 | 安全负责人 | 域主 | 审计 |

## 2. 三类角色与权责

| 角色 | 干什么 | 关心什么 |
|---|---|---|
| **治理机构**（中央） | 维护核心层、批准变更、解决争议 | 长期稳定性、跨域一致性 |
| **域主**（Domain Owner） | 维护本域对象、审批本域变更 | 本域业务的准确性、变更成本 |
| **消费者** | 使用语义、提交提案 | 别被破坏性变更打断 |

**⚠️ 反模式：把治理机构变成"审批机器"。**

> 如果所有变更都要中央批，中央就成了瓶颈，各域会绕过它自己搞——
> **这正是一切中央式治理失败的路径。**
>
> **解法：扩展层无需批准（安全阀）+ 核心层极简（减少必须走流程的量）。**

## 3. 三种剖面（Profile）

**v0.1 的错误：用一套要求覆盖所有用途。但三种用途的需求差别极大。**

| | **Profile A · 轻量** | **Profile B · 组织** | **Profile C · 严格** |
|---|---|---|---|
| **适用** | Agent 记忆库、个人知识 | 部门数据治理、单组织多系统 | 跨系统权威语义、受监管场景 |
| **语义稳定性** | 低（随时改） | 中 | 高 |
| **消费者** | 1 个 | 几个人 | 多系统多团队 |
| **命名空间** | 只用扩展层/本地 | 领域层 + 扩展层 | **核心层 + 领域层 + 扩展层** |
| **变更流程** | 无需提案 | 内部评审 | **正式提案 + 公示 + 弃用期** |
| **必须实现** | **I1 + I2 + I3**（+ I6） | **+ I4 + 审计** | **全部六个契约 + 全部治理机制** |
| **合规等级** | **L0**（做到 I6 才升 L1） | L0~L3 | L0~L4 |
| **典型规模** | 单机 | 单组织 | 跨组织 |

**判定规则：**

```
只有一个消费者，且语义可随时改         → Profile A
多个消费者，但都在一个组织内           → Profile B
跨组织 / 受监管 / 改动会影响外部系统    → Profile C
```

> **⚠️ Profile 是"当前状态"，可以升级。**
> **记忆库长成了部门资产，就该升到 B。**

## 4. 术语表

> **标准的第一件事是统一术语。以下词在本框架内有且仅有以下含义。**
>
> 带 ★ 的五个是**五要素**（见 §5）；其余是要素内部的构件，或要素作用的运行期对象。

| # | 术语 | 英文 | 定义 | 例子 |
|---|---|---|---|---|
| 1 | **域** | Domain | 一个独立的语义空间（限界上下文）。**一切从域开始** | 供应链域、财务域 |
| 2 | ★ **对象** | Object | 一类业务实体。**"世界"这一侧**——这是本框架对"概念"的称谓 | 订单、客户、设备 |
| 3 | **属性** | Property | 对象的字段 | 订单金额、下单时间 |
| 4 | ★ **关系** | Relation | 对象之间的**类型化连接** | 订单—属于→ 客户 |
| 5 | **角色** | Role | 关系中的位置 | 关系「运输」有角色：起运地、目的地 |
| 6 | **基数** | Multiplicity | 角色的数量约束 | 一个订单最多一个客户 |
| 7 | ★ **规则** | Rule | 对实例或事实的**合法性要求**。判定只有二值，**无裁量空间** | 金额必须为正 |
| 8 | **派生对象** | Derived Object | **由规则算出**的对象（**算出来的，不是存下来的**）。它**不是**第六个要素——声明归规则，产物归对象 | "某订单的所有上游依赖" |
| 9 | ★ **策略** | Strategy | 在**规则判定为合法的候选集**内作出优选判定。**有裁量空间**，输出的是序，不是合法与否 | 优先走低时延路径；冲突时优先保核心层 |
| 10 | **实例** | Instance | 一个具体的业务对象 | 订单 #12345 |
| 11 | **事实** | Fact | 实例之间的连接，或实例的属性值 | 订单 #12345 属于客户 acme |
| 12 | ★ **动作** | Action | 对实例的**受控修改**。**五要素中唯一能改变状态的** | 取消订单、发放优惠券 |
| 13 | **视图** | View | 对事实的查询结果（**不落库**） | "api 的所有上游依赖" |

**四个容易混的点：**

| 容易混 | 区别 |
|---|---|
| 对象 vs 实例 | 对象是"订单这一类"，实例是"订单 #12345 这一个" |
| 属性 vs 关系 | 属性指向**值**（金额=100），关系指向**另一个实例**（属于客户 acme） |
| 事实 vs 视图 | 事实是**存下来的**，视图是**算出来的** |
| **规则 vs 策略** | 规则回答"**能不能**"，**不可权衡**，失败即**系统出错**；策略回答"**选哪个**"，**可以权衡**，失败只是**不够优**。拿掉一条看后果：出现非法状态的是规则，只是效果变差的是策略 |

> **"约束"这个词在本框架中的位置**：框架的要素名是**规则**；`约束` 作为 Ossie 的机器可读载体名（`requires`）保留在下表中，指的是**规则的实现载体**，不是另一个要素。

**本框架的词 ↔ Ossie 的载体**（**要素名用框架的，载体名用 Ossie 的**，两者不混叫）：

| 五要素 | 本框架称谓 | Ossie 载体 | 说明 |
|---|---|---|---|
| 对象 | 对象 | `concept`、`extends`、`type` | ✅ 覆盖 |
| 关系 | 关系 | `relationships`、`roles`、`multiplicity` | ✅ 覆盖 |
| 规则 | 规则 | `requires`、`multiplicity`（基数约束） | ⚠️ `requires` 官方 validator **只校验结构、不执行**——强制点必须下沉到实现（见 I4 `ST-4`） |
| 策略 | 策略 | ❌ **无载体** | 本框架的原创部分（见 §5） |
| 动作 | 动作 | ❌ **无载体** | 本框架的原创部分（见 §5） |
| —（非要素） | 映射 | `ontology_mappings` | 归 I5 接入契约，**不占要素** |
| —（非要素） | 派生对象的声明 | `derived_by` | **归规则**：`derived_by` 是规则的一种声明形式，产物是派生对象 |

## 5. 四个正交维度：别把它们混成一锅

> **这一节是全文最容易读错的地方，所以单独拿出来先讲清。**
>
> 框架里有四套名词，**它们不是四套分类，是四个不同的问题**。
> 混在一起看，就会出现"为什么动作既是要素又是契约""为什么还要分层"这类困惑。

### 5.1 四个维度各答一个问题

| 维度 | 回答什么 | 出处 | 性质 |
|---|---|---|---|
| **五要素** | 语义**由什么构成**（内容分类） | 对象·关系·规则 ← **Apache Ossie**<br>策略·动作 ← **本框架原创** | 声明侧 |
| **TBox / ABox** | 这句话在讲**类型还是事实**（角色） | **描述逻辑**（学术理论，OWL 的基础区分） | 角色 |
| **Apache Ossie** | 怎么写进文件（**格式**） | **Apache 标准** | 格式 |
| **契约** | 谁**能**读写、怎么读写（**通道**） | 本框架原创 | 通道 |

**读法**：**一个东西在四个维度上各有一个坐标，四个坐标互不替代。**

```
「订单」这个东西：
  · 五要素轴：它是【对象】
  · TBox/ABox 轴：作为定义它在【TBox】；作为 #12345 那条记录它在【ABox】
  · 格式轴：它写成 【Ossie 的 concept: Order】
  · 契约轴：谁读它走【I1】，谁写它走【I2】
```

### 5.2 TBox / ABox 是「角色」，不是「层」

> **⚠️ 这是 v0.4 的一处重要更正。**
> v0.3 曾写"L3 语义层 = TBox 的载体、L2 事实层 = ABox 的载体"——
> **"载体"这个词把它说成了两个房间**，于是凭空多出一套"层"，与 §0.4 的架构图冲突。

**正确的说法**：**TBox 与 ABox 是同一个东西的两种角色。**

| 要素 | TBox 角色（定义：允许什么） | ABox 角色（事实：实际是什么） |
|---|---|---|
| **对象** | 「订单」**这个类型**存在 | 「订单 #12345」**这个实例** |
| **关系** | 「订单—属于→客户」**这个类型化连接** | 「#12345 属于 acme」**这条事实** |
| **规则** | 「金额必须为正」**这条约束** | —— 规则**没有事实侧**（只在入口判定） |
| **策略** | 「优先走低时延」**这条偏好** | —— 策略**也没有事实侧** |
| **动作** | 「取消订单」**这个契约** | 一次提交**及其审计记录** |
| **派生** | `derived_by` **表达式** | 派生结果（**不落库**，现算现用） |

**对应到 §0.4 的架构图：**

| 图里的位置 | 角色 |
|---|---|
| **本体空间** | 装着 **TBox**（五个要素的声明） |
| **数据来源** | 提供 **ABox**（真实数据） |
| **映射 + 契约** | 让两者对上（字段 → 对象与事实） |

> **所以"TBox/ABox 要分开"不是一条"层的规则"，是一条"纪律"**——
> 定义与事实必须分属不同的存放单元（`LD-4`）。
> 这件事在架构图里已经表达了：本体空间是定义侧，数据来源是事实侧。

### 5.3 本体空间之外的两样东西

**这两样常被误当成要素或对象，必须说清：**

| | 在不在本体空间里 | 它是什么 |
|---|---|---|
| **数据来源** | **不在** | 数据从哪来。只有**经映射进来的那部分**才成为对象与事实 |
| **使用者**（人 / 智能体） | **不在** | 契约的调用方。它没有标识、能力、状态——**只有权限与审计记录** |

**为什么必须分清**：

- **数据来源不清** ⇒ 没人知道"数据在哪一刻、按哪份声明变成对象"，"写入必须过规则"就没有落脚点
- **使用者不清** ⇒ 智能体被塞进对象清单，而它根本没有"标识、能力、状态"这三样对象属性

**映射是声明的，不是隐含的**：归 **I5 接入契约**，用 Ossie 的 `concept_mappings` /
`object_mappings` / `link_mappings` 声明"哪个字段变成哪个对象的哪个属性"。

### 5.4 五个要素一览（**含出处**）

> **"可声明"= 可以写进契约文件的东西。** 其余（实例、事实）是运行时的。

| # | 要素 | 声明什么 | **出处** | 载体 |
|---|---|---|---|---|
| 1 | **对象** | 有哪些类东西、层次、标识 | ✅ **Apache Ossie** | `concept` `type` `extends` `identify_by` |
| 2 | **关系** | 对象之间怎么连（角色、基数、方向） | ✅ **Apache Ossie** | `relationships` `roles` `multiplicity` `verbalizes` |
| 3 | **规则** | 什么合法（**约束式** · **派生式**） | ⚠️ **槽位来自 Ossie**，表达式语法 Ossie 未定 | `requires` `derived_by` |
| 4 | **策略** | 在合法候选里选哪个（序，可权衡） | ❌ **无公开规范 → 本框架原创**；语义参照 OMG DMN / W3C ODRL | 旁挂声明（§9.8） |
| 5 | **动作** | 允许怎么改、带什么条件、连带动什么 | ❌ **无公开规范 → 本框架原创**；概念参照 Palantir kinetic elements | 旁挂声明（§10.9） |

**前两个是名词性的**（世界上存在什么），**后三个是动词性的**（允许做什么、应该怎么做）。

> **Ossie 覆盖前三个的槽位；策略与动作是空白——这两个是本框架的原创部分。**
> 这个判断有据可查，不是拍脑袋：**Ossie 本体规范里根本没有"策略"或"动作"这两个概念**，
> 也**没有任何扩展机制**（`ontology.md` 里 extension/custom/vendor 出现 0 次）。

### 5.5 三句话把五要素的关系定死

| 要素 | 一句话 | 失败算什么 |
|---|---|---|
| **规则** | 划定可行域的**边界** | 系统**出错**（出现非法状态） |
| **策略** | 在可行域内建立**偏好序** | 系统**次优**（仍然合法，只是效果差） |
| **动作** | 把选择**落地**为状态变更 | 提交被拒，或需要补偿 |

**派生不是独立要素**：声明归规则（`derived_by` 与 `requires` 是同一要素的两种声明形式），
产物归对象（**派生对象**），且**不落库**（`I2-4`）。

**三条切割线**（判断一个声明属于哪个要素，展开见 §8.2 / §9.3）：

| 切割线 | 规则 | 策略 | 动作 |
|---|---|---|---|
| **论域** | 尚未受约束的状态空间 | 规则筛出的**合法候选集** | 已选定的那一个 |
| **值域** | **二值**（合法 / 非法） | **序**（优劣与选中项） | **状态变更** |
| **失败语义** | 系统**出错** | 系统**次优** | 提交被拒 / 需要补偿 |

**一条最好用的现场判据——拿掉它看后果：**

| 拿掉它 | 归属 |
|---|---|
| 产生**非法状态** | **规则** |
| 系统**仍然合法，只是效果变差** | **策略** |
| **没有任何状态改变** | **不是规则也不是策略**——它根本不在这里 |

**由三条切割线推出的两条硬结论**：

1. **规则与策略 MUST NOT 产生状态变更；凡产生状态变更者必属动作。**（`ELE-8`）
2. **策略的论域是规则论域的子集**——所以"把优选塞进规则"与"把合法性交给策略"都是语义污染。

### 5.6 搭框架的准则：按公开出处来

> **有槽就用槽，没槽就用别的公开标准，都没有才自定——且必须标明。**

| 顺序 | 判断 | 处置 |
|---|---|---|
| 1 | Ossie 有对应槽位吗？ | **有 → 直接用**（对象、关系、规则的槽位） |
| 2 | 没有——别的公开标准有吗？ | **有 → 照标准做并标明**（策略 → DMN / ODRL） |
| 3 | 都没有——必须自己定吗？ | **是 → 自定，但 MUST 标明"本框架原创，无公开规范可依"** |

**这条准则的价值在第 3 档：一标注就露馅。**
凡是说不出来源的，就不该以"标准"或"推导"的面目出现——
v0.3 的"六层架构"正是这么被发现的（它其实是把 Palantir 的后端服务反推成层，再补的理论说辞，见附录 B）。

## 6. 对象

> **对象回答"有什么"。它是"世界"这一侧的名词。**

### 6.1 一个对象声明四件事

| # | 声明 | 说明 | Ossie 载体 |
|---|---|---|---|
| 1 | **标识** | 这个对象靠什么被唯一引用 | `identify_by` + 标识关系 |
| 2 | **类型** | 实体类型还是值类型 | `type: EntityType / ValueType` |
| 3 | **层次** | 继承谁；值类型最终必须落到内建类型 | `extends` |
| 4 | **属性** | 对象的字段 | 指向值类型的关系 |

### 6.2 实体类型 vs 值类型

| | **实体类型** | **值类型** |
|---|---|---|
| 是什么 | 现实世界的对象，**必须靠其他信息才能被引用** | 带语义的数据类型（等价于 domain） |
| 怎么引用 | 经一条或多条**标识关系** | 直接是值 |
| 能不能悬空 | 不能——引用实体必须有标识 | 不适用 |
| 例 | 订单、客户 | 订单号、金额、状态枚举 |

> **⚠️ 一个高频错误**：把"实体"和"表"混为一谈。
> 实体是语义概念，一张表可以承载多种实体，一个实体也可能跨表。

### 6.3 对象与"数据来源"的关系

**对象不是数据来源，数据来源也不是对象。**

| | 在不在本体里 | 说明 |
|---|---|---|
| **对象** | **在** | 被描述的东西 |
| **数据来源** | **不在** | 数据从哪里来；只有**映射进来的那一部分**才成为对象与事实 |
| **契约的调用者**（人 / Agent） | **不在** | 使用者不是被建模的对象；它只有权限与审计记录 |

映射是**声明的**，不是隐含的：`映射` 归 **I5 接入契约**，用 Ossie 的 `concept_mappings` / `object_mappings` / `link_mappings` 声明"哪个字段变成哪个对象的哪个属性"。

> **这条一旦含糊，"写入必须过规则"就没有落脚点**——因为没人知道数据是在哪一刻、按哪份声明变成对象的。

### 6.4 对象是不变的吗

对象（定义）**一经发布不可原地修改**，只能新增版本（`I1-G1`、`G-2`）。
但对象的**实例**随运行不断变化——这正是 TBox / ABox 变更频率不同的体现。

## 7. 关系

> **关系回答"怎么连"。它是一等公民，不是外键。**

### 7.1 关系声明四件事

| # | 声明 | 说明 | Ossie 载体 |
|---|---|---|---|
| 1 | **角色** | 关系里的位置。**⚠️ Ossie 的约定**：声明关系的那个概念演**第一个角色**，**其余角色**才列进 `roles`——所以一个二元关系的 `roles` 只有 **1 项**，一元关系为空 | `roles` + `name` |
| 2 | **基数** | **最后一个角色**是否被其余角色唯一确定（`ManyToOne` 对 n 元关系也**只作用于最后一角色**；`OneToOne` **仅限二元关系**） | `multiplicity`：`ManyToOne` / `OneToOne` |
| 3 | **方向** | 按声明它的对象组织（Ossie 把关系挂在"扮演第一个角色的对象"下） | 结构约定 |
| 4 | **verbalizes** | 怎么把它念成人话（**给人与 Agent 读**） | `verbalizes` |

### 7.2 为什么关系是"一等公民"

因为**引擎自己会走关系**——调用方不需要在应用层写连接语句。

| 写法 | 谁在做连接 |
|---|---|
| 外键 | **应用层**：自己 join |
| 一等关系 | **引擎**：按声明遍历，且遍历可被权限过滤、可被审计 |

这也是为什么"结果必须可追溯"（`I3-2`）能成立：遍历的是**声明过的**关系，每一步都能说清走的是哪条。

### 7.3 基数是**关系字段**，其语义属于规则

`multiplicity` 声明的是**合法性要求**（"一个订单最多一个客户"）。

> **⚠️ 归属说清楚**：Ossie 把它定义为**关系的字段**（官方称 "Multiplicity constraint"），
> 而 Ossie 自述的 business rules **只括注 `requires` 与 `derived_by`**——
> **把基数归入"规则"要素是本框架的归类，不是 Ossie 的说法。**
> 依据是框架自己的切割线（§5.5）：拿走它会**产生非法状态**（一物两主），所以它是规则、不是策略。

**所以同一处声明在坐标系里有两个位置**：载体在**关系**（它是关系的字段），要素归属在**规则**（判定二值、在写入路径拦截）。

> **实践含义**：写入路径上必须强制 multiplicity（见 I4 `ST-4`）。
> 只在读取时校验，等于"脏数据能写进去，读的时候才炸"。

### 7.4 派生关系：规则写在关系上

关系也可以有 `derived_by`（派生式规则）。此时的产物在要素归属上仍是**派生对象**（`ELE-3`）——
**关系本身就属对象侧**（它是被声明的名词性内容），所以"派生出来的关系"不构成新类别。**不落库。**

> **⚠️ 用词**：本文档**不用"派生关系"这个词**——它会让读者以为多了个类别。
> 统一说法是：**`derived_by` 的产物一律是派生对象**，只是它可能落在"关系"这个载体上。

例（传递闭包）：

```yaml
- name: holds_transitively
  roles: [ { concept: Customer, name: held } ]
  derived_by:
    - "Customer.holds(held)"                    # 基例
    - "Customer.holds_transitively.holds(held)" # 递归例
```

> **注意**：Ossie 用**规则**而不是**公理**表达传递性（不同于 OWL 的 `TransitiveProperty`）。
> 这一选择让"为什么这两个客户有关联"永远有依据可查。

## 8. 规则

> **规则回答"什么合法"。判定只有二值，无裁量空间，不可权衡。**

### 8.1 规则有两种声明形式

| 形式 | 作用 | Ossie 载体 | 产物 |
|---|---|---|---|
| **约束式** | 声明"什么状态组合被允许"，在写入与状态迁移的入口拦截 | `requires` | 无（只有判定） |
| **派生式** | 声明"什么能算出来" | `derived_by`（支持递归） | **派生对象**（不落库） |

**两者是同一要素的两种形式，不是两个要素**——这是派生的归宿：**声明归规则，产物归对象。**

### 8.2 规则的三条边界

| 边界 | 说明 |
|---|---|
| **规则不是数据** | 它不描述世界是怎样的，只描述世界**被允许**是怎样的；不随运行过程改变 |
| **规则不是策略** | 规则回答合法性，策略回答优越性；规则**不可权衡**，策略可以权衡 |
| **规则不是动作** | 规则不产生任何状态变更；它与动作的关系是**关卡与通行**，不是命令与执行 |

### 8.3 规则的失败语义

**规则失败即系统出错**——出现了非法状态，正确性被破坏。

因此规则的保障手段是**定义期**的：**静态一致性检查**（同一个对象、同一个条件、相反结论即报警），把矛盾在定义期排除，而不是等运行时临场判断。

> **⚠️ 一个必须说清的边界**：`requires` 这类声明式规则的**实际强制点**在写入路径上，
> 而 Ossie 官方 validator **只校验"是字符串/结构"、不求值**。
> 所以"规范上写着、跑起来不生效"是这类声明的头号陷阱——见 I4 `ST-4` 与 §16.1。

### 8.4 撤销一条事实会怎样

撤掉一条前提，依赖它的**派生结论不需要专门机制去级联失效**：派生对象从不落库，下次求值**算不出来**，自然就没了。

真正未决的是两件事（列在 §28.2）：**增量的代价**与**撤回的语义分级**。

## 9. 策略

> **策略回答"选哪个"。它在规则判定的合法候选集内建立优先序。**
>
> 这是五要素里**唯一在 Ossie 中没有载体**的声明性要素（动作是另一个空白要素）。

### 9.1 定义

**策略是本体内在合法状态空间中作出优选判定的、有裁量空间的偏好声明。**

它以**规则判定为合法的候选集**为定义域，按给定目标给出候选之间的优先序，输出**选中项及选择依据**。

### 9.2 策略声明四件事

| # | 声明 | 说明 |
|---|---|---|
| 1 | **作用域** | 管哪些对象、哪个方向；**分组不构成私有边界** |
| 2 | **依据的规则集** | 论域 = 该规则集筛出的合法候选集（`ELE-4` **MUST**） |
| 3 | **目标与优先序** | 按什么目标排序（低时延 / 低功耗 / 抗抖 …） |
| 4 | **选择依据** | 每次判定必须能说清"为什么选它"（`ELE-6`，对应 `I3-2` 的溯源精神） |

### 9.3 三条切割线（与规则的分别）

| 切割线 | 规则 | 策略 |
|---|---|---|
| **论域** | 尚未受约束的状态空间 | **规则筛出的合法候选集**（子集关系） |
| **值域** | 二值：合法 / 非法 | **序**：优劣与选中项 |
| **失败语义** | **系统出错** | **不够优**，系统仍然正确 |

**策略不能把非法变合法**——它只能在"合法与合法"之间分出优劣。
若策略试图选一个不满足规则的候选，**那不是"策略认为它更好"，而是这一步根本不合法**。

### 9.4 失败语义与保障手段

策略失败**不是出错**，只是**次优**。所以它的保障手段不在定义期，而在**运行期**：
**运行时仲裁**——冲突时确定取舍，而不是靠静态检查排除。

### 9.5 冲突处理：五层，从预防到兜底

| 层 | 手段 | 说明 |
|---|---|---|
| **1** | **切干净**（最主要） | 让两个策略的判定对象互不重叠——**结构上不重叠，就永远撞不上。冲突大多不是靠仲裁解决的，是靠切分消灭的** |
| **2** | **显式定优先级** | 真出现同对象判定，按"**核心层规则 ＞ 领域层规则 ＞ 策略 ＞ 动作**"逐级压制，**且必须写在定义里**，不能靠运行时临场判断 |
| **3** | **运行时仲裁** | 真僵住了，由治理流程或指定的仲裁主体裁 |
| **4** | **判定出口唯一** | 同一时刻、同一对象只允许一个判定生效，其余记为备选并留决策记录 |
| **5** | **静态检查 + 变更治理** | 跨域冲突要在**定义期**尽量查出来；改策略走"提案 → 影响分析 → 评审 → 发布" |

**先分清是哪种"撞"**：大多数所谓冲突是**假冲突**——管的对象根本不同，只是名字听着像。
**真冲突只有一种形态：两个策略对同一个对象、同一时刻给出了不同结论。**

### 9.6 「策略」不等于「授权策略」

这两个词必须分列（`ELE-7`）：

| | **语义策略** | **授权策略** |
|---|---|---|
| 问什么 | **选哪个** | **谁可以** |
| 归属 | 本框架的**要素** | I4 的**权限**部分 |
| 载体 | ❌ 无标准 | ✅ **OPA / Rego** 或 **Cedar** |
| 失败 | 次优 | 拒绝 |

> **混用的代价**：把"谁可以"写成策略要素，会让可权衡者掌握不可权衡之事；
> 把"选哪个"塞进授权引擎，会让业务偏好散落在权限配置里，谁也看不出业务取向。

### 9.7 策略是可选的（条件式条款）

**不声明策略是合法状态**——一个只做校验与派生的实现，不因缺少策略而不合规。

但**一旦声明**，就必须满足 `ELE-4`~`ELE-6`：声明依据的规则集、不改变合法性、携带选择依据。
否则策略会退化成"用规则的口吻表达偏好"，两边都不再可靠。

### 9.8 策略的承载格式：**旁挂声明**

> **为什么必须旁挂**：策略**没有公开规范**（见 §5.4），而 Apache Ossie 的**本体规范里根本没有扩展机制**——
> `ontology.md` 与本体官方 schema `ontology.json` 里 `extension` / `custom` / `vendor` 均出现 **0 次**，
> 且概念/关系/角色/映射上共 **9 处 `additionalProperties: false`**（**不能加任何字段**）。
> 扩展槽 `custom_extensions` 只长在 **core-spec 的语义模型那一侧**，**挂不到本体元素上**。
> **所以策略既不能塞进 Ossie 的字段，也不能挂在 Ossie 的扩展槽里。**
>
> **⚠️ 注意 Ossie 有两份官方 schema，别混**：本体用 `ontology/ontology.json`（顶层 7 项），
> 语义模型用 `core-spec/ossie-schema.json`（顶层 `version` + `semantic_model`）。
> 扩展槽属于后者。

| | |
|---|---|
| **放哪** | 与 Ossie 本体文件**并列的旁挂声明文件**（例：`strategies.yaml`） |
| **怎么标明出处** | 文件头 **MUST** 声明"本框架原创，无公开规范；语义参照 OMG DMN / W3C ODRL" |
| **最小字段**（对应 `ELE-4`~`ELE-6`） | `id` · `scope`（作用对象/方向）· `basis_rule_ids`（依据的规则集 = 论域）· `objective`（优选目标）· `ordering`（优先序）· `rationale`（选择依据） |

**三条 MUST**：

| 编号 | 条款 |
|---|---|
| **SP-1** | 策略声明 **MUST** 与 Ossie 本体文件分离存放，**MUST NOT** 混进 `requires` 等 Ossie 字段 |
| **SP-2** | 策略声明 **MUST** 显式引用其**依据的规则集**（`basis_rule_ids`），论域由该集合界定 |
| **SP-3** | 每次策略判定 **MUST** 携带选择依据（`rationale`），并 **MUST** 可被审计 |

> **⚠️ 与授权策略的区别**：授权策略（OPA / Cedar）管"谁可以"，有公开标准；
> 本节的语义策略管"选哪个"，无公开标准。两者 **MUST** 分列（`ELE-7`），不要合并到一个文件里。

### 9.9 【关键】策略的求值与落地归属（**这一环以前是断的**）

> **策略只输出"序"，它自己不改变任何状态**（`ELE-8`）。那么——
> **谁求值它？谁把"选中项"变成一次真正的状态变更？**
>
> v0.4 之前，文档只说"策略结论由**调用方**落地"，**没有指定调用方是谁、走哪条契约**——
> 于是策略从"声明"到"生效"之间**断了一环**。本节把它接上。

**一条策略从声明到生效，必须走完这四步，每一步都要有明确归属：**

| # | 步骤 | 归属 | 承载 |
|---|---|---|---|
| 1 | **声明** | 本体建设方 | 旁挂声明文件（`SP-1`） |
| 2 | **求值**（在合法候选集内排出优先序） | **决策执行方**（人或智能体），**在规则筛出候选之后** | **I3 查询契约**取候选 → 求值 |
| 3 | **落地**（把选中项变成状态变更） | **同一决策执行方**，**MUST 经 I4 动作契约提交** | **I4** |
| 4 | **留痕**（为什么选它） | 动作的审计记录 | `I3-2`（候选来源）+ 动作审计（`I4-G3`） |

**三条 MUST：**

| 编号 | 条款 |
|---|---|
| **SP-4** | 策略的**求值方**与**落地方** **MUST** 是同一个主体；**MUST NOT** 由一方求值、另一方落地 |
| **SP-5** | 策略结论的落地 **MUST** 经 **I4 动作契约**提交，**MUST NOT** 绕过动作直接改状态（同 `ELE-8`） |
| **SP-6** | 实现 **MUST** 在声明里写明求值时机（事件触发 / 定时 / 人工），**MUST NOT** 留空 |

> **⚠️ 为什么"由调用方落地"这个说法不够**：
> "调用方"是个含糊的词——它可以是人、智能体、外部系统或内部调度。
> **不说清是谁，就没有人能验收这一环**；而策略恰恰是**唯一没有公开规范可依**的声明性要素，
> 最需要把归属写死。**这一节就是补这个洞。**

> **与本框架的取值取向一致**：框架**不规定策略算法**（那是实现自由），
> 只规定**归属与留痕**（那是可验收的）。

## 10. 动作

> **动作回答"怎么改"。它是五要素中唯一能改变状态的要素，也是<u>使用者侧</u>唯一的写入通道。**
> （事实共有**两条**写入路径：接入与动作，见 §16 `I2-G3`。）

### 10.1 为什么动作必须是"使用者侧"唯一的写入通道

由关系①（约束）直接推出：**ABox 只能装合法事实 ⇒ 往 ABox 里写必须过 TBox 这道关。**

**如果存在第二条写入通道，那道关就可以被绕过**——规则就从"保证"退化为"建议"。
所以 `I2-G3`「只有两条写入路径」不是设计偏好，而是理论必然（见 `I2-2`）。

### 10.2 动作契约字段清单（十项）

| # | 声明 | 说明 |
|---|---|---|
| 0 | **标识** | 动作名、所属命名空间、定义版本（**旁挂文件的身份**） |
| 1 | **作用对象** | 动谁（含多实例） |
| 2 | **参数** | 带什么（含参数级约束） |
| 3 | **前置条件** | 什么情况下才允许 |
| 4 | **效果** | 会发生什么（含连带影响） |
| 5 | **副作用** | 除效果之外还触发了什么 |
| 6 | **幂等性** | 重复提交怎么识别 |
| 7 | **权限** | 谁可以提交 |
| 8 | **审计** | 必须留下什么记录 |
| 9 | **拒绝格式** | 被拒时说清什么 |

> **⚠️ 这一组是动作契约的"完整字段清单"，全框架以此为准。**
> §18（I4 契约）只讲**接口行为与保证**，不再重复这份清单——
> 曾有两处各写一份（字段数与内容都不一致），v0.4 已去重。

### 10.3 提交必须依次完成四件事

```
① 参数校验 → ② 权限校验 → ③ 前置条件校验 → ④ 效果写入（同一事务）
```

**顺序不可交换**：权限必须早于前置条件——否则"前置条件不满足"与"你无权看"会泄漏信息（见 I4 `ST-1`）。

### 10.4 提交语义五件事

| 要素 | 待定义 |
|---|---|
| 同步 / 异步 | 什么时候返回？长动作怎么处理 |
| **事务边界** | 涉及多个实例时，原子性范围是什么 |
| **幂等键** | 重复提交怎么识别 |
| **失败语义** | 拒绝（全无副作用）／部分成功（怎么补偿）／补偿（Saga） |
| **并发** | 两个动作同时改同一实例，怎么办 |

### 10.5 审计记录

每次提交 **MUST** 产生一条不可变记录：

```
谁 · 何时 · 提交了哪个动作 · 参数是什么
· 基于什么（读取了哪些事实）· 结果如何 · 副作用有哪些 · 是否可回滚
```

> **"基于什么"这一项最关键**——它是"为什么批准/拒绝了这笔操作"的答案，也是合规审计的核心。

### 10.6 拒绝的格式（**为 Agent 而设计**）

拒绝 **MUST** 说清违反了哪条规则：

```
REJECTED cancel_order(order:12345)
  原因：前置条件不满足
  违反：order:12345 的状态为「已发货」，而 cancel_order 要求「未发货」
  依据：规则 Rule#17「已发货订单不可取消」
  建议：可执行 return_order 走退货流程          ← 可选，但对 Agent 极有价值
```

> **这一条是"可用性"的关键**——人看到报错会去问人，**Agent 只能靠自己重试**，
> 所以拒绝信息必须**足以让它自己纠正**。

**三段内容要求**：违反哪条（`I4-5` **MUST**）· 依据哪条（**MUST**）· 可行的替代动作（`I4-8` **SHOULD**，且可由 I6 发现契约兜底）。

### 10.7 周边全部用现成标准

| 要素 | 用什么 | 标准 / 模式 |
|---|---|---|
| 契约描述（OpenAPI） | **OpenAPI** | 有标准 |
| 权限判定 | **OpenFGA**（Zanzibar 模型） | 有标准 |
| 授权策略表达 | **OPA / Rego** 或 **Cedar** | 有标准 |
| 语义**策略**（五要素之一：候选集内的优选序） | ❌ **无标准** | 见 §9——**授权策略管"谁可以"，语义策略管"选哪个"** |
| 跨系统可靠写回 | **Transactional Outbox** | 成熟模式 |
| 跨系统长事务 | **Saga** | 成熟模式 |
| 审批 / 编排 | **Temporal** / Cadence | 有实现 |
| 审计事件格式 | **CloudEvents** | 有标准 |
| 幂等 | 幂等键 + 去重表 | 成熟做法 |

> **I4 的工作量 = 定义抽象模型（10%）+ 组装现成组件（90%）。**

### 10.8 为什么权限天然匹配

| 本框架 | OpenFGA |
|---|---|
| 对象 | `type` |
| 关系 | `relation` |
| 实例 | `object` |

**权限模型与本体的形状同构**，所以不需要另造一套——直接把本体里的对象与关系映射过去。

### 10.9 动作的承载格式：**旁挂声明**

> **为什么必须旁挂**：与策略同理——**Ossie 本体规范里没有动作这个概念，也没有扩展机制**
> （`ontology.md` 中 extension/custom/vendor 出现 0 次）。而 Palantir **从未公开其 Action 模型**，
> 所以没有可照抄的公开格式。

| | |
|---|---|
| **放哪** | 与 Ossie 本体文件**并列的旁挂声明**（例：`actions/<name>.action.yaml`） |
| **怎么标明出处** | 文件头 **MUST** 声明"本框架原创，无公开规范；概念参照 Palantir kinetic elements" |
| **最小字段**（对应 §10.2 的字段清单） | `name` · `namespace` · `version` · `applies_to`（作用对象）· `parameters` · `preconditions` · `effects` · `side_effects` · `idempotency` · `permissions` · `audit` · `rejection_format` |

**三条 MUST**：

| 编号 | 条款 |
|---|---|
| **ACT-1** | 动作定义 **MUST** 与 Ossie 本体文件分离存放；本体文件里 **MUST NOT** 出现动作定义 |
| **ACT-2** | 动作 **MUST** 只经 **I4 动作契约**提交，**MUST NOT** 由 I2 直接写入事实绕过它 |
| **ACT-3** | 字段名 **MUST NOT** 使用 `on`（YAML 1.1 会把它解析成布尔值，字段静默丢失）——用 `applies_to` |

## 11. 纪律条款

> 这一组是**跨要素**的纪律——不描述单个要素，而约束它们**怎么放在一起**。
> 编号 `LD-n`（LD = Layer Discipline → 现改称"纪律"）。全部可检验。

### 11.1 接入侧是条件能力

> **先接上 §16 的 `I2-G3`**：事实有**两条**写入路径——**接入路径**（外部数据）与**动作路径**（使用者）。
> 本节讲的是：**第一条是条件性的，第二条是恒在的。**

| 入口 | 触发者 | 负责什么 | 典型场景 | 恒在吗 |
|---|---|---|---|---|
| **接入路径** | **外部数据的到来** | 把**外部表示**翻译成合法事实 | 外部数据源、ERP/CRM/数仓、消息流、设备 | ❌ **条件性** |
| **动作路径** | **人 / 智能体 / 内部逻辑** | 在**内部**产生或修改事实 | 用户在界面上提交一次修改 | ✅ 恒在 |

| 编号 | 条款 |
|---|---|
| **LD-1** | 接入侧 **MUST** 被视为**条件性能力**：只在存在外部数据源时出现。**MUST NOT** 假定它必然存在 |
| **LD-2** | 接入侧缺席时，进入事实的路径**只剩动作**——此时"动作是使用者侧唯一写入通道"升级为**全局唯一路径** |
| **LD-3** | 实现 **MUST** 显式声明接入侧存在与否，**MUST NOT** 用"这部分没有内容"暗示 |

**LD-2 是个意外的收获**：接入侧缺席反而让"写入必须过规则"变得**更强、更可检验**——
有接入侧时，你要分别证明"外面来的一定过了规则"**和**"内部改的一定过了规则"；
没有接入侧时，**写入路径只剩一条，堵住它就堵住了全部**。

> **⚠️ 别把它读成"只有动作能写"**：即使接入侧在场，动作也**不是**唯一写入路径。
> 准确的说法是：**动作是"使用者侧"的唯一写入通道**（见 §16 `I2-G3` 的路径表）。

> **缺席不是缺陷，是域的属性。** 但它有代价，MUST 被记下来而不是等要用时才发现：
> 整块缺席 ⇒ 没有任何"把外部表示翻译成合法事实"的能力；
> 想接入真实数据源时，要**新做一整块**，而不是加一个适配器。

### 11.2 定义与事实 MUST 分属不同的存放单元

> §5.2 说 TBox 与 ABox 是两种**角色**。这一条把角色落成一条**可检验的纪律**。

若同一个单元既是"允许什么"又是"实际是什么"的载体，后果是可枚举的：

| 后果 | 说明 |
|---|---|
| 改定义要动数据 | **低频变更被高频数据绑住** |
| 同一份事实无法换定义投影 | 而"多投影"正是分层的理由 |
| 任何"要素 × 角色"的表都画不出来 | 只能把它塞进一格，**表格因此不准** |

| 编号 | 条款 |
|---|---|
| **LD-4** | 定义（TBox 角色）与事实（ABox 角色）**MUST NOT** 混装在同一个存放单元内；混装 **MUST** 被登记为已知偏差 |
| **LD-5** | 若因域的特性（如事实为构建期常量、与定义同生命周期）暂不拆分，**MUST** 写明**触发拆分的条件**（例：出现运行期可变事实） |

**LD-5 的意义**：不拆是可以的，但**"为什么不拆"必须是一个有条件的判断**，
而不是"一直没拆"。条件一旦成立（域变动态），拆分就从"可选优化"变成"必须做的事"。

### 11.3 契约只声明五要素，不得增设第六个

| 编号 | 条款 |
|---|---|
| **LD-6** | 契约 **MUST** 按五要素声明；**MUST NOT** 增设第六个要素（同 `ELE-1`） |
| **LD-7** | 接入侧、数据来源、使用者 **MUST NOT** 被当作要素——它们是要素**之外**的东西（§5.3） |

**为什么必须写死**：一旦允许增设，就会出现"规则产出要素""策略也是约束"这类跨要素的生产关系，
**要素之间的边界随之失效**——而边界一旦失效，三条切割线就全塌了。

>

## 14. 六个契约

| # | 名称 | 谁调谁 | 方向 | 契约核心 | 现有标准 |
|---|---|---|---|---|---|
| **I1** | **语义契约** | 任何方 → 定义 | 读 | 读定义，定义不可变 | ✅ **Ossie** |
| **I2** | **事实契约** | 映射引擎 / 动作引擎 → 事实 | 读+写 | **写入必须过规则**（只有两条写入路径） | ⚠️ GQL（**格式可用，语义需补**） |
| **I3** | **查询契约** | 使用方 → 读路径 | 读 | **结果必须可追溯** | ⚠️ MCP（**接入可用，溯源需补**） |
| **I4** | **动作契约** | 使用者 → 动作路径 | 写 | **使用者侧唯一写入通道** | ❌ **无** |
| **I5** | **接入契约** | 外部数据源 → 接入侧 | 入 | 契约先于数据 | ✅ **ODCS** |
| **I6** | **发现契约** | 任何方 → 全域 | 读 | **不知道有什么时能列出来** | ❌ 无 |

> **"谁调谁"这一列用架构位置描述（§0.4），不用 `L1`~`L6`**——后者只是处理环节的简写（`LD-8`）。

### 14.1 契约 × 五要素：谁负责读哪些要素

**这张表是第二、四部分之间的桥**——它回答"五要素到底由谁读写"。

| 五要素 | 由谁**声明** | 谁**读**它 | 谁**写**它 |
|---|---|---|---|
| **对象** | 契约文件（人工/工具） | **I1**（读定义）· I3（读实例） | ❌ 只读——定义不可原地改（`I1-G1`） |
| **关系** | 契约文件 | **I1** · I3（遍历） | ❌ 只读 |
| **规则**（约束式） | 契约文件 | **I1**（`GetConstraints`） | ❌ 只读 |
| **规则**（派生式） | 契约文件 | **I1**（`GetDerivations`） | ❌ 只读 |
| **派生对象** | —（规则算出） | **I3** 求值（带 `via` 溯源） | ❌ **不落库**（`I2-4`） |
| **策略** | 契约文件（旁挂） | **I1 / I6**（读声明）· **I3**（取合法候选） | ❌ 只读——求值方＝落地方，**落地必经 I4**（`SP-4`/`SP-5`） |
| **动作** | 契约文件 | **I4 / I6**（读契约） | **I4** 提交（**唯一写入通道**） |
| **实例与事实** | —（运行期产生） | **I2** · I3 · I6 | **I2**，且只有两条路径（接入 / 动作，`I2-G3`） |
| **映射**（数据来源 → 对象） | 接入契约 | — | **I5**（声明式，不是要素） |

**三条从这张表直接读出来的结论：**

| # | 结论 | 含义 |
|---|---|---|
| 1 | **五个要素全部是"读多写无"** | 定义的变更**不经过任何契约**，走治理流程（§1.2）。这就是"不开放就地修改"在契约层的体现 |
| 2 | **只有动作与事实能改变状态** | 其余要素与派生对象都是只读的——与 §5.3 切割线一致（规则、策略 MUST NOT 产生状态变更） |
| 3 | **映射不是要素，是一条契约** | 它描述"数据怎么变成对象"，归 I5；把它当第六个要素是常见误解 |

> **⚠️ 一个必须点明的缺口**：表中"五个要素由谁**声明**"一列写的是"契约文件"，
> 但契约清单里**没有一个"改定义"的契约**——这是**刻意的**（定义不可原地改）。
> 代价是：**变更的执行通道没有被规范指定**。参考做法是用"Git 里的 YAML + PR 评审"充当这个通道（见 `CONTRIBUTING.md` 的变更流程），
> 但那是**实现选择**，不是本框架的规范要求。**这是本部分最值得补的一条。**

**一句话看懂：**

> **六个契约里，两个有完整标准（I1、I5），两个需要补一条关键约束（I2、I3），
> 两个需要原创（I4、I6）。**
>
> **要发明的只有两个，其余全是选型和组合。**

## 15. I1 语义契约

**方向**：只读（定义由治理流程写）

> **⚠️ 上表的 `GetXxx` 操作名是本框架自定的**（Ossie 只定义**字段**，不定义 API）。
> 它们**内嵌了 Ossie 的字段名**（`concept` / `relationships` / `ontology_mappings`），这样名字本身能提示对应哪个字段——
> **但别把它们当成 Ossie 规定的接口**。I1 的具体操作名属实现选择。

| 操作 | 输入 | 输出 |
|---|---|---|
| `GetConcept(name)` | 对象名 | 属性、层次、接口、规则 |
| `ListRelations(concept)` | 对象名 | 该对象下的关系（含角色、基数） |
| `GetConstraints(target)` | 对象/关系名 | 适用的规则表达式 |
| `GetDerivations(target)` | 对象/关系名 | 派生式规则 |
| `GetActions(concept)` | 对象名 | 可对该对象执行的动作 |
| `GetMappings(concept)` | 对象名 | 字段 → 对象的映射规则 |
| `GetVersion()` | — | 当前定义版本 |
| `Diff(v1, v2)` | 两个版本 | 差异（供影响分析用） |

**保证：**

| # | 保证 | 为什么重要 |
|---|---|---|
| **I1-G1** | **定义不可变** | 一经发布只能新增版本，不能原地改 → 让回溯和撤回成为可能 |
| **I1-G2** | **读取一致** | 同一次操作内读到的定义来自同一版本 |
| **I1-G3** | **可自检** | 定义本身可被校验（环、悬空引用、冲突） |
| **I1-G4** | **可差异对比** | 任意两版本可算出差异 → 影响分析的前提 |

### 15.1 Ossie 的已知表达力缺口（**实测，非推测**）

> 本框架把 I1 押在 Ossie 上，所以 **Ossie 表达不了什么，就是本框架表达不了什么**。
> 下面两条来自**对上游文件的实测核验**，不是阅读理解。

**核验依据（可复核）**：

| 断言 | 依据 |
|---|---|
| `multiplicity` 只有两个取值 | 上游 `ontology/ontology.json` 的枚举为 `["ManyToOne", "OneToOne"]`；用该 schema 实测 `OneToMany` 报错原文 `'OneToMany' is not one of ['ManyToOne', 'OneToOne']` |
| `requires` / `derived_by` 不求值 | 上游 `validation/validate.py` 只在载荷含 `semantic_model` 时才跑 SQL/引用检查（本体文档只过 JSON Schema）；而 schema 里 Expression 仅定义为 `{"type":"string"}`——**有类型、无语法** |

| 缺口 | 现象 | 后果 |
|---|---|---|
| **无 `OneToMany`** | 只接受 `ManyToOne` / `OneToOne` | **一对多只能借 `ManyToOne` 表达**。"一个会话含多个槽位"这类最常见的基数无法精确声明，各实现只能各自发明绕法 → 互操作从定义层就断了 |
| **`requires` / `derived_by` 不执行** | validator 只校验"是字符串/结构"，不求值 | 约束的**实际强制点被迫下沉到实现**（见 I4 `ST-4`）。规范上写着、跑起来不生效 —— 这正是"声明式"最容易骗人的地方 |

**这两条的应对（本框架的立场）**：

1. **不自行扩展 Ossie 的语法**。加一个自定义字段很容易，但那就不是"用标准"，
   而是"借标准的名字发自己的标准"——比一开始就自研更糟。
2. **缺口 MUST 被显式记录**（就是本节的用途），且实现 MUST 在**自己的校验器**里补上强制点，
   MUST NOT 假设"写在 YAML 里就等于生效"。
3. **一旦 Ossie 补上，本框架的对应绕法 MUST 被移除**，而不是留着"兼容"。
   留着兼容 = 永久保留两套语义。

> **判据**：若某个对象只能用绕法表达，那么在跨实现比对时，它 **MUST** 被视为
> "**未被标准覆盖**"的部分——即：这部分的一致性是巧合，不是保证。

## 16. I2 事实契约

**方向**：读 + 写（写**只经两条路径**，见 `I2-G3`）

| 操作 | 调用方 | 说明 |
|---|---|---|
| `GetInstance(concept, id)` | 读路径 / 动作引擎 | 取一个实例 |
| `ListFacts(pattern)` | 读路径 | 按模式取事实 |
| `WriteFact(fact)` | **仅动作引擎**（内部原语，见 §17.1） | 写入一条事实 |
| `DeleteFact(fact)` | **仅动作引擎**（内部原语） | 删除一条事实 |

> **⚠️ 调用方用角色描述，不用 `L1`~`L6`**（`LD-9`）。
> **接入路径不走本表**——它是映射引擎按 I5 声明的映射直接写入事实存放的，同样要过规则（`I2-G1`）。

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **I2-G1** | **写入必须过规则** ⭐ | 任何写入（**两条路径都算**）必须已通过规则校验，失败即拒绝且**无副作用** |
| **I2-G2** | **写入必须带来源** | 每条事实 **MUST** 记录它的**产生者**：哪次动作提交，或哪个数据源（+ 时间） |
| **I2-G3** | **只有两条写入路径** ⭐ | ①**接入路径**：外部数据经**映射引擎**写入；②**动作路径**：使用者经 **I4** 写入。**除此之外没有第三条路** |
| **I2-G4** | **派生事实不落库** | 推出的结论是视图，不是事实 |

> **⚠️ 这一组是本框架最容易被实现走形的地方，所以必须说死：**
>
> | 谁 | 能写吗 | 走什么 |
> |---|---|---|
> | **外部数据源** | ✅ 能 | 经**映射引擎**（I5 声明的映射）→ 写入即过规则（`I2-G1`） |
> | **人 / 智能体 / 业务应用** | ✅ 能 | **只能经 I4 动作契约**（`I4-G1`、`WR-1`） |
> | **查询方**（L4 / L6） | ❌ 不能 | 一律只读（`I2-2`） |
> | **任何绕过上面两条的直写** | ❌ 不能 | 视为违规实现（`WR-3`） |
>
> **"动作是唯一写入通道"这句话的准确版本是**：
> **动作是"使用者侧"的唯一写入通道**——因为另一条路径（接入）不由使用者发起，而是由外部数据的到来触发。
> 两者都**必须过规则**，都**必须可溯源**。

### 16.1 ⚠️ 这里需要补的约束

> **GQL / Cypher 定义了"怎么写"，但没有定义"写入必须过规则"。**
>
> **本框架在 GQL 之上加一条：任何 `WriteFact` 必须原子地包含规则校验，失败即拒绝。**
>
> 这一条把图数据库从"能写的存储"变成"**受治理的事实层**"。

## 17. I3 查询契约

**方向**：只读

| 操作 | 说明 |
|---|---|
| `Query(pattern)` | 按模式查事实 |
| `Traverse(from, relation, depth)` | 多跳遍历 |
| `Infer(query)` | 含派生事实的查询 |
| `Search(text)` | 向量 / 全文检索，返回入口实例 |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **I3-G1** | **只读** | 查询契约**永不产生写入** |
| **I3-G2** | **可追溯** ⭐ | 每条返回的事实必须带来源：是存的，还是推出来的；推出来的依据是什么 |
| **I3-G3** | **权限过滤** | 结果必须已按调用者权限过滤 |
| **I3-G4** | **预算可限** | 支持限制返回量（节点数 / token 数）——**为 Agent 设计** |

### 17.1 【关键】I2 的写操作是 I4 的内部原语，不是第二条写入通道

> **这一节专门消一个矛盾**：§16 的 I2 暴露了 `WriteFact` / `DeleteFact`，
> 而 §10.1 与 `ELE-8` 说"**只有动作能改变状态**"。两者看起来打架。**不打架，但必须说清边界。**

| 角色 | 谁能调 | 说明 |
|---|---|---|
| **使用者**（人 / 智能体 / 业务应用） | **只能**走 **I4 动作契约** | 对外**只有一条**写入通道 |
| **I4 动作引擎** | 在执行动作的效果阶段，可调 I2 的 `WriteFact` / `DeleteFact` | 它们是**内部原语**，且**MUST** 在同一事务、同一快照内调用 |

**三条 MUST**：

| 编号 | 条款 |
|---|---|
| **WR-1** | `WriteFact` / `DeleteFact` **MUST NOT** 对使用者暴露；它们**只能**由动作引擎在效果阶段调用 |
| **WR-2** | 经 I2 写入的每一条事实 **MUST** 可回溯到它的产生者：**一次动作提交**（动作路径）或**一个数据源**（接入路径）——与 `I2-G2` 一致 |
| **WR-3** | 任何绕过 I4、直接经 I2 写入的路径 **MUST** 被视为违规实现 |

> **为什么值得单列一节**：如果这条边界不写死，"动作是使用者侧唯一写入通道"就只是一句口号——
> 实现者完全可以把 I2 当公开的写接口用，于是规则校验、权限、审计**全都可以绕过去**。
> **这正是本框架最容易被实现走形的地方。**

### 17.2 ⚠️ 这里需要补的约束

> MCP 定义了"怎么把工具暴露给 Agent"，**但没有定义"结果必须可追溯"**。
>
> **本框架加一条：`Infer` 的每条派生结果 MUST 带 `via` 字段，标明由哪条规则、从哪几条事实推出。**
>
> **这是让 LLM 的结论可验证的关键**——它必须能引用具体事实，而不是只给结论。

**实现示例（`dsh-ontology` 的做法）：**

```
api depends_on pg (inferred: transitive)
                      ↑ via 字段
```

## 18. I4 动作契约

**方向**：写 · **现有标准**：❌ 无

> **本框架唯一需要原创设计的核心部分。**

> 📄 **实现规范见 [`spec/i4-action-minimal.md`](../spec/i4-action-minimal.md)（v0.2.4）。**
>
> 该规范**逐步收窄范围**：v0.1 只做**单实例 · 同步 · 无副作用 · 有审计**；
> v0.2 已加入**多实例原子效果**；异步执行、声明式副作用、长事务补偿仍留给后续版本。
>
> **本节的边界**：只讲**这个契约的接口行为与保证**。
> **动作契约的字段清单在 §10.2**（那里是唯一真源）；**具体条款以该规范为准**。

**保证（I4-G1~I4-G5）——这一组回答"这个契约答应你什么"：**

| # | 保证 | 说明 |
|---|---|---|
| **I4-G1** | **唯一写入通道** ⭐ | 使用者的任何状态变更 **MUST** 经 I4 提交；I2 的 `WriteFact`/`DeleteFact` 只是 I4 的内部原语（`WR-1`~`WR-3`） |
| **I4-G2** | **原子** | 一次提交内：参数 → 权限 → 前置条件 → 效果写入**同一事务**；任一步失败 **MUST NOT** 部分生效 |
| **I4-G3** | **可审计** | 每次提交 **MUST** 产生不可变记录，且 **MUST** 含"基于哪些事实"（读了什么、什么快照） |
| **I4-G4** | **可自纠** | 拒绝 **MUST** 说清违反哪条规则、依据哪条，并 **SHOULD** 给出可行替代（为智能体而设计） |
| **I4-G5** | **幂等** | **MUST** 支持幂等键；重放 **MUST** 返回原结果，**MUST NOT** 重复执行**效果** |

> **⚠️ 这一组为什么以前缺**：其余五个契约（I1/I2/I3/I5/I6）都有 3~4 条具名保证，
> **只有 I4 没有**——它是唯一"没有公开标准可依、要自己设计"的契约，
> 于是条款（`ST-`/`AT-`/`AU-`/`RP-`/`BD-`/`MI-`/`NL-`/`XAD-`/`DF-`/`FD-`…）又多又碎，
> **读者看不到"这个契约到底答应我什么"的总览**。v0.4 补上这一组。
>
> **这不是装饰**：一份动辄几十条零散条款的契约，如果没有具名保证，
> 实现者会挑着做，而验收者无从判断"做到什么算够"。

### 18.1 【关键】一致性读路径与 R1~R4

> **动作在提交前必须能"看到正确的世界"。** 前置条件的求值不能靠直读事实存放——
> 那是 v0.1 的错误（"动作直调事实层"），它掩盖了真实的设计复杂度。

**为什么不能直读：**

| 需求 | 为什么 | 直读能满足吗 |
|---|---|---|
| **事务内一致读** | 读到的状态必须与执行时的状态一致，否则前置条件失效 | ⚠️ 不一定 |
| **能读到派生事实** | 前置条件常需派生值（如"客户订单总额"） | ❌ 不能（派生不在事实存放里） |
| **带权限上下文** | 读本身也要受权限约束 | ❌ 不能（事实存放不认识权限） |

**修正后的设计：动作执行阶段使用一条专用的「一致性读路径」**

```
I4 动作提交
   │
   ├─→ 一致性读路径（专用）
   │     · 事务内快照读（保证前置条件与执行同源）
   │     · 可读派生事实（在事务快照上现算）
   │     · 带调用者权限上下文
   │
   └─→ 写入路径（经 I2 的写操作，见 §17.1）
         · 写前过规则校验
         · 写后记审计
```

**这条路径 MUST 满足（`R1`~`R4`）：**

| # | 要求 | 理由 |
|---|---|---|
| **R1** | **快照一致** | 前置条件读到的状态 = 执行时的状态 |
| **R2** | **可读派生** | 否则写不出"总额超限"这类前置条件 |
| **R3** | **带权限上下文** | 否则动作能读到调用者无权看的数据 |
| **R4** | **不产生副作用** | 它只是读，不能触发任何写 |

> **`R1`~`R4` 是 `I4-7` 的验收依据**，也是 `spec/i4-action-minimal.md` 里"前置条件求值 MUST 在同一快照上"的上位要求。
>
> **⚠️ 历史更正**：`R1`~`R4` 原本定义在旧的「分层视图」里，v0.4 删那一节时**误删了这里的定义**，
> 却留着 `I4-7` 对它的引用（成了悬空引用）。现已移回本节。

### 18.2 拒绝的格式（**为 Agent 而设计**）

拒绝 MUST 说清违反了哪条规则：

```
REJECTED cancel_order(order:12345)
  原因：前置条件不满足
  违反：order:12345 的状态为「已发货」，而 cancel_order 要求「未发货」
  依据：规则 Rule#17「已发货订单不可取消」
  建议：可执行 return_order 走退货流程          ← 可选，但对 Agent 极有价值
```

> **这一条是"可用性"的关键**——人看到报错会去问人，**Agent 只能靠自己重试**，
> 所以拒绝信息必须**足以让它自己纠正**。

### 18.3 周边全部用现成标准

| 要素 | 用什么 | 标准 / 模式 |
|---|---|---|
| 契约描述（OpenAPI） | **OpenAPI** | 有标准 |
| 权限判定 | **OpenFGA**（Zanzibar 模型） | 有标准 |
| 授权策略表达 | **OPA / Rego** 或 **Cedar** | 有标准 |
| 语义**策略**（五要素之一：候选集内的优选序） | ❌ **无标准** | 见 §5——这是策略与"授权策略"的区别：**授权策略管"谁可以"，语义策略管"选哪个"** |
| 跨系统可靠写回 | **Transactional Outbox** | 成熟模式 |
| 跨系统长事务 | **Saga** | 成熟模式 |
| 审批 / 编排 | **Temporal** / Cadence | 有实现 |
| 审计事件格式 | **CloudEvents** | 有标准 |
| 幂等 | 幂等键 + 去重表 | 成熟做法 |

> **I4 的工作量 = 定义抽象模型（10%）+ 组装现成组件（90%）。**

### 18.4 为什么权限天然匹配

| 本框架 | OpenFGA |
|---|---|
| 对象 | `type` |
| 关系 | `relation` |
| 实例 | `object` |
| 事实 | `relationship tuple` |

**推论：授权模型可以从 L3 的定义自动生成，且"权限沿业务关系继承"是原生的。**

## 19. I5 接入契约

**方向**：入

| 操作 | 说明 |
|---|---|
| `DeclareContract(source)` | 声明数据源的数据契约 |
| `ValidateContract(source)` | 校验上游是否满足契约 |
| `Ingest(source, mode)` | 摄取（增量 / 全量） |
| `Quarantine(badRecords)` | 拒收不合规记录 |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **I5-G1** | **契约先于数据** | 没有契约的数据源不得接入 |
| **I5-G2** | **不合规即拒收** ⭐ | **绝不自动清洗**——隔离等人来修 |
| **I5-G3** | **拒收可解释** | 说清违反了契约的哪一条 |
| **I5-G4** | **身份先于属性** | 实例身份必须能稳定解析 |

### 19.1 最强的一条原则

> **不指望数据干净，指望入口干净。**
>
> **不合规的数据不是"清洗掉"，是"隔离出来逼人解决"。**
> 自动清洗是错误放大器——它把业务问题藏起来，而且越藏越深。

**格式**：**ODCS（Open Data Contract Standard，Bitol / Linux Foundation）**——直接采用。

## 20. I6 发现契约

**方向**：只读 · **现有标准**：❌ 无

**v0.1 的缺陷**：只有"已知名字去查"（`GetConcept(name)`），
**没有"我不知道有什么，先列一遍"**。

**为什么这是刚需：**

| 场景 | 需要什么 |
|---|---|
| 新系统接入 | 有哪些域？各提供什么？ |
| 新 Agent 上线 | 我能用什么对象、什么动作？ |
| 跨域对接 | 对方的"订单"和我的能不能对上？ |
| 影响分析 | 改这个对象会影响谁？ |

| 操作 | 说明 |
|---|---|
| `ListDomains()` | 列出所有域 |
| `ListConcepts(domain, filter)` | 列出对象（可按标签/关键词过滤） |
| `ListActions(concept)` | 列出可用动作 |
| `DescribeCapability(name)` | 描述一个能力的完整契约 |
| `FindByCapability(need)` | **按需求找能力**（"我需要一个能取消订单的动作"） |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **I6-G1** | **可枚举** | 域、对象、动作必须可被完整列出 |
| **I6-G2** | **权限过滤** | 只列出调用者有权知道的 |
| **I6-G3** | **自描述** | 发现的结果本身符合标准格式 |

> **在中央式架构里，发现机制是"对齐"的入口——新系统靠它知道该向什么对齐。**

## 21. 契约 × 现有标准对照

| 契约 | 直接采用 | **本框架需要补的** |
|---|---|---|
| **I1 语义** | **Ossie YAML** | 运行态 API 四条保证（G1~G4） |
| **I2 事实** | **GQL**（ISO/IEC 39075:2024） | ⭐ **写入必须过规则**；只有两条写入路径（`I2-G3`） |
| **I3 查询** | **MCP** | ⭐ **结果必须可追溯**（`via` 字段）；预算可限 |
| **I4 动作** | OpenAPI / OpenFGA / Outbox / Saga / CloudEvents | ⭐ **抽象模型全套** |
| **I5 接入** | **ODCS** | 拒收区与身份解析的实现约定 |
| **I6 发现** | — | ⭐ **能力模型全套** |

**这就是本框架的"贡献清单"：**

> **两条必须补的约束（`I2-1`、`I3-2`）**
> **两个必须原创的模型（I4、I6）**
> **其余全是选型和组合。**

## 22. 模块清单与可替换性

> 📄 **本节的"模块只列了清单，没定纪律"。**

| **身份解析** | **接入侧** | 实体消解 | **中**（依赖数据特征） |

| **查询引擎** | **读路径** | 模式查询、遍历 | 高 |
| **推理引擎** | **读路径** | 派生规则求值 | 中 |
| **检索引擎** | **读路径** | 向量 / 全文 | 高 |
| **动作引擎** | **动作路径** | 动作提交与执行（**使用者侧唯一写入通道**） | **低（本框架定义）** |
| **策略求值** | **决策执行方**（本体空间之外） | 在规则筛出的候选集内排序、给出选中项（`SP-4`） | **低（本框架定义）** |
| **发现服务** | **本体空间** | 目录与能力检索 | 中 |
| **授权引擎** | **切面** | 权限判定 | **高（OpenFGA 已标准化）** |
| **审计日志** | **切面** | 不可变记录 | 高 |
| **契约网关** | **使用者侧** | 对外 API / MCP | 高 |
| **治理工作流** | **治理** | 提案、评审、发布 | 中 |

> 因为 `L1`~`L6` 只是**处理环节的简写**，把它当表头会让人以为它是架构分层（违反 `LD-8`）。

# 第五部分 · 合规等级

---

## 23. 五级阶梯 × 三种剖面

```
Level 4  可运营   + 全部切面（合规删除、成本、SLA、治理流程）+ 接入契约（I5）
   ↑
Level 3  可治理   + 授权 + 审计 + 版本
   ↑
Level 2  可写     + 动作契约（I4）          ← ⭐ 分水岭
   ↑                  （若声明策略，须同时满足 SP-4~SP-7：求值方＝落地方）
Level 1  可读     + 事实 + 查询 + 发现契约
   ↑
Level 0  可声明   + 语义契约（I1）           ← Ossie 已给
```

> **⚠️ `I5`（接入契约）挂在哪一级？**
> 它**不是必达项**——因为**接入侧是条件性能力**（`LD-1`：只在存在外部数据源时才有）。
> **不接外部数据源的实现，可以完全不实现 I5 而仍然合规。**
> **一旦接入外部数据源，I5 即为必达**，且该实现按接入规模归入 **L4**（可运营）。
>
> **这条以前没写**，导致"只做 I1~I4+I6 也能声称 L4"——现已明确：
> **声称 L4 的实现，若它接入了外部数据源，就必须实现 I5。**

> **策略在哪一级**：策略是**条件式**的——不声明策略的实现**不因缺少策略而降级**（§9.7）。
> 但**一旦在 L2 及以上声明了策略**，就必须同时满足 `SP-4`~`SP-7`（求值方与落地方同一、经 I4 落地、写明求值时机）；
> **L0/L1 只读的实现不得声明策略**（`SP-7`）——因为它没有落地的能力（没有 I4）。

| Profile | 目标等级 | 必须实现 |
|---|---|---|
| **A · 轻量** | **L0**（+ **I6** 才到 L1） | I1 + I2 + I3 |
| **B · 组织** | L0 ~ L3 | I1~I4 + I6 + 审计 |
| **C · 严格** | L0 ~ L4 | **全部六个契约 + 全部治理机制** |

> **⚠️ 注意 L1 的门槛里含 `I6`**：`I1+I2+I3` 只够 **L0**；
> **列出不来"有什么"，就算不上"可读"**——这是本节与 §3 剖面表曾经不一致的地方，
> 现已对齐（Profile A 若不做 I6，就诚实地只声称 L0）。

> **Level 1 → 2 是分水岭：以下只能"看"，以上才能"安全地改"。**
> **绝大多数开源方案停在 Level 1。**

## 24. 验收标准

| 级别 | 必须满足 | 验收方法 |
|---|---|---|
| **L0** | 能用 Ossie YAML 描述本域对象、关系、规则（含派生式） | 通过 Ossie 校验器 |
| **L1** | 按 I1 读定义；按 I2 读事实；按 I3 查询（含派生，带 `via`）；按 I6 发现 | 给定事实集，能答出派生问题并给出依据 |
| **L2** | 按 I4 提交动作；**写入必须过规则**；拒绝可解释 | ✅ **"该被拒绝的样本集"全部被拒，且拒绝原因正确** |
| **L2 + 策略**（条件式） | 若声明了策略，另须满足 `SP-4`~`SP-6` | 给出一次真实的策略判定：**能说清候选从哪来、为何选它、由谁把它提交成了动作** |
| **L3** | 授权 + 审计 + 版本 | 能回答"谁在何时基于什么做了什么"；能回滚定义 |
| **L4** | 合规删除 + 成本计量 + SLA + **治理流程**；**若接入了外部数据源，另须实现 I5 接入契约** | 能执行一次跨存储实体删除并验证无残留；能跑通一次变更提案 |

**跨级别的两组条款——它们不挂在某一级上，而是"采用即生效"：**

| 条款组 | 何时生效 | 验收方法 |
|---|---|---|
| **纪律条款 `LD-1`~`LD-9`** | **任何级别都生效**（与能力等级无关） | ① 接入侧存在与否**被显式声明**（`LD-3`）<br>② 定义与事实**分属不同存放单元**；若未拆，**写明了触发拆分的条件**（`LD-4`/`LD-5`）<br>③ 契约里**没有第六个要素**；接入/来源/使用者**没有被当作要素**（`LD-6`/`LD-7`）<br>④ **能指出接入侧在何处**（或明确声明其缺席）—— `LD-1`<br>⑤ **能演示"接入侧缺席时事实只能由动作产生"**（关掉接入侧，看还有没有别的写入路径）—— `LD-2`<br>⑥ **文档与实现里没有把 L1~L6 当架构分层的表述** —— `LD-8`<br>⑦ 对外材料一律用五要素/契约的措辞 —— `LD-9` |
| **治理条款 `G-1`~`G-7`** | 从 **L3** 起生效（L0~L2 单方自用，可豁免） | ① 每个定义项**有命名空间**（`G-1`）<br>② 定义**不可原地改**，改动**产生新版本**（`G-2`）<br>③ 改语义时**新建**而非复用旧名（`G-3`）<br>④ 破坏性变更**有弃用期**（`G-4`）<br>⑤ 能算出**一次变更的影响面**（`G-6`）<br>⑥ **导出物能脱离本实现被解析**（换一份实现或独立解析器读一遍）—— `G-5`<br>⑦ **定义文件里没有对扩展层的引用** —— `G-7` |

> **⚠️ 为什么必须把这两组单列**：v0.4 之前，§24 的验收表**只覆盖六个契约**——
> **治理条款与纪律条款没有任何对应的验收方法**。
> 而 §25 前言声称"声称合规的实现必须满足"全部条款——**两者对不上**。
> 单列之后，"哪些条款在哪一级生效、怎么验"才是闭合的。
>
> **为什么纪律条款"任何级别都生效"**：`LD-1`~`LD-9` 约束的是**结构纪律**
> （接入侧是否存在、定义与事实是否分离、有没有增设第六要素），与"实现到哪一级"无关——
> **L0 的一个只读声明也必须满足它们**。

> **⚠️ 策略的验收为什么要单列一行**：策略是**条件式**的（不声明就不降级），
> 但它**一旦声明**就必须能验收——否则"声明了策略"这件事本身没有代价，也没有保障。
> 它的验收不看"算法好不好"（那是实现自由），**只看归属是否闭合**：
> **候选从哪来 · 为何选它 · 由谁落地**。

### 24.0 两类门禁：运行期与构建期，**两者都要**

> **⚠️ 本节曾自陈"缺构建期门禁"——那个缺口已经跨文档闭合。**
> 这里把两类门禁的关系讲清，并指出构建期门禁的规范在哪。

**运行期门禁**（本节 §24.1~§24.2 讲的就是这个）：系统跑起来之后，喂它脏数据、看会不会被拒。

**但实现本身也会烂掉**：术语被拷贝进各模块、依赖变成隐式、文档与代码脱节、
编码在某条工具链下被读错。**这些用运行期门禁查不出来**——所以还要构建期门禁。

| | 构建期门禁 | 运行期门禁 |
|---|---|---|
| 何时跑 | 提交前 / 持续集成 | 每次写入 |
| 拦什么 | 违反纪律的**代码与文档** | 违反规则的**数据与操作** |
| 覆盖 | ✅ [`spec/module-discipline.md`](../spec/module-discipline.md) §4 | ✅ 本节 §24.1~§24.2 |

**构建期门禁的最小集合是五项**（编码 / 引用 / 依赖 / 契约 / 组装），
并带四条强制要求（一条命令跑完 · 非零退出码 · 阻断合并 · 离线可跑）——
见 **[`spec/module-discipline.md`](../spec/module-discipline.md) §4**（`BT-1`~`BT-4`）。

> **两者都要。** 只做运行期，实现会慢慢烂掉；只做构建期，脏数据会进去。
>
> **本仓库自己就以身作则**：它没有实现任何软件，但仍给自己配了一道**文献自检闸**
> （[`tools/audit.py`](../tools/audit.py)：锚点 · 引用 · 条款编号唯一性 · 编码），
> 因为**规范本身也是文档，也会烂**。详见 [`tools/README.md`](../tools/README.md)。

### 24.1 最便宜也最有效的验收方法

> **建一个"该被拒绝的样本集"：收集 100 条应该被系统拒掉的数据/操作**
> （非法关系、超范围值、无权限、会形成环……），做成测试，每次改规则跑一遍。

**同时做到三件事：**

1. 验证规则没写错
2. 验证拒收真的生效（不只是写在文档里）
3. 防止改规则时把原来能拒的搞坏了（回归测试）

**这是 L2 验收的核心手段，几乎零成本。**

### 24.2 加规则的安全姿势

```
第 1 步：新规则写成"只记录，不拦截"
第 2 步：跑一段时间，看它会拒掉什么
第 3 步：人工审这份"本该被拒"的清单
        ├─ 都是真该拒的 → 改成强制拦截
        └─ 有误伤的   → 先修规则，别上线
第 4 步：上线，保留清单做回归测试
```

# 第六部分 · 规范条款（Normative）

> **v0.2 新增。** MUST / MUST NOT / SHOULD 是**规范性**的——
> 声称合规的实现**必须满足**；**验收主体是采用者自己**：
> 按条款逐条对照自己的实现，并对照 §23 的合规等级声明做到哪一级。
> 与**第七部分**的实施指南（Informative）严格区分。
>
> **⚠️ 条款编号是"文档内唯一"，不是"全局唯一"**：`S-1` 在 I4 规范与《模块纪律》里
> 指的是两条不同的条款。**跨文档引用时必须带上文档名**（如"I4 `ST-1`"、"《模块纪律》`S-1`"）。
> 每份 spec 的头部都列了**本规范自有条款前缀**，引用前先看那张表。
> 框架自身的条款前缀：`Ix-n`（契约条款）· `Ix-Gn`（契约保证）· `G-n`（治理）· `LD-n`（纪律）· `ELE-n`（五要素）· `AG-n`（Agent-first）· `SP-n` / `ACT-n` / `WR-n`（策略/动作承载、写入边界）。
> **完整对照见 §5.1.1 代号解码表。**

## 25. MUST / MUST NOT / SHOULD 清单

### 25.1 治理

| # | 条款 |
|---|---|
| G-1 | 每个定义项 **MUST** 属于某个命名空间 |
| G-2 | 定义一经发布 **MUST NOT** 被原地修改，变更 **MUST** 产生新版本 |
| G-3 | 改变语义时 **MUST** 新建对象，**MUST NOT** 复用旧名 |
| G-4 | 破坏性变更 **MUST** 提供弃用期 |
| G-5 | 核心层定义 **MUST** 支持完整导出，格式 **MUST** 独立于实现 |
| G-6 | 变更 **MUST** 可自动计算影响面 |
| G-7 | 核心层 **MUST NOT** 引用任何扩展层 |

### 25.2 五要素（对象 · 关系 · 规则 · 策略 · 动作）

| # | 条款 |
|---|---|
| ELE-1 | 契约 **MUST** 按五要素声明；**MUST NOT** 增设第六个要素 |
| **ELE-1a** | **对象 MUST 声明**：标识方式 · 类型（实体/值）· 层次（extends）· 属性；**值类型 MUST 最终落到内建类型** |
| **ELE-1b** | **关系 MUST 声明**：角色 · 基数（`multiplicity`）· **`verbalizes`**（人可读表述）。缺 `verbalizes` 的定义 **MUST** 被视为不完整 |
| **ELE-1c** | 定义 **MUST NOT** 混装定义与事实（见 `LD-4`）；**MUST NOT** 把实例写进定义文件 |
| ELE-2 | 规则 **MUST** 以两种形式之一声明：**约束式**（Ossie `requires`）或**派生式**（Ossie `derived_by`） |
| ELE-3 | **解析归入规则**：派生式声明的产物 **MUST** 是派生对象（对象侧），**MUST NOT** 被当作独立要素或独立存储 |
| ELE-4 | **若实现声明了策略**，策略 **MUST** 显式声明其**依据的规则集**（论域 = 该规则集筛出的合法候选集） |
| ELE-5 | **若实现声明了策略**，策略 **MUST NOT** 改变合法性判定（值域只有序与选中项，**MUST NOT** 输出合法与否） |
| ELE-6 | **若实现声明了策略**，每个策略判定 **MUST** 携带选择依据（对应 `I3-2` 的溯源精神） |
| ELE-6a | **若实现声明了策略**，策略的**求值与输出落地 MUST 有明确归属**：由谁求值、由谁把选中项变成动作提交——**MUST NOT 悬空**（见 §9.9） |
| ELE-7 | 「策略」与「授权策略」**MUST** 分列：前者问"选哪个"（要素），后者问"谁可以"（I4 权限） |
| ELE-8 | 规则与策略 **MUST NOT** 产生状态变更；**产生状态变更的声明 MUST 属于动作** |

> **条款背后的理由都在 §5.5（三条切割线）与 §5.2（TBox/ABox 是角色）** —— 本节只列可验收的要求，不重复论证。
>
> **ELE-4~ELE-6a 是条件式的，这是有意的**：不声明策略的实现（如仅做校验与派生的实现）**不因缺少策略而不合规**——"没有优选需求"是合法状态。但**一旦声明**，就必须满足论域、值域、依据、**归属**四条，否则策略会退化成"用规则的口吻表达偏好"，或者**变成一个没人执行的悬空声明**。
>
> **`ELE-1a`/`ELE-1b` 为什么补**：对象与关系是五个要素里**最"有标准可依"**的两个（格式全来自 Ossie），
> 却一直**没有任何专属的可验收条款**——只有"按五要素声明"这种笼统要求。
> 补上之后，**五个要素各自都有可验收的条款**，不再有"轻量要素"。

> **ELE-1 与 ELE-3 是一起读的**：五要素里没有"派生"，因为派生的声明归规则、产物归对象。若把派生单列成要素，就会出现"规则产出要素"这种跨要素的生产关系，要素间的边界随之失效。
>
> **ELE-8 是"联动"的归宿**：凡"改一个参数、相关参数跟着变"这类声明，都不可能是规则或策略（两者都不产生状态变更），只能是动作的效果，或派生对象的重新求值。

# 第七部分 · 实施指南（Informative）

## 26. 四阶段路线

### 阶段一：跑通一条链路

```
Ossie 定义 3~5 个对象 → 灌数据（**接入路径**，先手工）→ SQL 查询 → 1 个动作（**动作路径**）→ 1 个 MCP 工具
```
**交付物**：能演示"定义 → 事实 → 查询 → 动作 → Agent"的最小系统。

### 阶段二：补治理

```
数据契约（ODCS）+ 拒收区 + 身份解析（先规则）
```
**交付物**：一个数据源稳定接入，脏数据被隔离而非污染。

### 阶段三：补权限与审计

```
OpenFGA + 审计表 + CloudEvents
```
**交付物**：能回答"谁在何时基于什么做了什么"。

### 阶段四：补治理流程与规模化

```
提案/评审工作流 + CDC + 列存 + 图库（如需要）
```
**交付物**：能跑通一次完整的变更提案。

### 26.1 工作量分布（定性）

| 要素 / 环节 | 相对工作量 | 性质 |
|---|---|---|
| **接入** | **最大** | 无标准可循，要对付"多源、异构、脏、身份不一致" |
| **动作** | 大 | **抽象模型要自己定**（无公开规范） |
| **策略** | 中偏大 | **无公开规范**；语义可参照 DMN / ODRL，但格式要自己定 |
| **对象 · 关系** | **最小** | **Ossie 白拿**（格式与基数语义都是现成的） |
| **规则** | 中 | 槽位是现成的，但**表达式语法 Ossie 未定**，要自己定 |
| 查询 · 存储 | 中 | 有现成产品 |
| 治理流程 | 中 | 组织成本 > 技术成本 |

> **规律：越靠"标准已经管到"的一端越便宜（对象·关系），越靠"没人管"的一端越贵（策略·动作）。**
> 而大家最容易低估的，正是**没有公开规范可依的那两块**。

## 27. Agent-first 设计原则

**v0.1 的缺陷：把 Agent 相关的设计散落在各处，没有上升为原则。**

**Agent 和人消费语义的方式根本不同：**

| | 人 | Agent |
|---|---|---|
| 消费方式 | 看图表、点按钮、读文字 | **读结构化能力描述** |
| 出错时 | 问人、查文档 | **只能靠自己重试** |
| 需要 | 可读性、美观 | **可验证的来源 + 预算感知 + 可自纠的拒绝** |
| 规模 | 几个 | **可能几百个并发** |

**四条设计原则：**

| # | 原则 | 体现 |
|---|---|---|
| **1** | **一切可枚举** | Agent 无法"猜"有什么，必须能列出来（I6） |
| **2** | **一切可溯源** | Agent 的结论必须能指回具体事实（I3-2） |
| **3** | **拒绝即可自纠** | 拒绝信息必须足以让 Agent 自己改对（I4-5、I4-8） |
| **4** | **一切有预算** | Agent 会无意识烧钱，契约必须能限（I3-4、AG-3） |

> **这四条不是"为 Agent 优化"，而是"为 Agent 而设计"——因为 Agent 是这套语义背景的主要消费者。**

## 28. 尚未解决的问题

### 28.1 v0.1 的九条批判及处理

| # | 批判 | 处理 |
|---|---|---|
| 1 | 「共同」与「开放修改」矛盾 | ✅ 已在 §0.5 明确取舍：开放提案/分叉/退出，不开放就地修改 |
| 2 | 三种用途一套要求 | ✅ 已在 §3 引入 Profile A/B/C |
| 3 | 单域架构 vs 多域 | ✅ 中央式确认；域作为内部划分；**发现机制（I6）成为对齐入口** |
| 4 | 「L5 直调 L2」掩盖难点 | ✅ 已在 §18.1 修正为专用一致性读路径（R1~R4） |
| 5 | 派生不落库 vs 前置条件冲突 | ⚠️ **仅提出候选解法，未解决**（见 §28.2-1） |
| 6 | 缺发现能力 | ✅ 已新增 I6 |
| 7 | 「治理」被当成技术问题 | ✅ 已提升为第一部分（§1~3） |
| 8 | Normative / Informative 混杂 | ✅ 已分列第六、第七部分 |
| 9 | 无 Agent-first 原则 | ✅ 已在 §27 设为显式原则 + 规范性条款 §25.9 |

### 28.2 仍然未解决的（诚实）

| # | 问题 | 为什么难 |
|---|---|---|
| **1** | **派生不落库 vs 前置条件** | 事务内算闭包——性能、正确性、成本三难。候选解法均无定论（§18.1） |
| **2** | **撤回与派生的冲突** | 撤一条前提，依赖它的派生结论要失效；"多条独立支撑"的记账成本高。<br>**这里其实是两个未决项**（§8.4）：① **增量的代价**（全量重算正确但慢）② **撤回的语义分级**（"录错了"与"结论被推翻"对审计与血缘的要求不同） |
| **3** | **动作抽象模型没有先例** | Palantir 未公开。本框架给的是**候选设计**，不是定论 |
| **4** | **身份解析的准确率上限** | 规则解决约 80%，剩下 20% 必须人工。**且它是脏数据的头号来源** |
| **5** | **合规删除的完整性** | 删了实例，派生的向量 / 摘要 / 缓存要不要删？怎么验证删干净了 |
| **6** | **定义变更的影响分析** | 需要自动算爆炸半径，尚无标准做法（G-6 只规定了"必须能算"，没规定怎么算） |
| **7** | **核心层该多"瘦"** | 太瘦则各域重复定义，太胖则治理成本爆炸。**没有客观标准** |
| **8** | **治理的组织成本** | **本体不是"建"出来的，是"谈"出来的。** 技术解决不了 |
| **9** | **"强 TBox"是否普遍适用** | 本框架预设"语义定义应当独立成层"。**若语义本就稳定、消费者很少，本框架是过度的** |

**⚠️ 第 8、9 条是对本框架本身的质疑，值得认真对待：**

> **第 8 条**：本框架给了治理的技术机制（§1），但**治理真正难的是让人达成共识**。
> 一个高效的提案系统也救不了一群谈不拢的人。
>
> **第 9 条**：采用本框架 = 选择"强 TBox"路线。
> **如果你的场景里语义稳定、消费者很少，那用一张表 + 一段代码就够了，不要用这个框架。**
