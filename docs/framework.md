# 第零部分 · 理念与定位

---

## 0. 语义治理是什么

### 0.1 问题陈述

**现状**：企业的业务语义散落在应用代码、报表定义、数仓模型、文档里。后果是——

- 同一个"客户"在四个系统里四个定义
- 同一个"营收"在四个看板里四个数字
- AI 拿到互相冲突的业务逻辑，只能胡说
- 想改一个规则，要改几十个地方，还改不全

**Palantir 的解法**：把业务语义抽出来，做成一层**可声明、可校验、可执行、可交换的契约**，
让所有读写都必须经过它。**但这个解法是专有的。**

**本框架要给出一个通用、公开、可开源的等价物。**

### 0.2 为什么叫「语义治理」而不是「本体论」

| 词 | 隐含的重心 | 问题 |
|---|---|---|
| 本体论 | **建模** | 听起来像学术活动，做完就完了 |
| 知识图谱 | **数据** | 听起来像存储选型 |
| Palantir Ontology | **产品** | 专有 |
| **语义治理** | **权责 + 契约 + 技术** | ✅ 点出了"这是一件持续治理的事" |

**"治理"三个字要求框架必须回答：谁有权定义、怎么改、有分歧怎么办、怎么退出。**

> **如果一个叫"语义治理"的框架不回答这些问题，它名不副实。**
>
> 这是 v0.1 最大的缺陷——它把治理当成了技术机制（约束/权限/审计），
> 而那些只是治理的**执行手段**，不是治理本身。

### 0.3 核心命题

> **把业务语义从应用代码里抽出来，做成一份可声明、可校验、可执行、可交换的权威契约；
> 规定六个接口，让所有读写都必须经过它；
> 并用一套治理机制保证这份契约能持续演进而不失控。**

### 0.4 范围

| 管 | 不管 |
|---|---|
| 语义的**声明格式** | 具体行业的本体内容 |
| 语义与数据的**映射** | 物理存储实现 |
| 约束的**表达** | 推理算法选型 |
| 动作的**契约** | 具体动作的业务逻辑 |
| 层间的**接口** | 各层的产品选型 |
| **治理机制** | 商业模型、部署形态 |
| **合规等级** | 组织内部的政治 |

### 0.5 【关键】形态选择：中央式权威及其代价

**本框架采用中央式：一套权威语义，所有系统向它对齐。**

**它给你什么：**

| 收益 | 说明 |
|---|---|
| **强一致** | 一处改，处处生效；不存在"你的客户"和"我的客户" |
| **无歧义** | 只有一个"营收"的定义 |
| **可治理** | 有明确的权责主体，能追责 |
| **可推理** | 全局闭包可算，不存在跨域的语义断层 |

**它要你放弃什么——必须说清，这是本框架最重要的诚实：**

| 放弃的 | 说明 |
|---|---|
| ❌ **"任何人都能改核心"** | 不可能。改核心要提案、要评审、要公示 |
| ❌ **域之间的完全自治** | 各域必须向核心对齐，不能各说各话 |
| ⚠️ **中央成为瓶颈** | 核心团队的能力决定全局；核心改动要排队 |
| ⚠️ **中央成为风险点** | 核心定义出错，影响所有消费者 |

**所以本框架的"开放"具体指什么：**

| ✅ 开放的 | ❌ 不开放的 |
|---|---|
| 规范本身（开源、任何人可自由实现） | **核心定义的直接修改权** |
| 提案权（任何人可提变更提案） | |
| 扩展命名空间（域内自定义，不受核心约束） | |
| **分叉权**（可 fork 核心，另立门户） | |
| **退出权**（可导出全部定义与事实并离开） | |

> **一句话：开放的是「加入、提案、分叉、退出」，不是「就地修改」。**

**这不是妥协。这是所有成功标准的共同形态：**

| 标准 | 提案 | 权威 |
|---|---|---|
| IETF | 任何人可提 Internet-Draft | 集中（IESG/IAB 批准） |
| W3C | 任何人可提 | 集中（工作组 + 会员投票） |
| Kubernetes | 任何人可提 KEP | 集中（SIG + TOC 批准） |
| **本框架** | 任何人可提变更提案 | **集中（治理机构批准）** |

> **"提案开放 + 权威集中"是唯一被验证过能同时做到"开放"和"稳定"的形态。**
>
> 而那些试图做到"谁都能改"的尝试（语义网的全球共享本体），**全部失败了**。

## 1. 治理的六件事

### 1.1 命名空间与权威（谁的地盘）

**核心设计：分层命名空间。**

```
urn:sem:<authority>:<domain>:<concept>
         ↑           ↑         ↑
      权威机构      域        概念
```

| 命名空间层 | 谁有权定义 | 变更流程 |
|---|---|---|
| **核心层** `urn:sem:core:*` | 治理机构 | **正式提案 + 评审 + 弃用期** |
| **领域层** `urn:sem:<org>:*` | 组织/域的建模负责人 | 内部评审 |
| **扩展层** `urn:sem:<org>:<domain>:ext:*` | 任何消费者 | **自由定义，无需批准** |
| **本地层**（不进标准） | 单个应用 | 随意 |

**规则：**

- **核心层 MUST 极简**——只放跨域必需的概念（客户、组织、时间、金额……）。
  **核心层越胖，治理成本越高，且越容易变成瓶颈。**
- **扩展层是安全阀**——想让所有人都改核心的冲动，应该被引导到扩展层
- **跨层引用只能向上，不能向下**：扩展层可引用核心层；核心层 MUST NOT 引用任何扩展层

### 1.2 变更流程

```
① 提案     任何人可提（不限身份）
   ↓
② 影响分析  自动算出：影响哪些概念、哪些消费者、哪些动作
   ↓
③ 公示期    至少 N 天（核心层 N 大，扩展层 N=0）
   ↓
④ 评审      治理机构 / 域主
   ↓
⑤ 发布      新版本号；旧版本进入弃用期
   ↓
⑥ 弃用      弃用期结束才可移除
```

**三条硬规则：**

| # | 规则 | 为什么 |
|---|---|---|
| **H1** | **定义一经发布即不可原地修改** | 否则无法回溯、无法追责 |
| **H2** | **破坏性变更 MUST 有弃用期** | 否则消费者会被静默打断 |
| **H3** | **变更必须能算出影响面** | 否则治理是盲的 |

### 1.3 争议解决

**当两个人对同一个概念有不同意见：**

| 情形 | 解法 |
|---|---|
| 命名冲突（都想叫"客户"） | 命名空间隔离 → 各自用全限定名 |
| 语义冲突（"客户"含义不同） | **必须拆成两个概念**，不能强行统一 |
| 粒度冲突（一个要粗一个要细） | 细的为基，粗的用派生规则算出来 |
| 无法调和 | **分叉**（见 1.5） |

**原则：**

> **共识是"谈"出来的，不是"统一"出来的。**
> **强行统一两个不同的概念，是语义治理中最常见的错误。**

### 1.4 版本与兼容性

| 变更类型 | 兼容性 | 处理 |
|---|---|---|
| 新增概念 / 关系 | ✅ 向后兼容 | 小版本号 |
| 新增可选属性 | ✅ 兼容 | 小版本号 |
| 新增必填属性 | ⚠️ **破坏性** | 弃用期 + 大版本号 |
| 删除 | ❌ **破坏性** | 弃用期 + 大版本号 |
| 改语义（同名不同义） | ❌ **欺骗性** | **MUST NOT** —— 必须新建概念 |
| 改约束 | ⚠️ 视情况 | 影响分析 |

> **"改语义但保留名字"是最危险的变更——它让所有消费者静默出错。**

### 1.5 分叉与退出（**最容易被忽略，也最重要**）

**没有退出权的标准是枷锁，不是标准。**

| 权利 | 怎么保证 |
|---|---|
| **分叉权** | 全部定义以**开放格式**提供（Ossie YAML）——任何人可 fork |
| **退出权** | MUST 提供**完整导出**：定义 + 事实 + 血缘 + 审计 |
| **回归权** | 分叉后仍可提交提案回来 |

**MUST 提供导出，且导出格式 MUST 可独立于本实现使用。**

### 1.6 权责矩阵

| 事 | 谁负责（R） | 谁批准（A） | 谁咨询（C） | 谁知会（I） |
|---|---|---|---|---|
| 核心概念新增 | 提案人 | 治理机构 | 消费者代表 | 全体 |
| 核心概念修改 | 提案人 | 治理机构 | 消费者代表 | 全体 |
| 领域概念 | 域建模负责人 | 域主 | 域内消费者 | 治理机构 |
| 扩展概念 | 任何人 | 无需 | — | — |
| 动作定义 | 域建模负责人 | 域主 + 安全负责人 | 审计 | 治理机构 |
| 权限模型 | 安全负责人 | 安全负责人 | 域主 | 审计 |

## 2. 三类角色与权责

| 角色 | 干什么 | 关心什么 |
|---|---|---|
| **治理机构**（中央） | 维护核心层、批准变更、解决争议 | 长期稳定性、跨域一致性 |
| **域主**（Domain Owner） | 维护本域概念、审批本域变更 | 本域业务的准确性、变更成本 |
| **消费者** | 使用语义、提交提案 | 别被破坏性变更打断 |

**⚠️ 反模式：把治理机构变成"审批机器"。**

> 如果所有变更都要中央批，中央就成了瓶颈，各域会绕过它自己搞——
> **这正是一切中央式治理失败的路径。**
>
> **解法：扩展层无需批准（安全阀）+ 核心层极简（减少必须走流程的量）。**

## 3. 三种剖面（Profile）

**v0.1 的错误：用一套要求覆盖所有用途。但三种用途的需求差别极大。**

| | **Profile A · 轻量** | **Profile B · 组织** | **Profile C · 严格** |
|---|---|---|---|
| **适用** | Agent 记忆库、个人知识 | 部门数据治理、单组织多系统 | 跨系统权威语义、受监管场景 |
| **语义稳定性** | 低（随时改） | 中 | 高 |
| **消费者** | 1 个 | 几个人 | 多系统多团队 |
| **命名空间** | 只用扩展层/本地 | 领域层 + 扩展层 | **核心层 + 领域层 + 扩展层** |
| **变更流程** | 无需提案 | 内部评审 | **正式提案 + 公示 + 弃用期** |
| **必须实现** | I1 + I2 + I3 | + I4 + 审计 | **全部六个接口 + 全部治理机制** |
| **合规等级** | L0~L1 | L0~L3 | L0~L4 |
| **典型规模** | 单机 | 单组织 | 跨组织 |

**判定规则：**

```
只有一个消费者，且语义可随时改         → Profile A
多个消费者，但都在一个组织内           → Profile B
跨组织 / 受监管 / 改动会影响外部系统    → Profile C
```

> **⚠️ Profile 是"当前状态"，可以升级。**
> **记忆库长成了部门资产，就该升到 B。**

## 4. 术语表

> **标准的第一件事是统一术语。以下词在本框架内有且仅有以下含义。**
>
> 带 ★ 的五个是**五要素**（见 §5）；其余是要素内部的构件，或要素作用的运行期对象。

| # | 术语 | 英文 | 定义 | 例子 |
|---|---|---|---|---|
| 1 | **域** | Domain | 一个独立的语义空间（限界上下文）。**一切从域开始** | 供应链域、财务域 |
| 2 | ★ **对象** | Object | 一类业务实体。**"世界"这一侧**——这是本框架对"概念"的称谓 | 订单、客户、设备 |
| 3 | **属性** | Property | 对象的字段 | 订单金额、下单时间 |
| 4 | ★ **关系** | Relation | 对象之间的**类型化连接** | 订单—属于→ 客户 |
| 5 | **角色** | Role | 关系中的位置 | 关系「运输」有角色：起运地、目的地 |
| 6 | **基数** | Multiplicity | 角色的数量约束 | 一个订单最多一个客户 |
| 7 | ★ **规则** | Rule | 对实例或事实的**合法性要求**。判定只有二值，**无裁量空间** | 金额必须为正 |
| 8 | **派生对象** | Derived Object | **由规则算出**的对象（**算出来的，不是存下来的**）。它**不是**第六个要素——声明归规则，产物归对象 | "某订单的所有上游依赖" |
| 9 | ★ **策略** | Strategy | 在**规则判定为合法的候选集**内作出优选判定。**有裁量空间**，输出的是序，不是合法与否 | 优先走低时延路径；冲突时优先保核心层 |
| 10 | **实例** | Instance | 一个具体的业务对象 | 订单 #12345 |
| 11 | **事实** | Fact | 实例之间的连接，或实例的属性值 | 订单 #12345 属于客户 acme |
| 12 | ★ **动作** | Action | 对实例的**受控修改**。**五要素中唯一能改变状态的** | 取消订单、发放优惠券 |
| 13 | **视图** | View | 对事实的查询结果（**不落库**） | "api 的所有上游依赖" |

**四个容易混的点：**

| 容易混 | 区别 |
|---|---|
| 对象 vs 实例 | 对象是"订单这一类"，实例是"订单 #12345 这一个" |
| 属性 vs 关系 | 属性指向**值**（金额=100），关系指向**另一个实例**（属于客户 acme） |
| 事实 vs 视图 | 事实是**存下来的**，视图是**算出来的** |
| **规则 vs 策略** | 规则回答"**能不能**"，**不可权衡**，失败即**系统出错**；策略回答"**选哪个**"，**可以权衡**，失败只是**不够优**。拿掉一条看后果：出现非法状态的是规则，只是效果变差的是策略 |

> **"约束"这个词在本框架中的位置**：框架的要素名是**规则**；`约束` 作为 Ossie 的机器可读载体名（`requires`）保留在下表中，指的是**规则的实现载体**，不是另一个要素。

**本框架的词 ↔ Ossie 的载体**（**要素名用框架的，载体名用 Ossie 的**，两者不混叫）：

| 五要素 | 本框架称谓 | Ossie 载体 | 说明 |
|---|---|---|---|
| 对象 | 对象 | `concept`、`extends`、`type` | ✅ 覆盖 |
| 关系 | 关系 | `relationships`、`roles`、`multiplicity` | ✅ 覆盖 |
| 规则 | 规则 | `requires`、`multiplicity`（基数约束） | ⚠️ `requires` 官方 validator **只校验结构、不执行**——强制点必须下沉到实现（见 I4 `S-4`） |
| 策略 | 策略 | ❌ **无载体** | 本框架的原创部分（见 §5） |
| 动作 | 动作 | ❌ **无载体** | 本框架的原创部分（见 §5） |
| —（非要素） | 映射 | `ontology mappings` | 归 I5 接入接口，**不占要素** |
| —（非要素） | 派生对象的声明 | `derived_by` | **归规则**：`derived_by` 是规则的一种声明形式，产物是派生对象 |

## 5. 五要素总览与理论根基

> **可声明的东西只有五样：对象 · 关系 · 规则 · 策略 · 动作。**
> 这是本框架的主轴。分层（第三部分）与接口（第四部分）是**实现参考**，不是主轴——
> 它们回答"怎么落地"，而五要素回答"语义由什么构成"。

### 5.1 五要素

| # | 要素 | 声明什么 | 理论归属 | Ossie 载体 | 能否改变状态 |
|---|---|---|---|---|---|
| 1 | **对象** | 有哪些类东西、层次、标识 | TBox | `concept`、`extends`、`type` | 否 |
| 2 | **关系** | 对象之间怎么连（角色、基数、方向） | TBox | `relationships`、`roles`、`multiplicity` | 否 |
| 3 | **规则** | 什么合法（**约束式** · **派生式**） | TBox | `requires`、`derived_by` | 否 |
| 4 | **策略** | 在合法候选里选哪个（序，可权衡） | TBox | ❌ **无载体** | 否 |
| 5 | **动作** | 允许怎么改、带什么条件、连带动什么 | TBox↔ABox | ❌ **无载体** | ✅ **唯一** |

**前两个是名词性的**（世界上存在什么），**后三个是动词性的**（允许做什么、应该怎么做）。

```
                 对象 ──→ 实例
                  ↑        （是什么）
                  │
                关系 ──→ 事实
                  ↑        （怎么连）
                  │
   规则 ──────────┘     规则（派生式）──→ 派生对象
   （什么合法）              （能算出什么）

   策略：在规则判定的合法候选集内建立优先序   （选哪个）
   动作：受控地产生新的实例和事实             （怎么改）
```

### 5.2 理论根基：TBox / ABox

| | **TBox** | **ABox** |
|---|---|---|
| 装什么 | 对象、关系、公理、**规则、策略** | 实例、具体事实 |
| 回答 | **"允许什么"** | **"实际是什么"** |
| 变更频率 | 低 | 高 |

**三条关系（全部机制的理论来源）：**

| 关系 | 含义 | 对应能力 | 对应要素 |
|---|---|---|---|
| **① 约束** | TBox 规定 ABox 里什么合法 | **校验** | **规则**（约束式） |
| **② 推理** | TBox 公理在 ABox 上求闭包 | **推理** | **规则**（派生式）→ 派生对象 |
| **③ 撤回** | 撤掉一条事实，依赖它的派生结论要失效 | **真值维护** | 不占要素位（见 §5.4） |

**两条由关系①、②直接长出来的要素：**

| 要素 | 从哪来 | 为什么必须单独存在 |
|---|---|---|
| **策略** | 关系①把空间收束成**可行域**之后，域内仍有多个合法解 | 规则说二值、不可权衡；可行域内的取舍需要另一个要素承载"序" |
| **动作** | 关系①要求 ABox 只能装合法事实 ⇒ **"往 ABox 里写"必须过这道关** | 写入通道必须存在且唯一 |

### 5.3 三条切割线：怎么判断一个声明属于哪个要素

三个要素最容易互相侵蚀。判断只看三条独立的线：

| 切割线 | 规则 | 策略 | 动作 |
|---|---|---|---|
| **论域** | 尚未受约束的状态空间 | 规则筛出的**合法候选集** | 已选定的那一个 |
| **值域** | **二值**（合法 / 非法） | **序**（优劣与选中项） | **状态变更** |
| **失败语义** | 系统**出错**（正确性被破坏） | 系统**次优**（仍然合法） | 提交被拒 / 需要补偿 |

**一条最好用的现场判据——拿掉它看后果：**

| 拿掉它 | 归属 |
|---|---|
| 产生**非法状态**（金额为负、一物两主） | **规则** |
| 系统**仍然合法，只是效果变差**（不再走低时延路径） | **策略** |
| **没有任何状态改变**（既不非法也不变差） | **不是规则也不是策略**——它根本不在这里 |

**由三条切割线推出的两条硬结论：**

1. **规则与策略 MUST NOT 产生状态变更；凡产生状态变更者必属动作。**（规范性条款 `E-8`）
2. **策略的论域是规则论域的子集**——所以"把优选塞进规则"（在只能表达"是否"的载体里表达"多好"）与"把合法性交给策略"（让可权衡者掌握不可权衡之事）都是语义污染。

### 5.4 为什么"派生"和"撤回"都不是独立要素

**派生（关系②）** = 规则的**派生式声明** ＋ 产出的**派生对象**。声明归规则，产物归对象，所以它不占要素位。

**撤回（关系③）** 的真实困难**不是"怎么让派生结论失效"**，而是另外两件事：

| 撤回的真实困难 | 本框架的处置 |
|---|---|
| 派生结论失效 | **不需要专门机制**：派生不落库（`I2-4`），前提撤掉，下次**算不出来**，自然就没了 |
| ① 增量与性能（不必全量重算） | ⚠️ **未解决**（§28.2）：全量重算永远正确但慢；增量要记 justification set，记账成本高 |
| ② 撤回的语义分级 | ⚠️ **未解决**：撤掉的是"录错了"还是"这件事被推翻了"？两者对审计与血缘的要求不同 |

> 所以关系③**不新增要素**：它的机制部分已被"派生不落库"承接，剩下的两条是开放问题。

### 5.5 五要素与分层、接口的关系

| 五要素 | 主要落在哪一层 | 主要由哪个接口读写 |
|---|---|---|
| 对象 · 关系 | L3 语义层（TBox 载体） | **I1** 语义接口（只读） |
| 规则（约束式） | L3 语义层 → 在 L5 写入路径上强制 | **I2** 事实接口（写入必过规则） |
| 规则（派生式）→ 派生对象 | L4 查询层求值，**不落库** | **I3** 查询接口（带 `via` 溯源） |
| 策略 | L3 语义层声明，L4/L5 运行期使用 | **I6** 发现（读取候选）· 策略结论由调用方落地 |
| 动作 | L5 动作层 | **I4** 动作接口（**唯一写入通道**） |

> **接口不变，要素不变——两者是正交的**：要素回答"语义由什么构成"，接口回答"谁能读写、怎么读写"。
> 一份契约只要把五个要素声明清楚，用哪个接口实现是第四部分的事。

### 5.6 两个关键结论

**结论 1：为什么必须有"动作层"**

> TBox 第 ① 条关系是"约束"——它要求 ABox 只能装合法的事实。
> **那么"往 ABox 里写"这个动作，就必须过 TBox 这道关。**
>
> 这是动作层存在的**理论理由**，而非"因为 Palantir 有 Action"。

**结论 2：为什么"对象"和"存储"必须分层**

> TBox 与 ABox 生命周期不同（一个低频、一个高频），
> 且同一份 ABox 可以有多种 TBox 投影。
> 混在一起，改一个定义就要动数据。

**Ossie 覆盖五个要素里的前三个（对象、关系、规则）；策略与动作是空白——这两个是本框架的原创部分。**

## 6. 对象

> **对象回答"有什么"。它是"世界"这一侧的名词。**

### 6.1 一个对象声明四件事

| # | 声明 | 说明 | Ossie 载体 |
|---|---|---|---|
| 1 | **标识** | 这个对象靠什么被唯一引用 | `identify_by` + 标识关系 |
| 2 | **类型** | 实体类型还是值类型 | `type: EntityType / ValueType` |
| 3 | **层次** | 继承谁；值类型最终必须落到内建类型 | `extends` |
| 4 | **属性** | 对象的字段 | 指向值类型的关系 |

### 6.2 实体类型 vs 值类型

| | **实体类型** | **值类型** |
|---|---|---|
| 是什么 | 现实世界的对象，**必须靠其他信息才能被引用** | 带语义的数据类型（等价于 domain） |
| 怎么引用 | 经一条或多条**标识关系** | 直接是值 |
| 能不能悬空 | 不能——引用实体必须有标识 | 不适用 |
| 例 | 订单、客户 | 订单号、金额、状态枚举 |

> **⚠️ 一个高频错误**：把"实体"和"表"混为一谈。
> 实体是语义概念，一张表可以承载多种实体，一个实体也可能跨表。

### 6.3 对象与"数据来源"的关系

**对象不是数据来源，数据来源也不是对象。**

| | 在不在本体里 | 说明 |
|---|---|---|
| **对象** | **在** | 被描述的东西 |
| **数据来源** | **不在** | 数据从哪里来；只有**映射进来的那一部分**才成为对象与事实 |
| **接口的调用者**（人 / Agent） | **不在** | 使用者不是被建模的对象；它只有权限与审计记录 |

映射是**声明的**，不是隐含的：`映射` 归 **I5 接入接口**，用 Ossie 的 `concept_mappings` / `object_mappings` / `link_mappings` 声明"哪个字段变成哪个对象的哪个属性"。

> **这条一旦含糊，"写入必须过规则"就没有落脚点**——因为没人知道数据是在哪一刻、按哪份声明变成对象的。

### 6.4 对象是不变的吗

对象（定义）**一经发布不可原地修改**，只能新增版本（`I1-2`、`G-2`）。
但对象的**实例**随运行不断变化——这正是 TBox / ABox 变更频率不同的体现。

## 7. 关系

> **关系回答"怎么连"。它是一等公民，不是外键。**

### 7.1 关系声明四件事

| # | 声明 | 说明 | Ossie 载体 |
|---|---|---|---|
| 1 | **角色** | 关系里的位置（二元关系有两个，n 元有 n 个） | `roles` + `name` |
| 2 | **基数** | 某个角色是否被其余角色唯一确定 | `multiplicity`：`ManyToOne` / `OneToOne` |
| 3 | **方向** | 按声明它的对象组织（Ossie 把关系挂在"扮演第一个角色的对象"下） | 结构约定 |
| 4 | **verbalizes** | 怎么把它念成人话（**给人与 Agent 读**） | `verbalizes` |

### 7.2 为什么关系是"一等公民"

因为**引擎自己会走关系**——调用方不需要在应用层写连接语句。

| 写法 | 谁在做连接 |
|---|---|
| 外键 | **应用层**：自己 join |
| 一等关系 | **引擎**：按声明遍历，且遍历可被权限过滤、可被审计 |

这也是为什么"结果必须可追溯"（`I3-2`）能成立：遍历的是**声明过的**关系，每一步都能说清走的是哪条。

### 7.3 基数是一种"规则"

`multiplicity` 声明的是**合法性要求**（"一个订单最多一个客户"），所以它**同属规则要素**——
只是它的载体是关系自身的字段，而不是 `requires` 表达式。

> **实践含义**：写入路径上必须强制 multiplicity（见 I4 `S-4`）。
> 只在读取时校验，等于"脏数据能写进去，读的时候才炸"。

### 7.4 派生关系：规则写在关系上

关系也可以有 `derived_by`（派生式规则）。此时的产物是**派生关系**——它是**对象侧**的东西（关系也是被声明的名词性内容），不落库。

例（传递闭包）：

```yaml
- name: holds_transitively
  roles: [ { concept: Customer, name: held } ]
  derived_by:
    - "Customer.holds(held)"                    # 基例
    - "Customer.holds_transitively.holds(held)" # 递归例
```

> **注意**：Ossie 用**规则**而不是**公理**表达传递性（不同于 OWL 的 `TransitiveProperty`）。
> 这一选择让"为什么这两个客户有关联"永远有依据可查。

## 8. 规则

> **规则回答"什么合法"。判定只有二值，无裁量空间，不可权衡。**

### 8.1 规则有两种声明形式

| 形式 | 作用 | Ossie 载体 | 产物 |
|---|---|---|---|
| **约束式** | 声明"什么状态组合被允许"，在写入与状态迁移的入口拦截 | `requires` | 无（只有判定） |
| **派生式** | 声明"什么能算出来" | `derived_by`（支持递归） | **派生对象**（不落库） |

**两者是同一要素的两种形式，不是两个要素**——这是派生的归宿：**声明归规则，产物归对象。**

### 8.2 规则的三条边界

| 边界 | 说明 |
|---|---|
| **规则不是数据** | 它不描述世界是怎样的，只描述世界**被允许**是怎样的；不随运行过程改变 |
| **规则不是策略** | 规则回答合法性，策略回答优越性；规则**不可权衡**，策略可以权衡 |
| **规则不是动作** | 规则不产生任何状态变更；它与动作的关系是**关卡与通行**，不是命令与执行 |

### 8.3 规则的失败语义

**规则失败即系统出错**——出现了非法状态，正确性被破坏。

因此规则的保障手段是**定义期**的：**静态一致性检查**（同一个对象、同一个条件、相反结论即报警），把矛盾在定义期排除，而不是等运行时临场判断。

> **⚠️ 一个必须说清的边界**：`requires` 这类声明式规则的**实际强制点**在写入路径上，
> 而 Ossie 官方 validator **只校验"是字符串/结构"、不求值**。
> 所以"规范上写着、跑起来不生效"是这类声明的头号陷阱——见 I4 `S-4` 与 §16.1。

### 8.4 撤销一条事实会怎样

撤掉一条前提，依赖它的**派生结论不需要专门机制去级联失效**：派生对象从不落库，下次求值**算不出来**，自然就没了。

真正未决的是两件事（见 §28.2）：**增量的代价**与**撤回的语义分级**。

## 9. 策略

> **策略回答"选哪个"。它在规则判定的合法候选集内建立优先序。**
>
> 这是五要素里**唯一在 Ossie 中没有载体**的声明性要素（动作是另一个空白要素）。

### 9.1 定义

**策略是本体内在合法状态空间中作出优选判定的、有裁量空间的偏好声明。**

它以**规则判定为合法的候选集**为定义域，按给定目标给出候选之间的优先序，输出**选中项及选择依据**。

### 9.2 策略声明四件事

| # | 声明 | 说明 |
|---|---|---|
| 1 | **作用域** | 管哪些对象、哪个方向；**分组不构成私有边界** |
| 2 | **依据的规则集** | 论域 = 该规则集筛出的合法候选集（`E-4` **MUST**） |
| 3 | **目标与优先序** | 按什么目标排序（低时延 / 低功耗 / 抗抖 …） |
| 4 | **选择依据** | 每次判定必须能说清"为什么选它"（`E-6`，对应 `I3-2` 的溯源精神） |

### 9.3 三条切割线（与规则的分别）

| 切割线 | 规则 | 策略 |
|---|---|---|
| **论域** | 尚未受约束的状态空间 | **规则筛出的合法候选集**（子集关系） |
| **值域** | 二值：合法 / 非法 | **序**：优劣与选中项 |
| **失败语义** | **系统出错** | **不够优**，系统仍然正确 |

**策略不能把非法变合法**——它只能在"合法与合法"之间分出优劣。
若策略试图选一个不满足规则的候选，**那不是"策略认为它更好"，而是这一步根本不合法**。

### 9.4 失败语义与保障手段

策略失败**不是出错**，只是**次优**。所以它的保障手段不在定义期，而在**运行期**：
**运行时仲裁**——冲突时确定取舍，而不是靠静态检查排除。

### 9.5 冲突处理：五层，从预防到兜底

| 层 | 手段 | 说明 |
|---|---|---|
| **1** | **切干净**（最主要） | 让两个策略的判定对象互不重叠——**结构上不重叠，就永远撞不上。冲突大多不是靠仲裁解决的，是靠切分消灭的** |
| **2** | **显式定优先级** | 真出现同对象判定，按"全局规则 ＞ 领域规则 ＞ 策略 ＞ 动作"逐级压制，**且必须写在定义里**，不能靠运行时临场判断 |
| **3** | **运行时仲裁** | 真僵住了，由治理流程或指定的仲裁主体裁 |
| **4** | **判定出口唯一** | 同一时刻、同一对象只允许一个判定生效，其余记为备选并留决策记录 |
| **5** | **静态检查 + 变更治理** | 跨域冲突要在**定义期**尽量查出来；改策略走"提案 → 影响分析 → 评审 → 发布" |

**先分清是哪种"撞"**：大多数所谓冲突是**假冲突**——管的对象根本不同，只是名字听着像。
**真冲突只有一种形态：两个策略对同一个对象、同一时刻给出了不同结论。**

### 9.6 「策略」不等于「授权策略」

这两个词必须分列（`E-7`）：

| | **语义策略** | **授权策略** |
|---|---|---|
| 问什么 | **选哪个** | **谁可以** |
| 归属 | 本框架的**要素** | I4 的**权限**部分 |
| 载体 | ❌ 无标准 | ✅ **OPA / Rego** 或 **Cedar** |
| 失败 | 次优 | 拒绝 |

> **混用的代价**：把"谁可以"写成策略要素，会让可权衡者掌握不可权衡之事；
> 把"选哪个"塞进授权引擎，会让业务偏好散落在权限配置里，谁也看不出业务取向。

### 9.7 策略是可选的（条件式条款）

**不声明策略是合法状态**——一个只做校验与派生的实现，不因缺少策略而不合规。

但**一旦声明**，就必须满足 `E-4`~`E-6`：声明依据的规则集、不改变合法性、携带选择依据。
否则策略会退化成"用规则的口吻表达偏好"，两边都不再可靠。

## 10. 动作

> **动作回答"怎么改"。它是五要素中唯一能改变状态的要素，也是唯一的写入通道。**

### 10.1 为什么动作必须是唯一的写入通道

由关系①（约束）直接推出：**ABox 只能装合法事实 ⇒ 往 ABox 里写必须过 TBox 这道关。**

**如果存在第二条写入通道，那道关就可以被绕过**——规则就从"保证"退化为"建议"。
所以 `G3`「只有 L5 能写」不是设计偏好，而是理论必然（见 `I2-2`）。

### 10.2 动作契约九项

| # | 声明 | 说明 |
|---|---|---|
| 1 | **作用对象** | 动谁（含多实例） |
| 2 | **参数** | 带什么（含参数级约束） |
| 3 | **前置条件** | 什么情况下才允许 |
| 4 | **效果** | 会发生什么（含连带影响） |
| 5 | **副作用** | 除效果之外还触发了什么 |
| 6 | **幂等性** | 重复提交怎么识别 |
| 7 | **权限** | 谁可以提交 |
| 8 | **审计** | 必须留下什么记录 |
| 9 | **拒绝格式** | 被拒时说清什么 |

### 10.3 提交必须依次完成四件事

```
① 参数校验 → ② 权限校验 → ③ 前置条件校验 → ④ 效果写入（同一事务）
```

**顺序不可交换**：权限必须早于前置条件——否则"前置条件不满足"与"你无权看"会泄漏信息（见 I4 `S-1`）。

### 10.4 提交语义五件事

| 要素 | 待定义 |
|---|---|
| 同步 / 异步 | 什么时候返回？长动作怎么处理 |
| **事务边界** | 涉及多个实例时，原子性范围是什么 |
| **幂等键** | 重复提交怎么识别 |
| **失败语义** | 拒绝（全无副作用）／部分成功（怎么补偿）／补偿（Saga） |
| **并发** | 两个动作同时改同一实例，怎么办 |

### 10.5 审计记录

每次提交 **MUST** 产生一条不可变记录：

```
谁 · 何时 · 提交了哪个动作 · 参数是什么
· 基于什么（读取了哪些事实）· 结果如何 · 副作用有哪些 · 是否可回滚
```

> **"基于什么"这一项最关键**——它是"为什么批准/拒绝了这笔操作"的答案，也是合规审计的核心。

### 10.6 拒绝的格式（**为 Agent 而设计**）

拒绝 **MUST** 说清违反了哪条规则：

```
REJECTED cancel_order(order:12345)
  原因：前置条件不满足
  违反：order:12345 的状态为「已发货」，而 cancel_order 要求「未发货」
  依据：规则 Rule#17「已发货订单不可取消」
  建议：可执行 return_order 走退货流程          ← 可选，但对 Agent 极有价值
```

> **这一条是"可用性"的关键**——人看到报错会去问人，**Agent 只能靠自己重试**，
> 所以拒绝信息必须**足以让它自己纠正**。

**三段内容要求**：违反哪条（`I4-5` **MUST**）· 依据哪条（**MUST**）· 可行的替代动作（`I4-8` **SHOULD**，且可由 I6 发现接口兜底）。

### 10.7 周边全部用现成标准

| 要素 | 用什么 | 标准 / 模式 |
|---|---|---|
| 接口描述 | **OpenAPI** | 有标准 |
| 权限判定 | **OpenFGA**（Zanzibar 模型） | 有标准 |
| 授权策略表达 | **OPA / Rego** 或 **Cedar** | 有标准 |
| 语义**策略**（五要素之一：候选集内的优选序） | ❌ **无标准** | 见 §9——**授权策略管"谁可以"，语义策略管"选哪个"** |
| 跨系统可靠写回 | **Transactional Outbox** | 成熟模式 |
| 跨系统长事务 | **Saga** | 成熟模式 |
| 审批 / 编排 | **Temporal** / Cadence | 有实现 |
| 审计事件格式 | **CloudEvents** | 有标准 |
| 幂等 | 幂等键 + 去重表 | 成熟做法 |

> **I4 的工作量 = 定义抽象模型（10%）+ 组装现成组件（90%）。**

### 10.8 为什么权限天然匹配

| 本框架 | OpenFGA |
|---|---|
| 对象 | `type` |
| 关系 | `relation` |
| 实例 | `object` |

**权限模型与本体的形状同构**，所以不需要另造一套——直接把本体里的对象与关系映射过去。

## 12. 六层架构

```
        ╔══════════════════════════════════════════════════╗
        ║  外部：数据源（ERP/CRM/数仓/API/流）  ← 入站      ║
        ╚═══════════════════════╤══════════════════════════╝
                                │  I5 接入接口
┌───────────────────────────────┴──────────────────────────┐
│ L6  消费层     人 / Agent / 外部系统                      │
├──────────────────────────────────────────────────────────┤
│ L5  动作层     受控修改         ┌────────────────────────┼──→ 写回外部（出站）
│                                │ 一致性读路径（见 §8）   │
├────────────────────────────────┴─────────────────────────┤
│ L4  查询层     读取、遍历、推理                           │
├──────────────────────────────────────────────┬───────────┤
│ L3  语义层     = TBox 的载体（权威契约）      │           │
├──────────────────────────────────────────────┤  I1/I2    │
│ L2  事实层     = ABox 的载体                 │  语义接口 │
├──────────────────────────────────────────────┴───────────┤
│ L1  接入层     把外部数据变成合法事实                     │
└──────────────────────────────────────────────────────────┘
```

| 层 | 理论身份 | 一句话 | 关键问题 |
|---|---|---|---|
| **L1 接入** | ABox 的构建过程 | 把**外部表示**变成合法事实 | 数据不脏 |
| **L2 事实** | ABox 的载体 | 事实存在哪、怎么存得快 | 快 |
| **L3 语义** | TBox 的载体 | 允许什么（**权威**） | 统一语言 |
| **L4 查询** | TBox 在 ABox 上求值 | 能问出什么、能推出什么 | 问得出来 |
| **L5 动作** | TBox 约束 ABox 的关卡 | 能安全地改什么 | **安全地改** |
| **L6 消费** | 消费方 | 谁在用 | 用得上 |

### 12.1 修正：L1 是**条件层**，事实有**两个入口**

> 本节来自一次实现反馈。v0.2 把 L1 写成常设的一层（"把外部数据变成合法事实"），
> 这个写法隐含了"数据都从外面来"。**实际不成立。**

**事实进入系统的入口有两个，它们不是同一件事：**

| 入口 | 触发者 | 负责什么 | 典型场景 |
|---|---|---|---|
| **L1 接入** | 外部系统 | 把**外部表示**翻译成合法事实 | 硬件设备、ERP/CRM/数仓、消息流 |
| **L5 动作** | 人 / Agent / 内部逻辑 | 在**内部**产生或修改事实 | 用户在界面上提交一次修改 |

所以：

| 编号 | 条款 |
|---|---|
| **L-5** | L1 **MUST** 被视为**条件层**：只在存在外部数据源时出现。**MUST NOT** 假定它必然存在 |
| **L-6** | L1 缺席时，进入 L2 的事实**只能**由 L5 产生 —— 此时"只有 L5 能写"从一条约束升级为**唯一路径** |
| **L-7** | 实现 **MUST** 显式声明 L1 存在与否，**MUST NOT** 用"这一层没有内容"暗示 |

**L-6 是个意外的收获**：L1 缺席反而让 G3「只有 L5 能写」变得**更强、更可检验**——
有 L1 时你要证明"外部来的一定过了约束"；没有 L1 时，写入路径**只有一条**，堵住它就堵住了全部。

**L1 缺席不是缺陷，是域的属性。** 但它有代价，MUST 被记下来而不是等要用时才发现：

- 整层缺席 ⇒ 没有任何"把外部表示翻译成合法事实"的能力；
- 想接入真实数据源时，要**新做一整层**，而不是加一个适配器。

### 12.2 TBox 与 ABox **MUST** 分属不同原子

> §5.2 说"概念与存储必须分层"。这是一条**可检验**的要求，不只是设计品味。

若同一个模块既是"允许什么"又是"实际是什么"的载体，后果是可枚举的：

| 后果 | 说明 |
|---|---|
| 改定义要动装数据的模块 | 低频变更被高频数据绑住 |
| 同一份 ABox 无法换 TBox 投影 | 而"多投影"正是分层的理由 |
| 矩阵画不出来 | 任何"层 × TBox/ABox"的表格都只能把它塞进一格，**表格因此不准** |

| 编号 | 条款 |
|---|---|
| **L-8** | TBox 与 ABox **MUST NOT** 混装在同一个原子内；混装 **MUST** 被登记为已知偏差 |
| **L-9** | 若因域的特性（如 ABox 为构建期常量、与 TBox 同生命周期）暂不拆分，**MUST** 写明触发拆分的条件（例：出现运行期可变事实） |

**L-9 的意义**：不拆是可以的，但**"为什么不拆"必须是一个有条件的判断**，
而不是"一直没拆"。条件一旦成立（域变动态），拆分就从"可选优化"变成"必须做的事"。

## 13. 三条流（含修正后的 L5 读路径）

| 流 | 方向 | 内容 |
|---|---|---|
| **① 定义流（TBox）** | **自上而下** | L3 的定义驱动 L1 按什么形状抽、L2 按什么类型索引 |
| **② 数据流（ABox）** | **自下而上** | 数据源 → L1 → L2 → L4/L5 → L6 |
| **③ 控制流** | **横切** | L5 通过**专用一致性读路径**访问 L2 |

### 13.1 ⚠️ 修正：L5 的读路径（v0.1 的错误）

**v0.1 的说法**：「L5 直调 L2，不经过 L4」。

**这个说法是错的**，因为动作的前置条件需要读当前状态，而它必须：

| 需求 | 为什么 | "直调 L2"能满足吗 |
|---|---|---|
| **事务内一致读** | 读到的状态必须和执行时的状态一致，否则前置条件失效 | ⚠️ 不一定 |
| **能读到派生事实** | 前置条件常需派生值（"客户订单总额"） | ❌ 不能（派生不在 L2） |
| **带权限上下文** | 读本身也要受权限约束 | ❌ 不能（L2 不认识权限） |

**修正后的设计：L5 使用一条专用的「一致性读路径」**

```
L5 动作层
   │
   ├─→ 一致性读路径（专用）
   │     · 事务内快照读（保证前置条件与执行同源）
   │     · 可读派生事实（在事务快照上现算）
   │     · 带调用者权限上下文
   │
   └─→ 写入路径（经 I2）
         · 写前过规则校验
         · 写后记审计
```

**这条路径 MUST 满足：**

| # | 要求 | 理由 |
|---|---|---|
| **R1** | **快照一致** | 前置条件读到的状态 = 执行时的状态 |
| **R2** | **可读派生** | 否则写不出"总额超限"这类前置条件 |
| **R3** | **带权限上下文** | 否则动作能读到调用者无权看的数据 |
| **R4** | **不产生副作用** | 它只是读，不能触发任何写 |

> **v0.1 把这个难点简化成"直调 L2"，掩盖了真实的设计复杂度。**

### 13.2 ⚠️ 未解决的冲突：派生不落库 vs 前置条件

**这是一个真实的、本框架尚未解决的冲突：**

- 保证 I2-4 说"派生事实不落库"
- 但前置条件经常需要派生事实（R2）
- 于是每次动作提交都要**在事务内现算闭包**

**后果：**

| 问题 | 说明 |
|---|---|
| **性能** | 事务内算不动点，可能超时 |
| **正确性** | 算到一半规则变了怎么办 |
| **成本** | 高频动作场景下不可接受 |

**候选解法（尚无定论，见 §28）：**

1. **限定深度**——只允许有限深度的派生参与前置条件
2. **物化 + 版本**——对高频用到的派生值做物化，绑定定义版本
3. **前置条件改写**——把派生条件改写成对基础事实的条件（不总是可行）
4. **两阶段**——先在快照上算派生，再进事务校验（有窗口期）

# 第四部分 · 接口视图 ★核心

> **模块之间靠什么对话。这一部分是本框架真正的"标准"内容——分层是描述，接口才是约束。**

---

> **本部分的定位**：接口**不是**框架的主轴（主轴是第二部分·五要素）。
> 接口回答的是"**谁能读写、怎么读写**"——同样五个要素，可以用不同接口实现。
> 所以下面每个接口都先标明它**读写哪些要素**。

---

## 14. 五个接口 + 一个能力

| # | 名称 | 谁调谁 | 方向 | 契约核心 | 现有标准 |
|---|---|---|---|---|---|
| **I1** | **语义接口** | 所有层 → L3 | 读 | 读定义，定义不可变 | ✅ **Ossie** |
| **I2** | **事实接口** | L4/L5 → L2 | 读+写 | **写入必须过规则** | ⚠️ GQL（半覆盖） |
| **I3** | **查询接口** | L6 → L4 | 读 | **结果必须可追溯** | ⚠️ MCP（半覆盖） |
| **I4** | **动作接口** | L6 → L5 | 写 | **全套待定义** | ❌ **无** |
| **I5** | **接入接口** | 外部 → L1 | 入 | 契约先于数据 | ✅ **ODCS** |
| **I6** | **发现能力** | 任何方 → 全域 | 读 | **不知道有什么时能列出来** | ❌ 无（v0.2 新增） |

### 14.1 接口 × 五要素：谁负责读哪些要素

**这张表是第二、四部分之间的桥**——它回答"五要素到底由谁读写"。

| 五要素 | 由谁**声明** | 谁**读**它 | 谁**写**它 |
|---|---|---|---|
| **对象** | 契约文件（人工/工具） | **I1**（读定义）· I3（读实例） | ❌ 只读——定义不可原地改（`I1-2`） |
| **关系** | 契约文件 | **I1** · I3（遍历） | ❌ 只读 |
| **规则**（约束式） | 契约文件 | **I1**（`GetConstraints`） | ❌ 只读 |
| **规则**（派生式） | 契约文件 | **I1**（`GetDerivations`） | ❌ 只读 |
| **派生对象** | —（规则算出） | **I3** 求值（带 `via` 溯源） | ❌ **不落库**（`I2-4`） |
| **策略** | 契约文件 | **I1 / I6**（读声明与候选） | ❌ 只读——策略结论由**调用方**落地 |
| **动作** | 契约文件 | **I4 / I6**（读契约） | **I4** 提交（**唯一写入通道**） |
| **实例与事实** | —（运行期产生） | **I2** · I3 · I6 | **I2**（且仅 L5 能写） |
| **映射**（数据来源 → 对象） | 接入契约 | — | **I5**（声明式，不是要素） |

**三条从这张表直接读出来的结论：**

| # | 结论 | 含义 |
|---|---|---|
| 1 | **五个要素全部是"读多写无"** | 定义的变更**不经过任何接口**，走治理流程（§1.2）。这就是"不开放就地修改"在接口层的体现 |
| 2 | **只有动作与事实能改变状态** | 其余要素与派生对象都是只读的——与 §5.3 切割线一致（规则、策略 MUST NOT 产生状态变更） |
| 3 | **映射不是要素，是一个接口** | 它描述"数据怎么变成对象"，归 I5；把它当第六个要素是常见误解 |

> **⚠️ 一个必须点明的缺口**：表中"五个要素由谁**声明**"一列写的是"契约文件"，
> 但接口清单里**没有一个"改定义"的接口**——这是**刻意的**（定义不可原地改）。
> 代价是：**变更的执行通道没有被规范指定**。参考实现用"Git 里的 YAML + PR 评审"充当这个通道（见 `CONTRIBUTING.md` 的变更流程），
> 但这是**实现选择**，不是本框架的规范要求。**这是本部分最值得补的一条。**

**一句话看懂：**

> **六个接口里，两个有完整标准（I1、I5），两个需要补一条关键约束（I2、I3），
> 两个需要原创（I4、I6）。**
>
> **要发明的只有两个，其余全是选型和组合。**

## 15. I1 语义接口

**方向**：只读（定义由治理流程写）

| 操作 | 输入 | 输出 |
|---|---|---|
| `GetConcept(name)` | 概念名 | 属性、层次、接口、约束 |
| `ListRelations(concept)` | 概念名 | 该概念下的关系（含角色、基数） |
| `GetConstraints(target)` | 概念/关系名 | 适用的约束表达式 |
| `GetDerivations(target)` | 概念/关系名 | 派生规则 |
| `GetActions(concept)` | 概念名 | 可对该概念执行的动作 |
| `GetMappings(concept)` | 概念名 | 字段 → 概念的映射规则 |
| `GetVersion()` | — | 当前定义版本 |
| `Diff(v1, v2)` | 两个版本 | 差异（供影响分析用） |

**保证：**

| # | 保证 | 为什么重要 |
|---|---|---|
| **G1** | **定义不可变** | 一经发布只能新增版本，不能原地改 → 让回溯和撤回成为可能 |
| **G2** | **读取一致** | 同一次操作内读到的定义来自同一版本 |
| **G3** | **可自检** | 定义本身可被校验（环、悬空引用、冲突） |
| **G4** | **可差异对比** | 任意两版本可算出差异 → 影响分析的前提 |

**格式**：定义态用 **Apache Ossie YAML**；运行态 API 各实现自定，但 MUST 满足 G1~G4。

### 15.1 Ossie 的已知表达力缺口（实测，非推测）

> 本框架把 I1 押在 Ossie 上，所以 **Ossie 表达不了什么，就是本框架表达不了什么**。
> 下面两条来自参考实现的实测，不是阅读理解。

| 缺口 | 现象 | 后果 |
|---|---|---|
| **无 `OneToMany`** | `relationships[].multiplicity` 只接受 `ManyToOne` / `OneToOne`（validator 原文：`'OneToMany' is not one of [...]`） | **一对多只能借 `ManyToOne` 表达**。"一个会话含多个槽位"这类最常见的基数无法精确声明，各实现只能各自发明绕法 → 互操作从定义层就断了 |
| **`requires` / `derived_by` 不执行** | 官方 validator 只校验"是字符串/结构"，不求值 | 约束的**实际强制点被迫下沉到实现**（见 I4 `S-4`）。规范上写着、跑起来不生效 —— 这正是"声明式"最容易骗人的地方 |

**这两条的应对（本框架的立场）**：

1. **不自行扩展 Ossie 的语法**。加一个自定义字段很容易，但那就不是"用标准"，
   而是"借标准的名字发自己的标准"——比一开始就自研更糟。
2. **缺口 MUST 被显式记录**（就是本节的用途），且实现 MUST 在**自己的校验器**里补上强制点，
   MUST NOT 假设"写在 YAML 里就等于生效"。
3. **一旦 Ossie 补上，本框架的对应绕法 MUST 被移除**，而不是留着"兼容"。
   留着兼容 = 永久保留两套语义。

> **判据**：若某个概念只能用绕法表达，那么在跨实现比对时，它 **MUST** 被视为
> "**未被标准覆盖**"的部分——即：这部分的一致性是巧合，不是保证。

## 16. I2 事实接口

**方向**：读 + 写（写仅限 L5）

| 操作 | 调用方 | 说明 |
|---|---|---|
| `GetInstance(concept, id)` | L4/L5 | 取一个实例 |
| `ListFacts(pattern)` | L4 | 按模式取事实 |
| `WriteFact(fact)` | **仅 L5** | 写入一条事实 |
| `DeleteFact(fact)` | **仅 L5** | 删除一条事实 |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **G1** | **写入必须过规则** ⭐ | 任何写入必须已通过 L3 规则校验，失败即拒绝且**无副作用** |
| **G2** | **写入必须带来源** | 记录从哪来（哪个动作 / 哪个数据源） |
| **G3** | **只有 L5 能写** | L4、L6 一律只读——**本框架的硬约束** |
| **G4** | **派生事实不落库** | 推出的结论是视图，不是事实 |

### 16.1 ⚠️ 这里需要补的约束

> **GQL / Cypher 定义了"怎么写"，但没有定义"写入必须过规则"。**
>
> **本框架在 GQL 之上加一条：任何 `WriteFact` 必须原子地包含规则校验，失败即拒绝。**
>
> 这一条把图数据库从"能写的存储"变成"**受治理的事实层**"。

## 17. I3 查询接口

**方向**：只读

| 操作 | 说明 |
|---|---|
| `Query(pattern)` | 按模式查事实 |
| `Traverse(from, relation, depth)` | 多跳遍历 |
| `Infer(query)` | 含派生事实的查询 |
| `Search(text)` | 向量 / 全文检索，返回入口实例 |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **G1** | **只读** | 查询接口**永不产生写入** |
| **G2** | **可追溯** ⭐ | 每条返回的事实必须带来源：是存的，还是推出来的；推出来的依据是什么 |
| **G3** | **权限过滤** | 结果必须已按调用者权限过滤 |
| **G4** | **预算可限** | 支持限制返回量（节点数 / token 数）——**为 Agent 设计** |

### 17.1 ⚠️ 这里需要补的约束

> MCP 定义了"怎么把工具暴露给 Agent"，**但没有定义"结果必须可追溯"**。
>
> **本框架加一条：`Infer` 的每条派生结果 MUST 带 `via` 字段，标明由哪条规则、从哪几条事实推出。**
>
> **这是让 LLM 的结论可验证的关键**——它必须能引用具体事实，而不是只给结论。

**实现示例（`dsh-ontology` 的做法）：**

```
api depends_on pg (inferred: transitive)
                      ↑ via 字段
```

## 18. I4 动作接口

**方向**：写 · **现有标准**：❌ 无

> **本框架唯一需要原创设计的核心部分。**

> 📄 **实现规范见 [`spec/i4-action-minimal.md`](../spec/i4-action-minimal.md)（v0.1）。**
>
> 该规范刻意收窄范围：**单实例 · 同步 · 无副作用 · 有审计**。
> 多实例事务、异步、副作用、补偿留给 v0.2 / v0.3。
> **本节以下内容是设计要素清单；具体条款以该规范为准。**

### 18.1 动作的描述格式（静态）

| 要素 | 说明 |
|---|---|
| 标识 | 动作名、所属域、命名空间 |
| **作用对象** | 读写哪些概念 / 关系（**与 L3 定义的关联**） |
| **参数** | 名称、类型、是否必填、取值范围 |
| **前置条件** | 什么状态下允许执行 |
| **副作用** | 会触发什么（通知 / webhook / 触发下游） |
| **写回目标** | 是否回写外部系统，回写到哪 |
| **幂等性** | 是否幂等；非幂等时幂等键怎么取 |
| **权限** | 谁能执行（可基于属性动态推导） |

### 18.2 提交的语义（动态）

| 要素 | 待定义 |
|---|---|
| 同步 / 异步 | 什么时候返回？长动作怎么处理 |
| **事务边界** | 涉及多个实例时，原子性范围是什么 |
| **幂等键** | 重复提交怎么识别 |
| **失败语义** | 拒绝（全无副作用）／部分成功（怎么补偿）／补偿（Saga） |
| **并发** | 两个动作同时改同一实例，怎么办 |

### 18.3 审计记录的格式

每次提交 MUST 产生一条不可变记录：

```
谁 · 何时 · 提交了哪个动作 · 参数是什么
· 基于什么（读取了哪些事实）· 结果如何 · 副作用有哪些 · 是否可回滚
```

> **"基于什么"这一项最关键**——它是"为什么批准/拒绝了这笔操作"的答案，也是合规审计的核心。

### 18.4 拒绝的格式（**为 Agent 而设计**）

拒绝 MUST 说清违反了哪条规则：

```
REJECTED cancel_order(order:12345)
  原因：前置条件不满足
  违反：order:12345 的状态为「已发货」，而 cancel_order 要求「未发货」
  依据：规则 Rule#17「已发货订单不可取消」
  建议：可执行 return_order 走退货流程          ← 可选，但对 Agent 极有价值
```

> **这一条是"可用性"的关键**——人看到报错会去问人，**Agent 只能靠自己重试**，
> 所以拒绝信息必须**足以让它自己纠正**。

### 18.5 周边全部用现成标准

| 要素 | 用什么 | 标准 / 模式 |
|---|---|---|
| 接口描述 | **OpenAPI** | 有标准 |
| 权限判定 | **OpenFGA**（Zanzibar 模型） | 有标准 |
| 授权策略表达 | **OPA / Rego** 或 **Cedar** | 有标准 |
| 语义**策略**（五要素之一：候选集内的优选序） | ❌ **无标准** | 见 §5——这是策略与"授权策略"的区别：**授权策略管"谁可以"，语义策略管"选哪个"** |
| 跨系统可靠写回 | **Transactional Outbox** | 成熟模式 |
| 跨系统长事务 | **Saga** | 成熟模式 |
| 审批 / 编排 | **Temporal** / Cadence | 有实现 |
| 审计事件格式 | **CloudEvents** | 有标准 |
| 幂等 | 幂等键 + 去重表 | 成熟做法 |

> **I4 的工作量 = 定义抽象模型（10%）+ 组装现成组件（90%）。**

### 18.6 为什么权限天然匹配

| 本框架 | OpenFGA |
|---|---|
| 概念 | `type` |
| 关系 | `relation` |
| 实例 | `object` |
| 事实 | `relationship tuple` |

**推论：授权模型可以从 L3 的定义自动生成，且"权限沿业务关系继承"是原生的。**

## 19. I5 接入接口

**方向**：入

| 操作 | 说明 |
|---|---|
| `DeclareContract(source)` | 声明数据源的数据契约 |
| `ValidateContract(source)` | 校验上游是否满足契约 |
| `Ingest(source, mode)` | 摄取（增量 / 全量） |
| `Quarantine(badRecords)` | 拒收不合规记录 |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **G1** | **契约先于数据** | 没有契约的数据源不得接入 |
| **G2** | **不合规即拒收** ⭐ | **绝不自动清洗**——隔离等人来修 |
| **G3** | **拒收可解释** | 说清违反了契约的哪一条 |
| **G4** | **身份先于属性** | 实例身份必须能稳定解析 |

### 19.1 最强的一条原则

> **不指望数据干净，指望入口干净。**
>
> **不合规的数据不是"清洗掉"，是"隔离出来逼人解决"。**
> 自动清洗是错误放大器——它把业务问题藏起来，而且越藏越深。

**格式**：**ODCS（Open Data Contract Standard，Bitol / Linux Foundation）**——直接采用。

## 20. I6 发现能力（v0.2 新增）

**方向**：只读 · **现有标准**：❌ 无

**v0.1 的缺陷**：只有"已知名字去查"（`GetConcept(name)`），
**没有"我不知道有什么，先列一遍"**。

**为什么这是刚需：**

| 场景 | 需要什么 |
|---|---|
| 新系统接入 | 有哪些域？各提供什么？ |
| 新 Agent 上线 | 我能用什么概念、什么动作？ |
| 跨域对接 | 对方的"订单"和我的能不能对上？ |
| 影响分析 | 改这个概念会影响谁？ |

| 操作 | 说明 |
|---|---|
| `ListDomains()` | 列出所有域 |
| `ListConcepts(domain, filter)` | 列出概念（可按标签/关键词过滤） |
| `ListActions(concept)` | 列出可用动作 |
| `DescribeCapability(name)` | 描述一个能力的完整契约 |
| `FindByCapability(need)` | **按需求找能力**（"我需要一个能取消订单的动作"） |

**保证：**

| # | 保证 | 说明 |
|---|---|---|
| **G1** | **可枚举** | 域、概念、动作必须可被完整列出 |
| **G2** | **权限过滤** | 只列出调用者有权知道的 |
| **G3** | **自描述** | 发现的结果本身符合标准格式 |

> **在中央式架构里，发现机制是"对齐"的入口——新系统靠它知道该向什么对齐。**

## 21. 接口 × 现有标准对照

| 接口 | 直接采用 | **本框架需要补的** |
|---|---|---|
| **I1 语义** | **Ossie YAML** | 运行态 API 四条保证（G1~G4） |
| **I2 事实** | **GQL**（ISO/IEC 39075:2024） | ⭐ **写入必须过规则**；只有 L5 能写 |
| **I3 查询** | **MCP** | ⭐ **结果必须可追溯**（`via` 字段）；预算可限 |
| **I4 动作** | OpenAPI / OpenFGA / Outbox / Saga / CloudEvents | ⭐ **抽象模型全套** |
| **I5 接入** | **ODCS** | 拒收区与身份解析的实现约定 |
| **I6 发现** | — | ⭐ **能力模型全套** |

**这就是本框架的"贡献清单"：**

> **两条必须补的约束（I2-1、I3-2）**
> **两个必须原创的模型（I4、I6）**
> **其余全是选型和组合。**

# 第六部分 · 合规等级

---

## 23. 五级阶梯 × 三种剖面

```
Level 4  可运营   + 全部切面（合规删除、成本、SLA、治理流程）
   ↑
Level 3  可治理   + 授权 + 审计 + 版本
   ↑
Level 2  可写     + 动作接口（I4）          ← ⭐ 分水岭
   ↑
Level 1  可读     + 事实 + 查询 + 发现接口
   ↑
Level 0  可声明   + 语义接口（I1）           ← Ossie 已给
```

| Profile | 目标等级 | 必须实现 |
|---|---|---|
| **A · 轻量** | L0 ~ L1 | I1 + I2 + I3 |
| **B · 组织** | L0 ~ L3 | + I4 + I6 + 审计 |
| **C · 严格** | L0 ~ L4 | **全部六个接口 + 全部治理机制** |

> **Level 1 → 2 是分水岭：以下只能"看"，以上才能"安全地改"。**
> **绝大多数开源方案停在 Level 1。**

---

## 24. 验收标准

| 级别 | 必须满足 | 验收方法 |
|---|---|---|
| **L0** | 能用 Ossie YAML 描述本域对象、关系、规则（含派生式） | 通过 Ossie 校验器 |
| **L1** | 按 I1 读定义；按 I2 读事实；按 I3 查询（含派生，带 `via`）；按 I6 发现 | 给定事实集，能答出派生问题并给出依据 |
| **L2** | 按 I4 提交动作；**写入必须过规则**；拒绝可解释 | ✅ **"该被拒绝的样本集"全部被拒，且拒绝原因正确** |
| **L3** | 授权 + 审计 + 版本 | 能回答"谁在何时基于什么做了什么"；能回滚定义 |
| **L4** | 合规删除 + 成本计量 + SLA + **治理流程** | 能执行一次跨存储实体删除并验证无残留；能跑通一次变更提案 |

### 24.0 ⚠️ 本节的缺口：只有运行期门禁，没有构建期门禁

**本节的全部验收都是"运行期"的** —— 系统跑起来之后，喂它脏数据、看会不会被拒。

**但实现本身也会烂掉**：术语被拷贝进各模块、依赖变成隐式、文档与代码脱节、
编码在某条工具链下被读错。**这些用运行期门禁查不出来。**

| | 构建期门禁 | 运行期门禁 |
|---|---|---|
| 何时跑 | 提交前 / CI | 每次写入 |
| 拦什么 | 违反纪律的**代码与文档** | 违反规则的**数据与操作** |
| 本节覆盖 | ❌ **缺** | ✅ |

**构建期门禁的最小集合是五项**（编码 / 引用 / 依赖 / 契约 / 组装），
见 **[`spec/module-discipline.md`](../spec/module-discipline.md) §4**。

> **两者都要。** 只做运行期，实现会慢慢烂掉；只做构建期，脏数据会进去。

### 24.1 最便宜也最有效的验收方法

> **建一个"该被拒绝的样本集"：收集 100 条应该被系统拒掉的数据/操作**
> （非法关系、超范围值、无权限、会形成环……），做成测试，每次改规则跑一遍。

**同时做到三件事：**

1. 验证规则没写错
2. 验证拒收真的生效（不只是写在文档里）
3. 防止改规则时把原来能拒的搞坏了（回归测试）

**这是 L2 验收的核心手段，几乎零成本。**

### 24.2 加规则的安全姿势

```
第 1 步：新规则写成"只记录，不拦截"
第 2 步：跑一段时间，看它会拒掉什么
第 3 步：人工审这份"本该被拒"的清单
        ├─ 都是真该拒的 → 改成强制拦截
        └─ 有误伤的   → 先修规则，别上线
第 4 步：上线，保留清单做回归测试
```

# 第七部分 · 规范条款（Normative）

> **v0.2 新增。** MUST / MUST NOT / SHOULD 是**规范性**的——
> 声称合规的实现**必须满足**，测试套件按这些条款验收。
> 与第八部分的实施指南（Informative）严格区分。

---

## 25. MUST / MUST NOT / SHOULD 清单

### 25.1 治理

| # | 条款 |
|---|---|
| G-1 | 每个定义项 **MUST** 属于某个命名空间 |
| G-2 | 定义一经发布 **MUST NOT** 被原地修改，变更 **MUST** 产生新版本 |
| G-3 | 改变语义时 **MUST** 新建概念，**MUST NOT** 复用旧名 |
| G-4 | 破坏性变更 **MUST** 提供弃用期 |
| G-5 | 核心层定义 **MUST** 支持完整导出，格式 **MUST** 独立于实现 |
| G-6 | 变更 **MUST** 可自动计算影响面 |
| G-7 | 核心层 **MUST NOT** 引用任何扩展层 |

### 25.2 五要素（对象 · 关系 · 规则 · 策略 · 动作）

| # | 条款 |
|---|---|
| E-1 | 契约 **MUST** 按五要素声明；**MUST NOT** 增设第六个要素 |
| E-2 | 规则 **MUST** 以两种形式之一声明：**约束式**（Ossie `requires`）或**派生式**（Ossie `derived_by`） |
| E-3 | **解析归入规则**：派生式声明的产物 **MUST** 是派生对象（对象侧），**MUST NOT** 被当作独立要素或独立存储 |
| E-4 | **若实现声明了策略**，策略 **MUST** 显式声明其**依据的规则集**（论域 = 该规则集筛出的合法候选集） |
| E-5 | **若实现声明了策略**，策略 **MUST NOT** 改变合法性判定（值域只有序与选中项，**MUST NOT** 输出合法与否） |
| E-6 | **若实现声明了策略**，每个策略判定 **MUST** 携带选择依据（对应 `I3-2` 的溯源精神） |
| E-7 | 「策略」与「授权策略」**MUST** 分列：前者问"选哪个"（要素），后者问"谁可以"（I4 权限） |
| E-8 | 规则与策略 **MUST NOT** 产生状态变更；**产生状态变更的声明 MUST 属于动作** |

> **条款背后的理由都在 §5.3（三条切割线）与 §5.4（为什么派生与撤回不占要素）** —— 本节只列可验收的要求，不重复论证。
>
> **E-4~E-6 是条件式的，这是有意的**：不声明策略的实现（如仅做校验与派生的实现）**不因缺少策略而不合规**——"没有优选需求"是合法状态。但**一旦声明**，就必须满足论域、值域、依据三条，否则策略会退化成"用规则的口吻表达偏好"。

> **E-1 与 E-3 是一起读的**：五要素里没有"派生"，因为派生的声明归规则、产物归对象。若把派生单列成要素，就会出现"规则产出要素"这种跨要素的生产关系，要素间的边界随之失效。
>
> **E-8 是"联动"的归宿**：凡"改一个参数、相关参数跟着变"这类声明，都不可能是规则或策略（两者都不产生状态变更），只能是动作的效果，或派生对象的重新求值。

### 25.3 I1 语义接口

| # | 条款 |
|---|---|
| I1-1 | **MUST** 支持按版本读取定义 |
| I1-2 | **MUST** 提供定义自检（环、悬空引用、冲突） |
| I1-3 | **MUST** 支持任意两版本的差异对比 |
| I1-4 | 同一次操作内 **MUST** 读到同一版本的定义 |
| I1-5 | **SHOULD** 提供定义的人类可读视图 |

| # | 条款 |
|---|---|
| I2-1 | 所有写入 **MUST** 经过规则校验；校验失败 **MUST** 拒绝且**无副作用** |

## 26. 四阶段路线

### 阶段一：跑通一条链路

```
Ossie 定义 3~5 个概念 → 手工灌数据 → SQL 查询 → 1 个动作 → 1 个 MCP 工具
```
**交付物**：能演示"定义 → 事实 → 查询 → 动作 → Agent"的最小系统。

### 阶段二：补治理

```
数据契约（ODCS）+ 拒收区 + 身份解析（先规则）
```
**交付物**：一个数据源稳定接入，脏数据被隔离而非污染。

### 阶段三：补权限与审计

```
OpenFGA + 审计表 + CloudEvents
```
**交付物**：能回答"谁在何时基于什么做了什么"。

### 阶段四：补治理流程与规模化

```
提案/评审工作流 + CDC + 列存 + 图库（如需要）
```
**交付物**：能跑通一次完整的变更提案。

### 26.1 工作量分布（定性）

| 层 | 相对工作量 | 性质 |
|---|---|---|
| **L1 接入与治理** | **最大** | 无标准可循，要对付"多源、异构、脏、身份不一致" |
| L5 动作 | 大 | 抽象模型要自己定 |
| L3 语义 | **最小** | **Ossie 白拿** |
| L2/L4 | 中 | 有现成产品 |
| 治理流程 | 中 | 组织成本 > 技术成本 |

> **最费工的一层最不性感；最值钱的一层（L5）最容易被忽略；
> 而大家都在做的 L3，恰恰是最便宜的那块。**

## 27. Agent-first 设计原则（v0.2 新增为显式原则）

**v0.1 的缺陷：把 Agent 相关的设计散落在各处，没有上升为原则。**

**Agent 和人消费语义的方式根本不同：**

| | 人 | Agent |
|---|---|---|
| 消费方式 | 看图表、点按钮、读文字 | **读结构化能力描述** |
| 出错时 | 问人、查文档 | **只能靠自己重试** |
| 需要 | 可读性、美观 | **可验证的来源 + 预算感知 + 可自纠的拒绝** |
| 规模 | 几个 | **可能几百个并发** |

**四条设计原则：**

| # | 原则 | 体现 |
|---|---|---|
| **1** | **一切可枚举** | Agent 无法"猜"有什么，必须能列出来（I6） |
| **2** | **一切可溯源** | Agent 的结论必须能指回具体事实（I3-2） |
| **3** | **拒绝即可自纠** | 拒绝信息必须足以让 Agent 自己改对（I4-5、I4-8） |
| **4** | **一切有预算** | Agent 会无意识烧钱，接口必须能限（I3-4、A-3） |

> **这四条不是"为 Agent 优化"，而是"为 Agent 而设计"——因为 Agent 是这套语义背景的主要消费者。**

## 28. 尚未解决的问题

### 28.1 v0.1 的九条批判及处理

| # | 批判 | 处理 |
|---|---|---|
| 1 | 「共同」与「开放修改」矛盾 | ✅ 已在 §0.5 明确取舍：开放提案/分叉/退出，不开放就地修改 |
| 2 | 三种用途一套要求 | ✅ 已在 §3 引入 Profile A/B/C |
| 3 | 单域架构 vs 多域 | ✅ 中央式确认；域作为内部划分；**发现机制（I6）成为对齐入口** |
| 4 | 「L5 直调 L2」掩盖难点 | ✅ 已在 §18.1 修正为专用一致性读路径（R1~R4） |
| 5 | 派生不落库 vs 前置条件冲突 | ⚠️ **仅提出候选解法，未解决**（见 §28.2-1） |
| 6 | 缺发现能力 | ✅ 已新增 I6 |
| 7 | 「治理」被当成技术问题 | ✅ 已提升为第一部分（§1~3） |
| 8 | Normative / Informative 混杂 | ✅ 已分列第七、第八部分 |
| 9 | 无 Agent-first 原则 | ✅ 已在 §22 设为显式原则 + 规范性条款 §25.9 |

### 28.2 仍然未解决的（诚实）

| # | 问题 | 为什么难 |
|---|---|---|
| **1** | **派生不落库 vs 前置条件** | 事务内算闭包——性能、正确性、成本三难。候选解法均无定论（§18.2） |
| **2** | **撤回与派生的冲突** | 撤一条前提，依赖它的派生结论要失效；"多条独立支撑"的记账成本高 |
| **3** | **动作抽象模型没有先例** | Palantir 未公开。本框架给的是**候选设计**，不是定论 |
| **4** | **身份解析的准确率上限** | 规则解决约 80%，剩下 20% 必须人工。**且它是脏数据的头号来源** |
| **5** | **合规删除的完整性** | 删了实例，派生的向量 / 摘要 / 缓存要不要删？怎么验证删干净了 |
| **6** | **定义变更的影响分析** | 需要自动算爆炸半径，尚无标准做法（G-6 只规定了"必须能算"，没规定怎么算） |
| **7** | **核心层该多"瘦"** | 太瘦则各域重复定义，太胖则治理成本爆炸。**没有客观标准** |
| **8** | **治理的组织成本** | **本体不是"建"出来的，是"谈"出来的。** 技术解决不了 |
| **9** | **"强 TBox"是否普遍适用** | 本框架预设"语义定义应当独立成层"。**若语义本就稳定、消费者很少，本框架是过度的** |

**⚠️ 第 8、9 条是对本框架本身的质疑，值得认真对待：**

> **第 8 条**：本框架给了治理的技术机制（§1），但**治理真正难的是让人达成共识**。
> 一个高效的提案系统也救不了一群谈不拢的人。
>
> **第 9 条**：采用本框架 = 选择"强 TBox"路线。
> **如果你的场景里语义稳定、消费者很少，那用一张表 + 一段代码就够了，不要用这个框架。**
